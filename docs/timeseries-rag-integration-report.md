# 센서 경보와 정비 이력 연결 보고서

검토 브랜치는 `feat/timeseries-rag-demo`다. 개발을 시작한 GitHub main은 `33f429c`였고, PR 준비에서 후속 main 커밋 `3c743d2`를 반영했다. ML이 보낸 1분 센서값으로 과거 해결 사례를 찾고, 작업자가 화면에서 해결을 확인하면 그 조치가 다음 경보의 근거가 된다.

[A~D 실제 화면 시연](timeseries-rag-browser-demo.html)에서 경보 전송, 화면 클릭, Aura 저장과 재사용을 따라갈 수 있다. [50건 정량 평가](../rag/evaluation/timeseries_report.md)에는 자동 매뉴얼 검색과 해결 카드 재현의 Precision·Recall을 정리했다.

## 기존 main에서 바뀐 점

| 기존 main | 통합 브랜치 |
|---|---|
| API와 화면이 ML의 WARNING/CRITICAL 구분을 따라 정비 흐름을 선택한다. | API에서 시계열 경로를 활성화하면 v1.4 케이스의 안내를 **장비 E코드 → 과거 해결 사례 → 매뉴얼 후보** 순서로 결정한다. 기존 경보의 긴급도 표시는 유지한다. |
| WARNING은 물리 센서 세 개의 상승·하락이 모두 같은 이력을 찾는다. 별개 해결 케이스 두 건이 있어야 자동 카드로 표시한다. | **같은 채널의 초별 원시값**을 비교한다. 검토를 마친 해결 기록 한 건부터 Claude가 적용 가능성을 판단하고, 작업자가 과거 사례를 확인할 수 있다. |
| 기존 매뉴얼 후보는 등록된 사례에서 선택한다. | 모델이 검색된 PDF의 점검·조치 원문을 인용해 등록 목록 밖 후보도 제시할 수 있다. 새 PDF 근거는 해결 후 검토가 끝나면 다음 경보의 비교 대상이 된다. |
| E코드 안내와 WARNING 해결 종료가 별도 경로에 있다. | 새 화면은 E코드 안내도 표시한다. 같은 종료 절차에서 선택 근거와 실제 조치, 해결 결과를 해당 경보에 연결한다. |

새 경로는 API에서 `RAG_WARNING_TIMESERIES=1`을 켠 뒤 받은 v1.4 케이스에 적용된다. API가 생성할 때 케이스의 처리 방식을 기록하므로 이미 진행 중인 케이스는 기존 화면과 저장 흐름을 사용한다. 이 방식으로 팀이 데모 브랜치에서 새 동작을 검토하면서 기존 케이스도 열어 볼 수 있다.

## 담당 모듈별 개발 의도와 코드 변경

### ML. 조기 경보와 후속 E코드를 한 케이스에 연결한다

조기 경보를 보고 점검을 시작한 뒤 장비가 E코드를 보고할 수 있다. 두 이벤트를 같은 화면에서 확인할 수 있도록 v1.4 핸드오프에 선택 필드 `episode_id`를 추가했다. 이 ID는 설비 ID와 UTC로 정규화한 조기 경보 시작 시각으로 만든다. 후속 E코드는 코드가 관측된 센서 창에서, 그 시점에 이미 진행 중이던 조기 경보가 있을 때 같은 ID를 사용한다. 한 요청에서 여러 분의 센서를 처리해도 뒤에서 시작한 경보가 앞서 발생한 코드를 가져가지 않게 했다. [ML 발행 코드](../ml/main.py#L1833) · [에피소드 ID 계산](../ml/main.py#L1943)

한 요청에 조기 경보가 두 번 시작되는 경우, 기존 v1.4의 `early_warning.since`는 최신 센서 창을 기준으로 한다. 새 `episode_id`는 실제 전송한 첫 경보의 시작 시각으로 계산한다. 기존 `since`와 `event_id` 계산 방식은 유지해 이전 핸드오프와 재전송 중복 처리에 영향을 주지 않는다.

예를 들어 10:00에 조기 경보로 케이스가 열리고 같은 이상 상황에서 10:03에 E012가 관측되면, API는 후속 이벤트를 같은 설비·에피소드의 열린 케이스에 붙인다. **두 이벤트의 `event_id`와 각 센서 원본은 따로 남는다.** 작업자는 어느 이벤트를 보고 조치했는지 구분할 수 있다. `gun_id`는 한 케이스에 묶을 이벤트를 구분한다. RAG가 과거 해결을 검색하는 범위는 장비 적용 범위로 정한다. [API 케이스 등록](../api/main.py#L125)

기존 v1.4 `sensor_features`의 `c1`~`c19` 1분 변화점과 결측 초를 계속 보낸다. ML의 상위 기여 피처도 기존 형식으로 전달한다. RAG가 19채널을 복원하고 비교하므로 별도의 `comparison_channels` 목록은 필요 없다. 장비 코드와 관측 시각은 기존 핸드오프 필드에 들어간다. 모델 학습·이상 점수·임계값·발행 조건·쿨다운은 기준 main의 동작을 따른다. 운영 모드에서는 조기 경보 조건이 충족되거나 장비 코드 규칙이 발동할 때 핸드오프가 나온다. [센서 블록과 기여 피처 구성](../ml/main.py#L2049)

`RSW_DEMO_REPLAY=1`로 실행하면 모델 파일 없이 준비된 합성 경보 A~D를 전송할 수 있다. 각 요청을 받을 때 1분 파형은 유지하고 발생 시각은 재생 시점으로 옮긴다. 이후 운영 경보와 같은 전송 큐를 통해 API에 보낸다. A를 해결로 닫는 것과 다음 경보를 전송하는 것은 별개의 동작이다. [시연 모드 시작](../ml/main.py#L1570) · [합성 경보 전송](../ml/main.py#L2110)

### API. 화면에서 선택한 경보와 근거를 해결 기록까지 연결한다

- **수신과 조회를 분리.** ML 이벤트의 원시 블록을 Aura에 등록하고, 케이스와 화면 상태는 기존 API 저장소에 둔다. Aura 등록이 일시적으로 실패하면 보관한 원본으로 판정이나 종료 시 재시도할 수 있다. 케이스를 열면 UI가 판정을 한 번 요청하고, 결과 조회는 저장된 판정을 읽는다.
- **중복과 후속 코드 처리.** 동일한 ML 이벤트는 케이스를 중복 생성하지 않는다. 같은 에피소드에 코드가 오면 새 이벤트를 기존 열린 케이스에 추가하고, 다시 열 때 최근 코드 이벤트를 우선 표시한다. 화면에 이미 입력 중인 작업자는 현재 선택을 유지하며 다른 경보를 직접 고를 수 있다.
- **선택 근거 확인.** API는 해당 경보에 반환했던 카드와 PDF 근거를 보존한다. 해결 종료에는 실제로 표시했던 항목만 선택할 수 있다. 거절한 과거 카드는 그 경보에서 선택 대상에서 빠진다.
- **카드 거절 이후의 후보.** 과거 카드의 `manual_case_id`와 생성 후보의 `evidence_id`를 구분해, 거절한 과거 카드를 제외한 뒤에도 새 PDF 후보와 수동 검색 근거를 선택할 수 있다. API 회귀 테스트에서 거절, 재검색, 화면 재조회, 근거 선택을 확인한다. [카드 거절 회귀 테스트](../api/tests/test_timeseries_bridge.py#L64)
- **해결 전송 재사용.** 케이스 종료와 Aura 전송 대기는 기존 SQLite 트랜잭션에 함께 기록한다. 백그라운드 작업이 Aura의 새 해결 경로에 같은 이벤트를 멱등하게 저장한다. SQLite는 케이스 진행·임시 입력·전송 대기를 담당하고, **다음 경보에서 재사용하는 정비 이력은 공용 Aura**에서 읽는다. 오알람으로 닫은 사건은 해결 사례가 되지 않는다.

### RAG. 검색 점수와 정비 사례의 적용 판단을 분리한다

- **등록된 E코드가 우선.** 장비가 보고한 코드가 KG에 있으면 구조화된 점검·조치와 PDF 출처를 조회한다. 이 경로에는 Claude 판정과 임베딩 검색 호출이 없다.
- **E코드 없는 경보.** 같은 장비 범위에서 이전에 해결·검토된 이벤트의 원시 센서 구간을 조회한다. 19채널을 같은 채널과 상대 시각끼리 비교하고, 값 차이와 관측 범위로 상위 5건을 정렬한다. Claude는 후보의 원시값과 정비 기록을 함께 보고 `seen`, `unseen`, 판단 보류 중 하나를 선택한다. 유사도 점수는 후보 순위를 정하는 데 쓰인다. C처럼 유사도가 높은 사례도 중요한 채널의 변화 양상이 다르면 재사용하지 않을 수 있다.
- **검토할 자료와 실제 조치를 구분.** `seen`은 Aura에서 기존 조치·해결 시각·PDF 근거를 가져온다. `unseen`은 작업자가 요청할 때 기존 키워드·벡터 매뉴얼 검색을 사용한다. 수동 검색에서 E코드를 참고 문서로 입력하면 그 코드의 KG 근거를 함께 보여주고, 검색된 검토 사례는 바로 선택할 수 있다. 참고 검색어가 장비에서 보고된 오류 코드로 바뀌지는 않는다.
- **검증 가능한 이력.** 해결은 판단에 사용한 이벤트와 연결한다. 새로운 PDF 근거는 검토 완료 이후의 경보부터 재사용한다. 센서 원본·판정·해결 관계는 매뉴얼 KG 재구축 대상 밖에 보관한다.

### UI. 기존 케이스 화면에서 안내를 검토하고 해결을 기록한다

**작업함과 상세 화면.** 고장 분류명이 없는 시계열 경보는 ML이 보낸 요약을 작업함의 현상 칸에 표시한다. API가 `rag_mode: "timeseries"`로 표시한 케이스는 초기 경보가 WARNING이든 E코드 이벤트든 공통 정비 안내 화면을 연다. 이 모드는 API의 `RAG_WARNING_TIMESERIES=1` 설정으로 받은 새 v1.4 케이스에 적용된다. 기존 케이스는 생성 시점의 흐름으로 열린다. [작업함 표시](../ui/src/pages/InboxPage.tsx#L178) · [상세 화면 분기](../ui/src/pages/case/OverviewPage.tsx#L13)

**판정 요청과 후속 경보.** 화면은 선택된 `event_id`의 결과를 먼저 조회한다. 아직 판정이 없으면 `POST …/warning/assess`를 한 번 보내고 결과를 다시 읽는다. 열린 시계열 케이스의 상세 정보는 5초마다 갱신한다. 후속 장비 코드가 들어오면 새 이벤트가 있다는 안내를 띄우고, 작업 중인 경보 선택은 유지한다. 조치를 임시 저장한 뒤 드롭다운에서 후속 이벤트를 고를 수 있다. 케이스를 새로 열 때는 API의 `preferred_event_id`로 후속 코드를 우선 볼 수 있다. [케이스 갱신](../ui/src/lib/useCase.ts#L12) · [이벤트 선택과 판정 요청](../ui/src/pages/case/WarningPage.tsx#L57)

| RAG 응답 | 화면과 작업자 행동 |
|---|---|
| 등록 E코드 | 장비 보고 코드와 오류 설명, 매뉴얼의 점검·조치 카드와 PDF 페이지를 표시한다. 작업자가 적용할 카드를 선택한다. |
| `seen` | 이전 실제 조치, 해결 시각, 과거 이벤트 ID, 비교 이유와 PDF 근거를 보여준다. **맞아요 · 이 사례 선택**을 누르면 적용 근거가 선택된다. **아니에요**를 누르면 과거 카드가 빠지고 후보 보기나 수동 검색으로 이어갈 수 있다. |
| `unseen` | 적용할 과거 해결 사례가 없다는 상태를 보여준다. **원인 후보 보기**를 누르면 자동 후보를 요청한다. **직접 매뉴얼 검색**으로 작업자가 확인한 증상을 입력할 수 있다. |
| 판단 보류·미등록 E코드 | 현재 상태를 표시하고 매뉴얼 검색으로 이어진다. 판단 보류에서는 이력 판정을 다시 요청할 수 있다. |

**근거 표시와 선택.** 센서 관측을 펼치면 채널별 첫값·마지막값·관측 초·변화 횟수가 보인다. 과거 이력을 비교한 경우 후보별 검색 점수도 펼쳐 볼 수 있다. 생성 후보에는 제목, 선정 이유, 점검 또는 조치 원문, PDF 링크가 표시된다. 등록 카드는 `manual_case_id`, 생성 후보와 수동 검색의 PDF 근거는 `evidence_id`로 선택한다. 수동 검색은 현재 경보의 센서 소견과 작업자의 질문 한 건을 사용한다. [카드·관측·검색 표시](../ui/src/pages/case/WarningPage.tsx#L128)

**해결 기록과 반영 상태.** 근거를 고른 뒤 기존 점검·조치 양식에서 작업자와 실제 조치를 입력한다. 해결 확인과 일지 승인까지 체크하면 **해결 결과 저장·종료**가 활성화된다. API는 선택된 `event_id`에 해결을 연결한다. UI는 공용 이력 반영 대기·완료·근거 검토 대기·실패를 표시한다. **오알람으로 닫기**는 별도의 종료 동작이다. [선택과 종료 양식](../ui/src/pages/case/WarningPage.tsx#L222)

## A~D 실험 설계와 HTML 시연

**시나리오 선정.** 첫 해결이 바로 다음 경보에 도움이 되는지, 파형이 비슷해도 정비 방향이 다를 때 이전 사례를 걸러낼 수 있는지, 이력이 두 건으로 늘면 그중 맞는 조치를 보여주는지 차례로 확인하려고 네 상황을 골랐다. ML 예시의 v1.4 구조와 값 범위를 참고해 합성 1분 파형을 만들었다. 네 입력 모두 장비 보고 E코드를 비워 이력 판단을 거치게 했다. 정비와 해결 결과는 시연용 가정이다. 각 경보의 판정 입력에서 그 경보의 기대 결과와 예정된 조치를 제외했다. 저장을 확인한 A·C의 조치는 후속 경보의 비교 이력으로 사용했다. [A~D 입력과 기대 결과](../rag/demo/timeseries/README.md)

**실행 순서.** 빈 Aura 시연 영역에서 브라우저 자동화가 A를 ML 재생 API에 넣었다. ML이 전송 큐를 통해 API에 전달한 뒤 실제 React 작업함에서 **점검 시작**을 눌렀다. A의 해결이 Aura에 반영된 뒤 B를 전송했다. B의 카드 선택을 확인하고 C를 보냈으며, C의 별개 해결이 반영된 뒤 D를 전송했다. B가 비교할 수 있는 해결은 A 한 건, D가 비교할 수 있는 해결은 A와 C 두 건이었다. [브라우저 실행 순서](../rag/demo/timeseries/browser_demo.py#L42)

| 입력 | 시나리오에서 확인할 것 | 실제 클릭과 관찰 결과 |
|---|---|---|
| **A · 첫 압력 저하** | 새 경보에서 수동으로 근거를 찾아 첫 해결을 남길 수 있는가 | `unseen`. **원인 후보 보기**는 생성 오류를 반환했다. **직접 매뉴얼 검색**에서 보정 설정 압력과 공급 압력의 관계를 찾아 `manual:E012-C1`을 골랐다. 조치와 작업자 확인을 입력하고 **해결 결과 저장·종료**를 눌러 Aura 반영을 확인했다. 검색에 사용한 E012는 매뉴얼 참고용이었다. |
| **B · 압력 저하 재발** | 명령과 힘·압력 파형이 비슷한 다음 경보가 A의 조치를 보여주는가 | `seen → demo-A`, 검색 점수 약 **0.993**. 과거 실제 조치와 PDF 출처를 보고 **맞아요 · 이 사례 선택**을 눌렀다. |
| **C · 압력은 비슷하고 위치는 계속 이동** | 검색 점수가 높아도 필요한 조치가 다르면 A를 제외할 수 있는가 | A와 약 **0.978**이었지만, 위치가 계속 이동하고 힘·닫기 명령의 변화가 다르다는 이유로 `unseen`이 나왔다. 자동 후보는 근거 부족을 반환했다. 수동으로 누설·드리프트 근거 `manual:E029-C1`을 찾아 별개 해결로 저장했다. |
| **D · 위치 유지 이상 재발** | A와 C가 함께 검색될 때 C의 조치와 출처가 그대로 나오는가 | `seen → demo-C`. C 약 **0.999**, A 약 **0.977**이었다. C에서 저장한 조치와 PDF 출처를 확인하고 **맞아요 · 이 사례 선택**을 눌렀다. |

첫 브라우저 실행에서는 A와 C에 전극 위치 감시 설정이 후보로 나왔고, 표는 HTML에 담은 최종 실행 결과다. 두 실행에서 A·C는 수동 검색으로 시나리오의 근거를 골랐다. 최종 실행에서는 A·C 해결 두 건이 센서 원본에 연결됐는지 Aura에서 확인했고, 실행 종료 후 시연 데이터를 정리했다. B·D에서는 과거 카드를 선택하는 단계까지 확인했다.

**HTML 보는 법.** [A~D 실제 화면 시연](timeseries-rag-browser-demo.html)을 브라우저로 열고 A~D 탭과 **이전·다음** 버튼을 누르면 실제 UI 캡처 18장과 각 단계에서 누른 버튼을 확인할 수 있다. GitHub에서 파일을 받는 경우 HTML을 내려받아 브라우저에서 열면 된다. 보고서는 서버 없이 열린다. 새 경보를 보내거나 검색을 다시 실행하려면 아래 재현 절차로 서비스를 시작한다.

이 실험은 ML 서버의 핸드오프부터 API·RAG·UI·Aura까지 이어지는 흐름을 검증했다. 네 파형의 ML 탐지 성능과 현장 정비 효과는 별도 실험이 필요하다. 장비가 실제로 보고한 E코드 경로와 후속 코드 연결은 별도의 회귀 테스트에서 확인했다.

합성 데이터 전처리·학습과 v1.4 핸드오프·에피소드 연결을 포함한 ML 회귀 34개가 통과했다. 나머지 54개는 이번 실행에서 선택하지 않았다. 기준 main에서도 NaN을 강제로 넣는 테스트가 최신 FastAPI에서 실패했다. 직렬화 결과가 HTTP 500이거나 숫자 필드의 `null`로 나올 수 있어, 테스트가 두 경우 모두 잘못된 핸드오프로 확인하도록 보완했다. 실제 전송에서 비정상 기여 피처를 거르는 로직은 기존 동작을 따른다. [ML 회귀 테스트](../ml/tests/test_pipeline.py#L1894)

## 팀에서 다시 실행하기

저장소 루트에서 Python 환경에 ML·API·RAG 요구사항과 Playwright를 설치하고, `ui`에서 `npm ci`를 실행한다. Microsoft Edge가 있는 환경의 예시다. 팀 Aura, Claude와 임베딩 설정은 기존 RAG `.env`를 사용한다.

```powershell
python -B -m rag.demo.timeseries.run_browser_demo --output rag/var/browser-demo
python -B -m rag.demo.timeseries.render_report rag/var/browser-demo docs/timeseries-rag-browser-demo.html
```

다른 작업본의 환경을 읽을 때는 `--env-file <기존 rag/.env 경로>`를 붙인다. 재생기는 루프백의 ML·API·UI 서버를 실행하고, 별도 API 저장 파일과 Aura 이력 이름을 사용한다. 결과 JSON, 브라우저 캡처와 로그는 출력 폴더에 남는다. 실제 UI의 클릭 순서는 [A~D 화면 시연 보고서](timeseries-rag-browser-demo.html)에서 확인할 수 있다.

## 팀 검토에서 확인할 항목

- 자동 후보는 센서 관측의 차이가 검색어와 매뉴얼 검색 결과에 반영되는지 먼저 개선할 필요가 있다. 시연에서는 수동 검색으로 점검 근거를 찾았다.
- 현장 ML이 발행한 독립 경보와 실제 해결 이력으로 검색 상위 5건의 정답 포함률, 잘못된 `seen`, 판단 보류를 측정한다. 작업자 비교 실험에서는 올바른 첫 점검을 고르는 시간과 적합률을 같이 본다.
- 운영할 설비 범위, Aura 이력 이름, 모델 사용 설정과 적용 시점을 맞춘다. 과거 해결 이력은 일치하는 원시 핸드오프를 확보한 건부터 연결할 수 있다.
- 여러 에피소드와 다양한 운영 조건에서 뒤늦은 E코드의 연결을 추가 검증한다. 이력이 늘어날 때 조회 시간과 모델 호출량도 측정한다.
