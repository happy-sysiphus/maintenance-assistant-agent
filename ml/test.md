# 테스트셋 성능 (현재 모델)

대상: `models/baseline_ensemble.joblib` — IsolationForest(300 trees, 시각·c7~c9 제외) + LightGBM(고장 전 1h vs 정상) 앙상블(각 점수의 학습 정상 CDF 평균), 60초 윈도우 46피처(c19 제외), 건별 centering(워밍업 6시간, 워밍업 중 모델 알람 보류) + 건별 임계값, 글로벌 임계값 0.9458(학습 정상 점수 99% 분위수), sustain 3, 비용접 게이트 0.5
데이터: `test/` 8파일 → `preprocessed/test/`(학습과 같은 전처리·스케일러) → 80,533 윈도우
재현: `python .py/train.py --exclude-non-welding --cv 4` → `python .py/train.py --evaluate`(둘 다 기본 `--model ensemble`) → `models/baseline_ensemble_test_metrics.json`, `models/scores/test_N_ensemble.csv`
경과(이전 모델의 수치, 절제 실험, 바뀐 이유)는 `history.md`에 있다. IsolationForest 단독(이전 운영 모델)과의 비교는 `history.md` 18절.

## 1. 판정

**불충분(개선 중).** 앙상블로 고장 10분 전 분리력이 올랐지만(규칙 이전 AUROC 0.619→0.671) 30분 이상 선행하는 지속 알람은 여전히 없고, 고장 직전 확인은 종료 코드 규칙이 한다.

| 기준 | 목표 | 현재 | 판정 |
|---|---|---|---|
| 고장으로 이어지는 지속 알람(3회 연속)이 뜨는 건 수 | 8건 중 과반 | **2/8**(선행 2분·10분 — 규칙 구간) | ✗ |
| 그 알람의 선행 시간 | 30분 이상 | — | ✗ |
| 운영점(선행 ≥30분 & 오탐 ≤1회/일/건) 충족 건 | 과반 | 0/8 | ✗ |
| 정상 구간 알람률 | 1% 안팎 (설계) | 0.6%, 건별 0.1~1.4% (sd 0.4%) | ✓ |
| 정상 구간 지속 오탐 | 건당 하루 1회 이하 | 0~0.83회/일, 8/8건 충족 | ✓ |
| 종료 코드 규칙(모델 무관 기준선, 서빙과 같은 방식) | — | 8/8건, 선행 중앙값 9.2분 · critical 오트리거 0.18회/일/건(8/8건 ≤1회/일; 24h 안 반복 발화 4회는 warning으로 강등) | 규칙이 모델보다 낫다 |

파이프라인이 실제로 보장하는 것: (1) 정상 구간 오탐 0.6%(건별 편차 작음; 워밍업 6시간은 모델 알람 없음), (2) 종료 코드 규칙(`rule_triggered`, 에피소드 시작 시 1회·30분 쿨다운, 같은 코드가 24h 안에 이미 발화했으면 `rule_repeat` = warning)에 의한 고장 직전 ~10분 critical, (3) 상시 점수와 피처 기여도.

- 에러 상태 윈도우 알람률 3.8%(모델). 종료 코드 규칙은 서빙과 같은 방식(4개 코드 전부, 에피소드 시작 시 1회, 30분 쿨다운, 24h 반복 강등)으로 평가한다: 트리거 22회 중 8회가 고장 전 1h 안(8/8건)이고, 14회는 다른 클래스의 종료 코드(주로 E029)가 고장 며칠 전에 뜬 오트리거다. 그중 4회(전부 test_1)는 같은 코드가 24h 안에 이미 발화한 반복이라 warning으로 강등되고, critical 오트리거는 10회(test_0 0.72·test_1 0.29·test_4 0.29·test_5 0.14회/일).
- 비용접 게이트로 보류된 알람 404건, 게이트 대상 윈도우 5.3%.
- 클래스당 1~3건이라 클래스별 수치는 건 하나에 좌우된다. 분할 하나의 AUROC는 ±0.04 흔들린다(4-fold).
- AUROC 계열의 음성은 정상 창이다(에러 상태 창은 양쪽 어디에도 넣지 않는다). 운영점의 "마지막 지속 알람"은 고장 24h 이내에 시작한 것만 센다.

### 2.4 논문 프로토콜 비교 (60초 뒤 작동 상태 분류)

논문(Wang et al. 2024, Table 12)은 다음 60초의 상태를 정상 / E01~E04로 분류해 평가한다. 같은 프로토콜(`.py/paper_task.py`, `results/B-6/`): 60초 윈도우마다 다음 윈도우의 상태(종료 코드 E012/E016/E028/E029 → E01~E04, 없으면 정상)를 맞힌다. 테스트 8건:

| | 정확도 | 정상 재현율 | 고장 재현율 | E01 | E02 | E03 | E04 |
|---|---|---|---|---|---|---|---|
| 논문 (TFT/RF 예측 + 진단 규칙) | 0.686 | 0.443 | 0.743 | 0.358 | 0.195 | 0.238 | 0.184 |
| **이 파이프라인** (현재 종료 코드 → 클래스, `known_code_class_hint`) | **0.999** | **1.000** | **0.986** | 0.333 | **0.667** | **0.400** | **0.992** |
| 상태 + onset 모델 (LightGBM, 센서 + 에러 코드 이력) | 0.996 | 0.997 | 0.986 | 0.333 | 0.667 | 0.400 | 0.992 |

- 오탐(정상을 고장으로 오인)은 논문 56% → 0.03%. E01은 테스트 고장 상태 윈도우가 3개라 1윈도우 차이다(64건 4-fold E01 0.66).
- **이 지표는 예측력을 재지 않는다.** 고장 상태는 한 번 뜨면 수 분~수일 지속되므로 "다음 60초 = 지금"이 거의 다 맞는다. 예측이 필요한 **onset**(지금 정상 → 60초 뒤 고장, 테스트 22회)은 어떤 모델도 못 맞힌다: onset AUROC 0.61~0.65, 오탐 0.1% 예산(학습 표본 기준 명목값 — 실제 오탐률은 더 높다)의 재현율 0/22. 선행 10분·1시간에서도 onset AUROC 0.58~0.66.
- 결론: 논문 기준은 이미 넘는다(ML이 아니라 상태 코드 매핑으로). 우리가 목표로 하는 "고장 1시간 전"은 여전히 1절의 판정 그대로다.


## 3. 왜 부족한가

- **단일 모델로는 정보가 모자라고, 결합해야 조금 나온다.** 지도학습(LightGBM) 단독과 비지도(IsolationForest) 단독은 CV·테스트에서 서로 반대로 틀린다 — 둘의 CDF 평균이 둘 다보다 낫다(4-fold 규칙 이전 0.594 → 0.644). 지도학습만 섞은 조합은 CV가 더 높아도 새 건(테스트)에서 무너진다(`history.md` 18절). 30분 이상 선행은 여전히 없다.
- **신호는 사실상 마지막 10분(종료 코드 상태)에만 있다.** 레이블 창을 좁힐수록 AUROC가 오르지만(4-fold IF: 15분 0.778, 30분 0.683, 60분 0.631, 120분 0.588), 고장까지 남은 시간 구간별로 보면 0~10분만 0.77~0.84이고 10분 밖은 어느 구간이든 0.59~0.67이다. 그 10분은 규칙이 이미 잡으므로 레이블 창은 1시간을 유지하고 규칙 이전 성능(`auroc_pre_rule` ≈ 0.6)을 따로 본다.
- **"변동성(`_std`)이 전조"도 아니다.** `_std` 피처들은 판 두께 설정 전환(`c16_std`)과 ρ 0.8~0.9로 움직이는 프로그램 전환 지표이고, 현재 데이터에서 고장 전 1h와 정상의 효과 크기는 0.05 미만이다. 논문 타깃 c5·c2의 평균도 거의 움직이지 않는다.
- **모델은 종료 상태에도 약하다.** `error_code`는 입력이 아니고 `error_share_10min`은 코드가 뜬 뒤 수 분이 지나야 커진다. 이 구간은 규칙이 맡는다.
- **평가 불확실성.** 테스트 8건·검증 14건, 클래스당 1~3건. 폴드 간 AUROC 0.59~0.70.

## 4. 시도했으나 채택하지 않은 것

모두 같은 레시피(c16 ≤ 0 규칙, 비용접 제외 학습, 게이트 0.5, 건별 centering + 임계값) 위에서 검증 14건 / 테스트 8건으로 비교했다(정비 이력·레이블 창 행은 64건 4-fold + 테스트 8건, 발화 분류기는 건 단위 leave-one-out). 표와 경과는 `history.md`의 구 test.md 8절, 11절(B-5), 12절(B-6), 13절(B-7). 표의 AUROC는 당시 정의(에러 상태 창을 음성에 포함)다 — 같은 표 안의 비교는 유효하다.

## 5. 다음 단계

제공된 데이터 외에 다른 데이터는 없다(프로젝트 전제). 이 데이터로 만들 수 있는 피처(윈도우 통계·이력·잔차·정비 이력·에러 코드 이력·상태별 물리 피처)는 모두 시도했고, 고장 10분 이전 분리력은 단일 모델로 AUROC ~0.6, IsolationForest + LightGBM 앙상블로 4-fold 0.64·테스트 0.67이다. 남은 데이터 질문(고장 전 비용접, E02 수집 시기, 두꺼운 판)도 확인했고 구성 변경 사유는 없었다(`history.md` 21절).

1. 앙상블의 약한 곳: E04(드리프트) 테스트 AUROC 0.62, 검증 건 2개의 정상 구간 지속 오탐 > 1회/일, 건별 최대 5.5%(E02_13). 구성 요소를 더 섞으면 CV는 오르지만 새 건에서 떨어진다 — 설정값 전환 창 처리(B-8)도 창 단위로는 오탐과 전조를 가르지 못했다 — 남은 후보는 전환 이벤트 단위 비교(techspec B-8).
2. 규칙 쪽 개선: 오트리거의 71%는 여전히 첫 발화다. 건의 형식(어떤 고장 유형에 취약한지)을 알면 다른 클래스 코드를 거를 수 있다(오트리거는 전부 다른 클래스 코드였다, C-3).
