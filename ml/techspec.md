## 방향 (2026-10-06)

"수 시간 전 예지"는 이 데이터로 불가로 판정했다(`history.md` 26절). 목표는 **고장 즉시 감지 + 유형 판별 + 원인·조치 안내(정비 어시스턴트)** — ML은 알람 품질(오알람·신뢰도)과 하류 연동에 집중하고, 예지용 피처·모델 실험은 더 하지 않는다. C-5(critical 오알람 감소)는 완료(`history.md` 27절).

## 0. 범위

| 포함 | 제외 (다른 담당) |
|---|---|
| 이상탐지 모델·학습·평가(`.py/train.py`, `.py/experiments.py`) | api(케이스)·RAG(원인·점검·매뉴얼 조회) |
| 종료 코드 규칙과 서빙의 ML 로직(`main.py`의 스코어링·규칙·건별 상태) | RAG 검색, LLM 리포트, Slack 알림 |

경계: ML은 **① 이상 감지 + ② 사실(종료 코드·고장 유형·센서 소견)**까지 하고 `RagHandoff`를 api(`POST /api/ml/handoffs`)에 넘긴다. api가 종료 코드로 RAG를 부르고 답을 저장한다. ML이 받는 것은 api의 접수 응답(`{"result": …}`)뿐이다(readme 5.10.6).

## 2. ML 파트

### B-8 설정값 전환 창의 오탐 (개선 — 데이터 안에서는 해법을 찾지 못함)

- **현재**(운영 앙상블): 4-fold 정상 알람률 0.8%, 건별 최대 5.5%(E02_13; 5% 게이트 근소 초과). 정상 창의 44%가 설정값(c13~c16) 전환을 포함하고, 그 창의 알람률이 1.35%로 나머지(0.29%)의 4.6배 — 정상 알람의 79%가 전환 창이다(`results/B-8/`, `history.md` 20절).
- **기각된 것**: 설정값 피처 제외(`_std`만 / 전부: 건별 최대 8~14%, 테스트 규칙 이전 하락), 전환 창 알람 보류(건별 최대 1.6%지만 테스트 recall 6.4 → 2.9%), 보류 + 비전환 창 기준 임계값(건별 10.8%, 테스트 recall 3.1%), 창 유형별 임계값(건별 10.9%, 테스트 규칙 이전 0.609 → 0.587), 24h 재센터링(17절). **테스트 건의 고장 전 알람 절반 이상이 전환 창에 있다** — 전환 중 거동이 전조이자 오탐원이라 창 단위로는 가를 수 없다.
- **관련 발견(A-2)**: 얇은 판 건에 드물게 나오는 두꺼운 판(c16 = 8.7) 창은 11~100%가 알람(테스트 6건 110창, 그 건들 정상 알람의 ~7%) — 같은 전환 문제다.
- **남은 후보**: 전환 직후 N분의 거동을 같은 설정값 조합의 과거 전환과 비교하는 전환 이벤트 단위 모델(건 상태에 조합별 전환 이력 필요). 크기 중~대, 이득 불확실.
- **완료 기준**: 64건 4-fold 건별 정상 알람률 최대 ≤ 5%, 정상 알람률·`auroc_pre_rule`은 폴드 편차 안, 테스트 규칙 이전·recall 비하락.

### C-3 건 프로파일로 다른 클래스 종료 코드 거르기 (품질)

- **현재**: 반복 강등 후에도 테스트 critical 오트리거 0.18회/일/건(10회). 남은 오트리거는 **전부 그 건의 고장 유형과 다른 클래스의 종료 코드**다(주로 E029). 서빙은 건의 클래스를 모르므로 거를 수 없다. 또 쿨다운이 코드를 가리지 않아 test_3처럼 E016 직후의 E029가 눌린다(`MEMORY.md` §7-9).
- **설계**
  - 선택 입력 `GunProfile{gun_id, expected_fault_classes: list[E01..E04] | null}` — `PUT /guns/{id}/profile`. 없으면 지금과 같다(모든 코드 critical).
  - 프로파일이 있으면 목록 밖 클래스의 코드는 `rule_triggered=true, rule_out_of_profile=true`, severity `warning`(반복 강등과 같은 처리), 핸드오프 없음.
  - 코드별 쿨다운(`rule_last_trigger`를 코드별로)은 프로파일과 함께 넣을 때만 켠다 — 프로파일 없이 켜면 오트리거가 는다.
  - 평가: `evaluate()`에 "파일 클래스를 프로파일로 줬을 때"의 규칙 기준선을 추가(오프라인에서는 파일 클래스가 곧 프로파일).
- **완료 기준**: 테스트·검증에서 프로파일 기준 critical 오트리거 ≈ 0, 적중 8/8·14/14 유지. 프로파일 없는 요청은 기존 응답과 바이트 단위로 같다(회귀 테스트).
- **필요한 것**: 현장에서 건별로 어떤 고장 유형에 노출되는지(건 모델·공정) 정보. 없으면 이 항목은 보류.

### B-9 모델 교체 게이트 (공통 규칙)

- 앙상블 교체는 끝났다(2026-09-29, `history.md` 18절: IF+LightGBM, 운영 기본 `models/baseline_ensemble.joblib`). 아래 게이트는 이후 모든 모델·피처 변경에 공통이다.
- **모델 교체 게이트**
  - 비교는 64건 **4-fold**로(단일 분할은 ±0.04 흔들림). 후보가 여럿이면 선택 규칙을 결과를 보기 전에 고정한다: `auroc_pre_rule`의 4-fold 평균 − SD(하한) 순, 근접(0.005)하면 최저 폴드가 높은 쪽, 그다음 구성이 단순한 쪽.
  - 채택 조건: `auroc_pre_rule` 4-fold 평균이 현재 대비 **현재 폴드 표준편차 이상** 오르고, 테스트 8건에서 떨어지지 않으며(떨어지면 탈락 — 선택에는 쓰지 않는다), 정상 알람률 ≤ 1.5%, 건별 알람률 최대 ≤ 5%(현재 앙상블 5.5% — B-8). `auroc`(풀링)만 오른 변경은 채택하지 않는다(마지막 10분 = 규칙 몫일 수 있다).
  - 후보 비교의 실험 틀(`results/B-9/ensembles.py`)은 운영 경로와 수치가 다르다(같은 IF+LGBM이 틀 0.596 / 운영 0.671): 최종 판정은 운영 경로(`train.py --cv 4` + `--evaluate`)로.
  - 누설 점검: 새 피처의 건 안 경과 시간 Spearman |ρ| > 0.5면 기각(c19 사례). 룩백 피처는 6시간 상한.
  - 테스트 안에서 순위를 매긴 점수(전이적 순위)는 서빙이 재현할 수 없으므로 쓰지 않는다.

## 3. RAG 핸드오프

받는 쪽 합의는 끝났다(2026-10-28, `history.md` 37절). 받는 곳은 api이고, 필드는 v1.2 그대로다. RAG 입력은 api가 꺼낸 종료 코드다. 그래서 D-2(입력 형식 연동)는 닫았고, D-4(RAG 응답 검증)는 RAG 답이 ML로 오지 않아 뺐다.

### D-3 핸드오프 v1.1 — 맥락 확장 (품질)

- **2026-10-08 일부 구현(FE 요청 3)**: `error_timeline`은 버퍼(약 30분) 범위, `sensor_trend`는 trace ring에서 30분을 복사한다(1분 링버퍼 없이). 아래 표의 나머지 셋과 1h 코드 이력은 남았다.
- **현재**: 핸드오프는 이벤트 윈도우의 요약(센서 편차, 종료 코드, 고장 유형)에 위의 `error_timeline`·`sensor_trend`를 더해 담는다. readme 3절의 "이상 감지 시점 앞뒤의 센서 수치·로그를 모아 컨텍스트 구성"은 부분 구현이다.
- **추가 필드(전부 선택·추가만 — 1.x 호환 규칙)**

| 필드 | 내용 | 이유 |
|---|---|---|
| `error_timeline[]` | 최근 1h의 에러 코드 에피소드 `{code, start, end, duration_s, class_hint}` | 종료 코드 전후의 잔고장(E003 등)이 원인 분석 단서. 진짜 발화의 21%가 직전 1h에 다른 코드를 동반했다(오트리거는 7%) |
| `sensor_trend[]` | 기여 상위 센서의 최근 30분 1분 평균 시계열(z) | 화면(api·UI)이 "언제부터 어떻게" 변했는지 보여 줄 수 있게. **데이터는 `GET /guns/{id}/trace`의 `points[].deviation`으로 이미 있다(2026-09-28) — 핸드오프에 30분 분량을 복사하면 된다** |
| `recent_events[]` | 같은 건의 최근 24h 핸드오프 `{event_id, detected_at, trigger.rule_code}` | 반복 고장·연쇄 판단 |
| `trigger.rule_repeat_suppressed` | 같은 요청에 강등된 반복 발화가 있었는지 | 지금은 반복 발화가 핸드오프에서 사라진다(규칙 근거에서 제외) |
| `detector.reliability` | `{auroc_pre_rule, rule_lead_min_median, rule_false_per_day}` — 번들 지표 | api·UI가 신뢰도를 수치로 보여 주도록(RAG는 핸드오프를 읽지 않는다. 현재 `caveats`는 고정 문구) |

- **설계**: `error_timeline`·`sensor_trend`는 30분 버퍼로 부족하다 → 건 상태에 1분 요약 링버퍼(60~120개)를 둔다(건 상태 파일에 함께 저장). `schema_version` "1.1".
- **완료 기준**: `tests/test_rag_mapping.py::test_schema_keys_match_main` 갱신, v1.0 소비자(필드 무시)가 깨지지 않음을 예시 JSON으로 확인, 실데이터 재생 이벤트 9건의 `error_timeline`에 종료 코드 에피소드가 들어 있다.

## 4. 공통 규칙

- 학습·서빙이 같은 절차를 쓰는 로직(건별 정규화, 규칙, 윈도우)은 **오프라인 함수와 온라인 함수를 한 쌍으로** 고치고, `tests/test_pipeline.py`에 둘의 일치 단언을 둔다.
- `AnomalyResult`·`RagHandoff`는 계약이다: 필드 추가만, 삭제·의미 변경은 버전 올림과 하류 합의.
- 실험·모델 변경은 §B-9 게이트로 판정하고 `history.md`에 절을 추가, `readme.md`·`test.md`는 결과만 덮어쓴다.
