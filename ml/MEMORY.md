# MEMORY.md — 설계 결정 기록

이 파일은 **왜 그렇게 만들었는지**를 남기는 곳이다. 무엇이 어디에 있는지는 `readme.md` 5절, 코드 동작은 각 스크립트 docstring을 본다.
결정이 바뀌면 해당 항목을 고치고 맨 아래 변경 이력에 한 줄 남긴다. 코드에서 읽을 수 있는 내용은 적지 않는다.

## 1. 프로젝트 목표

- 데이터: RSW 용접기 고장 예측 벤치마크(Wang et al., Sci Data 2024, `docs/RSW Paper.pdf`). train 72파일(E01~E04 × 18), test 8파일, 1 Hz × 7일.
- 논문의 2-stage(센서 예측 → 진단 규칙)는 오류 누적으로 정확도 68%/오알람 56% → **우리는 1-step 이상탐지**로 간다 (readme 2절).
- 최종 파이프라인: 이상탐지 시그널 → api(케이스) → RAG 원인·점검 안내(종료 코드 E012·E016·E028·E029, 매뉴얼 4종) → Slack (readme 3절). 2026-10-28부터 Slack 말고는 연결됐다(api·RAG는 다른 담당).
- 예지보전 범위(2026-11-01, 사용자 결정): 수 시간 전 예지는 불가(B-14) 그대로다. **몇십 분 전은 낮은 정밀도의 조기 경보(C-8)**로 운영에 넣는다. 미탐 우선이고 오알람 다수를 감수한다. 고장 즉시 감지·유형은 종료 코드 규칙이 맡는다.

## 2. 데이터에 대해 확정된 사실 (EDA, 72파일)

- **`error` 컬럼은 이벤트가 아니라 상태 코드**다. 같은 코드가 수 시간 지속(E003 중앙값 1.5~2h, 최장 16.5h; E011 최장 28h). 샘플 수로 세면 안 되고 에피소드(연속 구간)로 센다. gap이 에피소드를 끊지 않도록 코드를 gap 너머로 carry한다.
- **클래스별 종료 코드는 거의 결정적**: E01→E012, E02→E016, E03→E028, E04→E029 (18/18, 17/18, 18/18, 18/18), 모두 고장 전 10분 안에만 등장. 파일 마지막 행의 error는 대개 `0`(80개 중 62개)이라 "마지막 행"이 아니라 "마지막 수 분"을 봐야 한다.
- E003·E011·E029는 며칠 전부터 장시간 지속되므로 단독 전조로는 약하다. readme의 "잔고장 빈도 = 전조" 가설은 부분적으로만 성립.
- 결측은 행 단위 block-out. E01/03/04는 ~1%, gap 99%가 ≤35초. **E02 8개 파일(0,2,3,4,5,6,7,8)은 64~84%** → 논문 규칙(40%)으로 폐기. E02_2는 10분짜리 데모 파일.
- c16(판 두께 setpoint) **≤0 = 캡 드레싱 등 비용접 작업**, 파일당 0.1~44%(평균 10%). 학습 파일에서 `c16 > 5`는 행의 1.3% 미만이지만 그 행들은 시간당 800~980회 용접한다(얇은 판 구간 520~600회보다 빠름) — **`>5`는 두꺼운 판 setpoint이지 비용접이 아니다.** 학습 파일의 실제 비용접(카운터 정지)은 사실상 전부 `c16 == 0`. 벤치마크 코드의 `>5` 분기를 그대로 따랐던 2026-09-23 이전 규칙은 test_2·test_3(행의 85~92%가 `c16 = 8.7`)의 87~95%를 비용접으로 오분류했다. 단 그 두 건의 8.7 구간은 시간당 27~72회로 대부분 대기 상태다 — 저활동은 `welds_10min`·`weld_duty_10min`이 표현하고, `non_welding`은 setpoint 상태만 뜻한다.
- c7·c8·c9는 파일 내 상수(건 고유 속성). c11·c12는 누적 카운터라 절대값이 건마다 다르다. c17 거의 상수. **c4·c18은 0/1 비트** — Festo fieldbus 13번 비트의 짝: c18 = 로봇의 "Close gun"(건 닫기·힘 형성 명령), c4 = 건의 "Force reached"(설정 힘 − 실제 힘 < 100 N). 1분 평균은 켜진 비율(사실상 용접 활동량)이지 시간·설정값이 아니다(D-7, `history.md` 35절).
- 시각은 CSV의 `...Z`를 **naive UTC**로 통일한다(`pd.to_datetime(utc=True).tz_localize(None)`). 로컬(KST) 변환 금지 — `hour_sin/cos`가 틀어진다.
- E02 일부는 2019-12~2020-07, 나머지는 2021-08~10 수집. 시기 차이가 분포 차이를 만들 수 있음(미검증).
- 논문 타깃: E02는 c2(전극 압력), 나머지는 c5(밸런스 압력). 원본 벤치마크 코드는 이와 달리 c1~c5를 타깃으로 씀.
- **c19("offset value in robot")는 센서가 아니라 추세가 경과 시간을 따라 오르는 값**(2021년 파일 70개: 초당 44~56, 경과 시간과 상관 0.999 이상. 1초 단위로는 ±10만 안팎 오르내린다). 모든 파일이 정확히 7일이고 고장에서 끝나므로 건별 centering 후 c19 = 168h − 잔여 시간 = **레이블 누설**. 지도학습이 c19로 AUROC 0.98, 없이 0.62. `train.py` 기본 `--drop-features c19`(번들 `dropped_features`). 2026-09-23 발견(`history.md` 구 test.md 8.1절). 2026-09-26 재점검: 다른 피처의 건 안 경과 시간 상관은 |ρ| ≤ 0.32로 추가 누설 없음.
- **파일 = 에러(클래스 종료 코드 첫 등장, T) 앞 7일 + 뒤 10분.** 이 저장소의 '고장'(`ttf_s` = 0, 레이블)은 파일 끝 = T + 10분이고, 조기 경보(B-18 · C-8 · A-5)의 '종료 코드 10–60분 전'은 T 기준이다. 적중 트리거 72건의 선행(파일 끝 기준)이 중앙값 10.0분, IQR 10.0~10.0(2026-09-26): 규칙은 에러가 뜬 순간에 잡을 뿐 미리 알지 못한다. 그래서 짧은 레이블 창의 AUROC 이득은 전부 이 마지막 10분(종료 상태)에서 나온다.
- **운전 맥락(A-4, 2026-11-01, `history.md` 40절, `results/A-4/report.md`)**:
  - c1 = 캡 마모 보정값이다. 드레싱마다 +0.3 mm, 캡 교체 때 ~3 mm 감소(c16 = 8 / 32 프로그램 직후).
  - 짧은 c16 = 0(≤ 60초)은 드레싱 동작이고, 긴 것은 정지다.
  - 결측 60초 초과의 71%는 생산이 계속된 기록 누락이다(카운터 평소 속도).
  - E003·E011은 야간 정지(03~07시) 상태 코드다.
  - 가동은 07시 기동·03시 정지, 택트 ~77초.
  - **79파일 = 물리적 건 72개**: (c7, c8, c9) + 카운터 연속. 6묶음 13파일이고, 그중 겹치는 쌍 4개는 다른 고장 유형이며, test_0 = E03_9의 건이다.
  - 고장 상당수는 기동·전원 차단 순간이고, 4묶음 13건이 동시다.
- **고장과 운전 전환(A-5, 2026-11-01, `history.md` 44절, `results/A-5/report.md`)**:
  - 사례-교차(같은 건·같은 시각 1~6일 전 대조)에서 E01·E03 고장 직전 30분 기동(10분+ 꺼짐 뒤 켜짐)이 55% vs 19%였다(OR 11.8, 사전 고정 가설 통과).
  - 기동에 이은 24건 중 20건은 용접 0타에서 났다 = **기동 점검 실패**.
  - E04는 18/21이 꺼짐 구간 안(꺼진 지 중앙값 3.8분)이다 = **전원 차단 상태 코드**. E01도 12/20이 전원 차단과 함께 뜬다.
  - 생산 중 고장은 E02뿐이다. 72건 중 56건이 전환에 걸려 있다(사후 정의).
  - 같은 건의 여러 기동 중 어느 것이 실패할지는 맥락으로 갈리지 않는다.
  - 탐색: 종료 코드 10–60분 전 짧은 전원 깜빡임(5초–10분)은 36% vs 17%였다.
    - 후속(`results/A-5/overlap.py`, 사전 고정): B-20 조기 경보에 얹으면 +4.8점 [−1.3, +11.2]이다. 테스트에서 늘어난 적중이 없다(3건 모두 모델도 잡음).
    - 그래서 **조기 경보에 넣지 않는다**.
    - 깜빡임 단독은 모델과 같은 초과분(+14.6)을 오알람 7.3회/건·일로 낸다. 같은 고장으로 고른 신호라 현장 재검정용 가설로만 남긴다.
- **`_std` 피처는 프로그램 전환 지표다.** c2~c5·c13·c18의 `_std`는 `c16_std`(판 두께 설정 전환)와 ρ 0.8~0.9로 움직인다. 현재 데이터에서 고장 전 1h 효과 크기 < 0.05 — `history.md` 3.1절의 "흔들림이 전조"(d 0.57)는 구 c16 규칙 시절 값이라 성립하지 않는다.

## 3. 전처리 결정 (`.py/preprocess.py`)

| 결정 | 이유 |
|---|---|
| 결측률 >40% 파일 폐기 | 논문 규칙. 80%대 파일은 ffill해도 상수 덩어리 |
| gap ≤60초 ffill, 초과 gap은 행 삭제 + `segment_id` 분리. 구현은 `preprocess.fill_gaps` 하나이고 `main.py`도 이것을 import한다 | gap 99%가 ≤35초. 윈도우가 구멍을 넘지 않게. **2026-09-22판은 `ffill(limit).bfill(limit)`이라 실제로는 120초까지 메꿨다**(학습 15개 파일·test_5에 해당 gap 존재) — 합성 데이터 스모크 테스트가 잡아냄. 같은 로직을 두 곳에 복제하지 말 것 |
| 비용접 = `c16 <= 0`만(`--outlier-hi` 기본 None; `--outlier-hi 5`로 논문·벤치마크 규칙 복원) | §2 c16 항목. `>5` 분기는 두꺼운 판 용접을 비용접으로 오분류해 test_2·test_3에서 오탐의 전부를 만들었다 |
| 비용접 행은 센서값 blank → 직전 용접값 carry(길이 제한 없음), 행은 유지 + `non_welding` 플래그 | 논문 방식. 60초 제한을 걸었더니 고장 직전 1시간이 날아가는 파일(E01_0)이 있었음 |
| c11·c12 → `welds_delta`, `pos_delta`, `welds_10min` | 건 간 비교 가능한 값으로 |
| `error_active`, `error_share_10min`, `terminal_code` 파생 | 상태 코드를 피처와 레이블 양쪽으로 쓰기 위해 |
| `weld_duty_10min`은 비용접 carry **전의 실측 c2**로 센다(2026-09-29) | carry 후 값으로 세면 캡 드레싱 중에도 직전 용접값(c2>0)이 "용접 중"으로 잡혔다. `main.py`도 같은 순서 |
| `ttf_s` + `label`(마지막 3600초=1) | 지도/비지도 양쪽에서 쓸 수 있게. 윈도우 길이는 옵션 |
| z-score를 **정상행(`label==0 & error_active==0`)** 으로만 fit, `scaler.json` 저장 | 비지도 학습 관례. 테스트/서빙에 동일 변환 적용 |
| `error_share_10min`, `weld_duty_10min`은 스케일링 제외 | 이미 0~1 비율. 정상행 기준 z-score가 30 같은 값을 만들었음 |
| 기본은 global 스케일, `--scale per-file`·`--drop-static` 옵션 | 건 간 오프셋 제거는 실험 대상 |
| 테스트 8파일은 `--split test`로 **같은 코드 경로**를 타되, 옵션은 train의 `preprocess_config.json`, 스케일러는 `scaler.json`을 읽어서 적용(재적합 금지). 출력은 `preprocessed/test/` | 학습/테스트 변환이 한 글자라도 다르면 평가가 무의미. train 산출물(manifest, scaler)을 덮어쓰지 않으려고 하위 폴더 |
| 테스트 파일 클래스는 **마지막 10분의 종료 코드**로 추론(`class_source`에 근거 기록). 여러 코드가 있으면 고장에 가장 가까운 것 | 파일명(`test_N`)에 클래스가 없다. 2절의 종료 코드 매핑이 71/72로 결정적이라 신뢰 가능. test_3은 E016→E029 순이라 E04 |

## 4. 모델링 결정 (`.py/train.py`)

- 60초 윈도우 집계(연속 피처 mean+std = 46 피처; c19 제외 전에는 48). 37M 초 단위 행을 그대로 쓰지 않는다 — 메모리와 시간 문제, 그리고 윈도우 통계가 시간 맥락을 준다.
- **B-2 실험 결론(2026-09-23, `history.md`(구 test.md 8절), `.py/experiments.py`, `results/B-2/`)**: 이력·추세 피처, 5분 창, 점수 EWMA/CUSUM, LSTM-AE, E02 전용 모델 — 전부 채택 안 함. 정직한 지도학습 상한선(c19 제외)이 검증 0.705 / 테스트 0.619로 비지도(0.647/0.636)와 같다 → **이 윈도우 통계에는 고장 1시간 전 정보가 없다(피처 문제, 모델 문제 아님)**. 운영점(선행 30분·오탐 1/일) 충족 테스트 건 0. **B-5(2026-09-26, `history.md` 11절, `results/B-5/`)**: 설정값 조건부 잔차, 정비 이력 피처(캡 드레싱·c1 변경, 6h 상한), 짧은 레이블 창 — 전부 채택 안 함(정비 피처는 IF 4-fold +0.03·테스트 −0.05로 매번 반대 방향 = 과적합). 데이터셋 안에서 만들 수 있는 정보는 소진 — 고장 10분 이전 분리력 AUROC ~0.6이 천장. **전제(2026-09-28 사용자 지시): 제공된 데이터 외에 다른 데이터는 없다** — "데이터셋 밖 정보원"은 다음 단계가 아니다. **B-7(2026-09-28, `history.md` 13절, `.py/physics.py`, `results/B-7/`)**: 상태별 물리 피처·점수 건별 이동 정규화 채택 안 함. IF + LightGBM 앙상블(`--model ensemble`)만 CV에서 폴드 sd 이상 올랐다(규칙 이전 0.585→0.681, 테스트 동률) — 운영 경로 검증 뒤 운영 모델로 채택(§5, `history.md` 18절). 구성은 CV로만 고르고, 테스트 안 순위(전이적)는 쓰지 않는다.
- **논문 비교는 논문 프로토콜로(B-6, 2026-09-28, `history.md` 12절, `.py/paper_task.py`, `results/B-6/`)**: 논문 68.62%/오탐 56%는 "다음 60초의 상태(정상/E01~E04) 분류"다. 우리 AUROC(고장 1h 전)와 직접 비교하지 말 것. 같은 프로토콜에서는 **현재 종료 코드 → 클래스(persistence = `known_code_class_hint`)만으로** 테스트 정확도 0.999·정상 재현율 1.000·고장 재현율 0.986, E02~E04 클래스 재현율 논문 이상(E01은 3윈도우라 동률 범위) — 상태가 수 분~수일 지속되기 때문이지 예측력이 아니다. 예측이 필요한 onset(정상→고장 전이)은 onset AUROC 0.61~0.73, 오탐 0.1%에서 테스트 0/22. "논문 수준 이상" 요구에는 이 표로 답하고, 개선 목표는 계속 `auroc_pre_rule`로 잡는다. 에러 코드 이력 피처(51개)는 1h 과제 4-fold +0.003·테스트 −0.09로 채택 안 함(정비 이력과 같은 과적합 패턴).
- **평가 설계(B-4)**: `evaluate()`가 운영점(`operating_point`: 선행 ≥30분 & 오탐 ≤1/일/건 충족 건 수)과 종료 코드 규칙 기준선(`rule_terminal_code`)을 항상 같이 낸다. 규칙 기준선은 **서빙과 같은 방식**(4개 코드 전부, 코드 시작 시 1회 — 코드 전환도 새 발화, 코드별 `RULE_COOLDOWN_S` 30분 쿨다운; 창 코드 플래그 `term_1..4` + `train.rule_events`, 플래그 없는 구 캐시는 `train.rule_triggers`)으로 적중(고장 전 1h 안 첫 트리거의 선행)과 오트리거/일을 낸다: 테스트 8/8건·9.2분·0.18회/일, 검증 14/14·9.4분·0.03회/일(반복 포함 0.25·0.05). 2026-09-24 전에는 파일 자기 클래스의 코드만 셌다(`terminal_code`) — 서빙은 클래스를 모르므로 다른 클래스 코드의 오트리거가 평가에서 빠져 있었다. `--cv k` 건 단위 층화 k-fold(폴드 간 AUROC 0.59~0.70, 한 분할 수치는 ±0.04 흔들림 — 구성 비교는 4-fold로), `--label-window`로 레이블 창 변경. **레이블 창은 1시간 유지**(2026-09-26): 좁히면 AUROC가 오르지만(IF 4-fold 15분 0.78 / 30분 0.68 / 60분 0.63) 고장까지 남은 시간 구간별로는 0~10분만 0.77~0.84, 10분 밖은 0.59~0.67 — 이득이 규칙이 덮는 구간에서만 나온다. 대신 **AUROC를 세 가지로 본다**: 풀링 `auroc`, 건별 평균 `auroc_gun_mean`(건 간 점수 오프셋 제거; 테스트 건별 0.24~0.89), 규칙 이전 `auroc_pre_rule`(고장 10분 이전 전조만 양성 = 모델이 규칙에 더하는 몫, `RULE_LEAD_S`). 규칙 기준선의 오트리거는 **critical 발화**(반복 제외) 기준이고 `all_triggers_false_per_day_mean`이 반복까지 센 값.

- 정상 = `label==0 & error_active==0`. **기본 학습은 `--exclude-non-welding`**(비용접 비율 > 0 윈도우 제외, 464k → 418k 윈도우). 성능 장치가 아니라 "비용접 중에는 판단하지 않는다"는 운영 규칙이다.
- **비용접 게이트**: 윈도우의 비용접 비율이 `--alarm-max-non-welding`(기본 0.5, `none`으로 해제)을 넘으면 점수가 임계값을 넘어도 알람이 아니다(보류). 평가와 서빙이 같은 규칙을 쓰도록 번들 `alarm_max_non_welding`에 넣는다. 지표에 `held_windows`(보류된 알람 수), `held_share_of_windows`(게이트 대상 윈도우 비율), `auroc_welding_windows`가 같이 나온다. 게이트가 사실상 두 건 전체를 가리는 구성(구 규칙 + 게이트: test_2·test_3의 99.8%)은 채택하지 않았다 — 오탐률은 0이 되지만 모델이 그 건을 보지 않는 것이다.
- **건별 정규화(B-1, 2026-09-23)**: 건마다 센서 오프셋이 최대 1.7σ라 글로벌 z-score + 글로벌 임계값은 건별 정상 알람률을 0~13%로 흩어 놓는다. `--scale per-file`은 서빙이 재현 못 하므로 **워밍업 방식**: 파일/스트림 첫 6시간의 정상·용접 행(600행 이상) 평균을 이후 행의 z-score 입력 18개(c19 제외)에서 뺀다(`--gun-norm center`, c7~c9는 0이 됨). 워밍업 구간은 글로벌 스케일로 점수화하고 `warmup` 플래그. 구현은 `train.window_file()`(오프라인)과 `main.Detector.gun_normalise()`(온라인) 한 쌍이고 레시피는 번들 `gun_norm`.
- **건별 임계값** = max(글로벌, 워밍업 윈도우 중 알람이 날 수 있는 창을 건별 통계로 재정규화한 점수의 99% 분위수; 10창 미만이면 없음). 기본 켜짐(`--no-gun-threshold`). 올리는 방향으로만 쓴다 — 360윈도우의 분위수는 거칠다.
- **`--gun-norm scale`(std까지 나눔)은 쓰지 말 것.** 검증 E04_4는 std가 하한에 걸려 이후 정상 알람률 56.5%(B-1). 워밍업이 정상 운전을 대표한다는 보장이 없으면 평균만 빼는 것이 안전하다. 같은 이유로 E04_4는 center에서도 높게 남는다(B-1 4.9%, 운영 앙상블 검증 3.0%) — 워밍업 뒤 가동 프로그램이 바뀐 건이다(`history.md` 17절). "정상 용접 N행" 워밍업은 B-8에서 기각(E04_4의 첫 6시간은 전부 정상 용접 행, 15절).
- 임계값 = 학습 정상 점수 99% 분위수(=오탐률 1% 설계). `sustain=3` 연속 초과를 "지속 알람"으로 정의 — readme 3절 알람 피로도 규칙에 대응.
- 평가는 AUROC/AUPRC(고장 전 1h vs 정상) + 정상 알람률 + 클래스별 + 파일별 "고장으로 이어지는 마지막 알람 구간 시작 시각"과 "24h 이전 오탐 에피소드/일". "최초 알람 시각"은 초반 오탐에 걸려 무의미해서 버렸다.
- 워밍업 윈도우(글로벌 스케일)는 학습 정상 집합에 **일부러 남긴다**. 서빙도 워밍업 구간을 같은 모델·글로벌 스케일로 판정하기 때문 — 빼면 AUROC는 같고 정상 알람률이 3배(검증 1.0→3.2%, 테스트 0.5→1.5%, 2026-09-26).
- 번들(joblib dict)에 `feature_reference`(정상 윈도우 중앙값)를 넣는다 — 서빙에서 피처 기여도 계산용.
- **지표 정의 정정(2026-09-29, `history.md` 14절)**: AUROC·규칙 이전 AUROC·AUPRC·클래스별 AUROC는 **고장 전 창 vs 정상 창**(에러 상태 창은 음성에서 뺌 — 건별 AUROC와 같은 정의). 운영점의 "고장으로 이어지는 마지막 지속 알람"은 **고장 24h 이내에 시작한 것만**(상시 알람이 선행 168h로 통과했다). 규칙 기준선의 적중 창은 `--label-window`와 무관하게 1h(`RULE_EVAL_WINDOW_S`). 건별 임계값 보정은 **알람이 날 수 있는 워밍업 창만**(에러 상태 아님, 비용접 비율 ≤ 게이트, 10창 이상 — `train.calibration_windows`/`gun_threshold`, 서빙 동일). 앙상블 양성에도 음성과 같은 비용접 필터.

## 5. 서빙 계약 (`main.py`)

- 입력은 CSV 컬럼 그대로(`time, c1~c19, error`). 서버가 건별 30분 링버퍼를 유지하고 전처리를 온라인으로 재현한다. 클라이언트는 아무 전처리도 하지 않는다.
- 출력 `AnomalyResult` 필드는 하류와의 **계약**이다: `is_anomaly, anomaly_score, threshold, score_z, severity(normal|warning|critical), sustained_alarm, consecutive_alarms, contributing_features[], context{latest_error_code, known_code_class_hint, ...}, model{}`. 필드를 빼거나 의미를 바꾸면 하류가 깨진다 — 추가는 자유.
- `severity: critical` = **C-9(2026-11-13)부터 종료 코드 규칙으로만 생긴다.** 모델 알람은 아무리 길어도 `warning`이다. `RSW_MODEL_CRITICAL=1`로 켠 서버에서만 예전 기준이 살아난다: 임계 초과(게이트 통과)가 **`critical_sustain × window` 초 이상 연속**(`alarm_duration_s`, 알람 시작 시각 기준; 2026-10-06 C-5부터 600초, 그 전·구 번들은 `sustain × window` 180초). 이게 그때의 핸드오프 기준. `sustained_alarm`은 계속 180초(warning 수준). 요청 횟수로 세면 호출 주기에 따라 3초~75분으로 바뀌었다(2026-09-24 수정). 청크 안의 완결 윈도우(연속 구간마다 분 경계 — C-2)를 모두 스코어링해 알람 상태를 윈도우마다 갱신하고, 청크 중간에 critical이 있었으면 `critical_in_request`/`sustained_in_request` — 하류 트리거는 `critical_in_request`를 본다.
- `contributing_features`는 모델 무관 perturbation(피처 하나를 정상 기준값으로 치환했을 때의 점수 감소). 모델을 바꿔도 이 방식은 유지 가능.
- `known_code_class_hint`는 모델과 무관하게 2절의 종료 코드 매핑으로 채운다. 모델이 약할 때 하류가 쓸 수 있는 안전장치. **B-3(2026-09-23)**: 그 규칙이 뜨면 `severity=critical` 강제, `rule_triggered=true`, `severity_source`(model/rule/model+rule/none). 모델이 종료 상태를 임계값 아래로 보는 문제(에러 상태 알람률 ~1%)를 규칙으로 메운다. 규칙이 보장하는 선행은 마지막 ~10분(코드가 그때 뜬다). **2026-09-24 수정: 상태가 아니라 에피소드 시작에서 1회 발화 + 건별 쿨다운 30분**(번들 `rule`; C-6부터 코드별 — 아래 C-6). 코드가 떠 있는 동안 계속 critical이면 E029가 다른 클래스 건에서 수 시간(테스트 test_0 16.2h·test_4 9.4h, EDA 최장 24h) critical을 냈다. `rule_code`/`rule_class_hint`는 발화시킨 코드(청크 끝에서는 코드가 이미 0인 경우가 대부분이라 `known_code_class_hint`로는 클래스가 사라진다). `rule_triggered`의 의미를 바꾼 것은 이 계약 변경의 예외 — 상태 의미는 `rule_code_active`로 남겼다. **반복 강등(2026-09-26)**: 같은 코드가 같은 건에서 `rule.repeat_s`(24h) 안에 이미 발화했으면 `rule_triggered=true` + **`rule_repeat=true`, severity `warning`, `critical_in_request=false`, 핸드오프 없음**. 80건에서 반복 발화는 18회 중 17회가 오트리거(적중 손실 1/72). 테스트 critical 오트리거 0.25→0.18회/일/건. 발화 시점 특징(코드, 주변 에러 코드, 점수, 센서)으로 진짜/오트리거를 가르는 분류기는 건 단위 CV AUROC 0.62로 버렸다. 구현은 `train.rule_events()`(창 코드 플래그 `term_1..4`, 반복 판정 포함) / `main.Detector.rule_check()` 한 쌍(쿨다운과 같은 구조). 플래그 없는 구 캐시·공통 쿨다운 구 번들은 `rule_triggers` + `rule_repeats`(창의 `terminal_idx`).
- 완결된 분 경계 윈도우(표본 30개 이상)가 아직 없으면 202 + `WarmingUp` 스키마.
- **이상 추적(2026-09-28)**: `GET /guns/{id}/trace`(스키마 `Trace`, 새 엔드포인트라 `AnomalyResult` 계약은 불변) + `/trace/view`(`static/trace.html`). 건 상태에 판정한 창 360개(6h)의 피처 벡터·판정을 링버퍼로 둔다. 차트 축 결정: 센서는 원 단위가 아니라 **모델 입력 − 정상 기준값(σ), ±4 고정**이다. 센서가 마스킹돼 단위가 섞여 있고, 모델이 본 값과 같아야 기여도와 맞기 때문이다. 1초 원시값이 아닌 60초 창 값을 쓰는 이유는 c2·c3·c5가 가압/해제 두 상태를 오가 빗살이 되기 때문이다. 점수 축도 고정한다(정상 점수 흔들림이 자동 스케일에서 이벤트처럼 보인다). 이중 축 없이 패널을 쌓는다. 기본 차트 피처에서 `error_share_10min`을 뺀다(코드 띠와 중복). 제목은 "이상 기여 센서"로 한다 — 물리적 원인이 아니다.
- 서빙의 건별 정규화(B-1): 건마다 첫 6시간(번들 `gun_norm.warmup_s`)의 행을 모아 두었다가 워밍업이 끝나면 건 평균과 건별 임계값을 고정한다. 그 전 응답은 `gun_norm: warming_up`(글로벌 기준), 이후는 `gun`; 정상·용접 행이 600개 미만이면 `global`. 응답의 `threshold`는 **그 윈도우를 판정한 값**(건별 있으면 건별), `model.threshold`는 글로벌. 요청당 최대 `MAX_CHUNK` = 1,200행(버퍼 `BUFFER_S` 1,860초 = 청크 + 롤링 이력 10분 + 다음 요청으로 넘어가는 미완결 분 1개)이고 넘으면 422 — 예전에는 3,600행까지 받아 버퍼를 넘는 행을 조용히 버렸다(50분 청크 → 워밍업 21,600행 중 13,688행만 수집). `DELETE /guns/{id}`가 워밍업을 재시작한다. 실측: 20분 청크로 test_0·3·6을 7일씩 보내면 점수·임계값·알람이 오프라인과 같다(C-2, `history.md` 15절).
- **서빙 견고화(2026-09-29, `history.md` 14절)**: `/predict`는 동기 함수(스레드풀, 건별 `threading.Lock`) — 요청당 ~40 ms 판다스 작업이 이벤트 루프를 막지 않게. 입력은 NaN/inf 거부(422, 오류 응답도 JSON 안전), 초 미만은 초로 내림. 한 요청의 시각 폭 > 30분이면 422, 건의 최신 시각보다 30분 넘게 과거면 409(잘못된 시각 한 줄이 30분간 건을 먹통으로 만들던 결함). 202 응답 중 뜬 종료 코드 발화는 `pending_rules` 대기열로 다음 200 응답에 싣는다. 규칙은 버퍼의 모든 세그먼트 코드를 본다(긴 gap 앞 코드 누락 수정). 발화 조건은 **종료 코드가 새로 생길 때**다 — 코드별 모드(C-6, 번들 `rule.per_code`)는 E016→E029 전환도 새 발화(오프라인 창 플래그 `term_1..4`와 일치), 공통 쿨다운 구 번들만 종료 코드가 하나도 없다가 생길 때(`terminal_any`). 비용접 carry는 **버퍼에서 밀려난 마지막 용접 행**(이전에는 버퍼 안 이후 값으로 덮였다). `context.welds_*`는 건별 centering **전** 프레임으로 원 단위 복원(이전에는 워밍업 후 +180/창 같은 값 — 증상 P4가 발동 불가). `critical_source`(요청 단위 위험 근거, 추가 필드)를 핸드오프 `trigger.source`가 쓴다. trace는 겹치지 않는 창만 쌓는다(요청 주기와 무관하게 6h).
- **상태 영속화(C-1·D-1, 2026-09-29, `history.md` 16절)**: `RSW_STATE_DIR`(기본 `state/`, gitignore; 빈 값 = 메모리만)에 건 상태 `guns/<gun_id>.json`(요청마다 원자적 쓰기)과 핸드오프 `outbox/<event_id>.json`. 결정: **버퍼·trace·진행 중 워밍업은 저장하지 않는다**(워밍업 행 최대 6h×1Hz를 요청마다 쓰는 비용 대비 이득 작음 — 워밍업 중 재시작은 워밍업 재시작). 번들 `created`가 다르면 건은 워밍업으로(건별 임계값은 옛 모델 점수 분위수), 규칙 이력은 유지. 재시작 직후 첫 창은 직전 창과 `gap_fill_limit + window` 안이면 같은 알람 런으로 본다(`GunState.restored`). push는 `outbox_worker`(1초 폴링) — 백오프 10s·30s·2m·10m, 5회 뒤 failed, 4xx(408·429 제외)는 "rejected"로 즉시 failed·재큐 안 함. `event_id` = sha1(건|창 끝|critical_source|규칙 시각)[:32] — 결정적이라 재생성돼도 같은 id, 수신 쪽이 `event_id`로 중복 제거(계약). `HandoffRecord`에 `attempts`·`last_attempt_at`·`next_attempt_at` 추가.
- **운영 모델 = IsolationForest + LightGBM 앙상블(2026-09-29, `history.md` 18절)**: `models/baseline_ensemble.joblib`(`main.MODEL_PATH` 기본). 4-fold 규칙 이전 0.594 → 0.644, 테스트 0.619 → 0.671, 정상 알람률 CV 0.8%·테스트 0.6%, 건별 최대 7.8 → 5.5%(E02_13; 5% 게이트는 근소 초과, IF보다 개선이라 채택). **선택 규칙(사용자 지시: robustness 중시)**: 조합은 CV로만 고르되 4-fold 평균 − SD와 최저 폴드로 순위, 정상 알람률 ≤ 1.5%·건별 ≤ 5%, 테스트는 현재 모델보다 떨어지면 탈락(선택에 쓰지 않음). B-9에서 CV 1위인 IF+LGBM+LGBM6h+ET(0.736 ± 0.027)는 운영 경로 테스트 0.607로 탈락 — 지도학습 구성이 늘수록 학습 건에 맞춰진다; 비지도(IF)를 빼면 새 건에서 무너진다(LR 0.42, LGBM 0.54). 서빙의 창 통계는 `train.window_features`를 그대로 호출한다(Series 통계는 1e-7 달라 LightGBM 분기가 뒤집혀 점수 최대 0.026 차이 — IF에서는 안 보이던 것).
- **워밍업 알람 보류(B-8, 2026-09-29, `history.md` 17절)**: 번들 `warmup_alarms: false`(기본; 구 번들은 true로 읽음) — 워밍업 창은 점수만 내고 모델 알람은 없다(`train.alarm_mask(warmup=)` / `Detector.in_warmup`, 응답 `alarm_held` + `hold_reason` "gun warm-up…"; `alarm_held` 설명을 "비용접 또는 워밍업"으로 넓힘 — 핸드오프는 critical에만 나가므로 하류 영향 없음). 워밍업이 `global`로 끝나는 건(정상·용접 행 < 600)은 온라인은 보류, 오프라인은 워밍업이 없어 첫 몇 시간 판정이 다르다(학습 64건 중 2건). 원인: 글로벌 스케일에서 건 상수 c7~c9가 최대 14σ. 기각: 24h 재센터링(테스트 규칙 이전 −0.02, 드리프트 신호 제거), c7~c9 제외(단독 효과 없음).
- **운영 모니터링(C-4, 2026-09-29)**: 건 상태 파일에 일 단위 카운터(`STAT_KEYS`, 31일). 창은 trace와 같은 조건(새로 채점된 비중첩 창)에서 한 번씩 센다. `GET /guns/{id}/stats`, `GET /stats`. `drift_warning`(응답·`/guns` 추가 필드): 워밍업 뒤 정상 알람률 3일 연속 > 3%(하루 정상 창 ≥ 360) 또는 하루 critical 규칙 ≥ 2. "정상" = 에러 코드 없는 창(서빙은 레이블을 모른다) — 오프라인 `alarm_rate_normal`(고장 전 1h 제외)과 테스트 8건 최대 0.05%p, 알람 수 전부 일치(앙상블).
- **서빙은 버퍼의 모든 연속 구간을 채점한다(2026-09-29, `history.md` 19절)**: `features()`가 버퍼 전체 + `segment` 열을 주고 `windows()`가 (구간, 분) 단위로 완결 창을 고른다. 전에는 마지막 구간만 — 한 요청이 긴 공백을 걸치면 공백 앞 완결 분이 채점·워밍업 수집에서 빠졌다(test_5 33창). 알람 런 초기화는 창 단위(직전 창과 `gap_fill_limit`+1초 넘게 떨어지면, 재시작 직후는 + window). "새 창 없음" 재채점은 현재 구간의 창만(공백 앞 창을 최신으로 돌려주지 않는다 → 202).
- **핸드오프 증상 임계값(D-5, 2026-09-29)**: `rag_mapping.MIN_SHARE` 0.03·`MIN_DEV` 0.5 — 80건 마지막 12h 재생의 이벤트 132개에서 0.05·1.0은 62%가 증상 0개(중앙값 0). 규칙(중앙값 1~3, 증상 0개 ≤ 25%, 현재 값에 가장 가까운 점)으로 골랐다; 정답 없음 → 정확도 근거는 아니다(`results/D-5/symptom_sweep.json`). 예시 JSON은 `docs/make_examples.py`로 다시 뽑는다.
- **critical 오알람 감소(C-5, 2026-10-06, `history.md` 27절)**: 모델 단독 critical = 알람 10창(600초) 지속(번들 `critical_sustain`), 30창 이상 유휴(가동률 < 0.02 또는 비용접 > 0.5) 뒤 30분은 모델 알람 보류(번들 `restart_hold`, `hold_reason` "restart"). 근거: critical 오알람 0.52회/일/건 중 대부분이 모델, 규칙이 놓친 고장을 모델이 잡은 것은 72건 중 0건(모델이 규칙보다 10분+ 앞선 건 3건). 사용자 결정으로 사전 선택(3창 + 보류)보다 공격적인 안 채택. 상태 기계 `train.restart_step` 하나를 오프라인·온라인이 공유. `sustained_alarm`은 3창 유지. **C-9(2026-11-13)부터 모델 단독 critical은 기본으로 꺼져 있다**(`RSW_MODEL_CRITICAL=1`일 때만 이 경로). 재가동 보류는 그대로다.
- **코드별 쿨다운·건 프로파일(C-6·C-3, 2026-10-06, `history.md` 30절)**: 규칙 쿨다운을 코드별로, 코드 전환(E016→E029)도 새 발화(번들 `rule.per_code`; 72건 적중 71→72, 오트리거 44 그대로). `PUT /guns/{id}/profile`의 고장 유형 밖 코드는 `rule_out_of_profile`(warning, 핸드오프 없음) — 파일 클래스를 프로파일로 주면 오트리거 0. 한 요청의 여러 발화는 응답에 첫 critical 발화를 싣고, 나머지 critical 발화도 그 요청에서 바로 핸드오프한다(`GET /handoffs`, `history.md` 31절 5). `pending_rules` 대기열은 202 응답 동안만 쓴다. 목표는 "고장 ~10분 전 알림"(선행 여지 없음, 남은 여지는 오트리거 = 현장 프로파일 정보). 몇십 분 전은 아래 C-8 조기 경보가 따로 맡는다.
- **조기 경보(C-8, 2026-11-01, `history.md` 43절)**: `severity`와 별개인 낮은 정밀도의 "수십 분 안 고장 가능성" 상태다.
  - 번들 `early_warning` 블록: rule·kind·sustain·threshold·quantile·cooldown_s·calibration·evidence.
  - 임계값은 `train.py --cv`의 폴드 밖 정상 점수 분위수로 정한다(없으면 val 파일). 운영 모델 자신의 fit 점수로 정하면 B-18이 쓴 모집단과 달라진다.
  - 상태 기계 `train.early_warning_step` 하나를 오프라인(`early_warning_flags`)·온라인(`Detector.judge`)이 같이 쓴다.
  - 응답·trace·`/guns`·`/stats`에는 필드만 추가했다(`early_warning*`).
  - 핸드오프는 기본으로 보낸다(C-9, 2026-11-13). `RSW_EARLY_WARNING_HANDOFFS=0`(`false` · `off` · `no`)으로 끈다. 그 전에는 `=1`일 때만 보냈다(api가 모든 핸드오프를 "긴급" 케이스로 받던 때). 지금 api는 `event_type`이 `early_warning`이면 WARNING 케이스로 받는다.
    - 보내는 시점은 에피소드 시작이다. 건별 쿨다운 60분이 있고, critical·종료 코드가 있는 요청에서는 보내지 않는다(`early_warning_handoff_suppressed`).
    - 문서는 v1.4다(v1.3의 `event_type` 위에 필드만 더했다). `event_type: "early_warning"`, `trigger.source: "early_warning"`이고, `rule_code`·`fault_class`는 없다. 건 프로파일은 `early_warning.candidate_*`에 후보로만 싣는다(진단 아님).
  - api·RAG 담당용 안내는 `docs/early-warning-handoff.md`.
  - 옛 번들(블록 없음)은 조기 경보 없이 그대로 동작한다. C-9부터는 그런 번들로 켠 서버에서 모델 신호가 하류로 가는 길이 없다(종료 코드 규칙만 간다).
- **critical은 종료 코드 규칙뿐(C-9, 2026-11-13, `history.md` 52절)**: 11-13에 main으로 들어온 변경이다(코드 주석: 멘토링 후 합의).

  - ML: `main.MODEL_CRITICAL`(`RSW_MODEL_CRITICAL`, 기본 `0`). 꺼져 있으면 `Verdict.critical`이 늘 거짓이라 모델 단독 핸드오프가 없다. `critical_sustain`은 번들에 남고 켰을 때만 쓴다.
  - `/model`에 `model_critical`(설정값)을 더했다. 응답 최상위의 `model_critical`(최신 창의 상태)과 이름이 같고 뜻이 다르다.
  - api: 조기 경보가 아니고 코드가 RAG 매핑(E012 · E016 · E028 · E029)에 없는 핸드오프는 케이스를 만들지 않고 본 것으로만 표시한다(`ignored_codeless_critical`). ML 규칙에 코드를 더하려면 매핑을 먼저 넓혀야 한다(한 번 버린 알림은 다시 받지 않는다).

  - 알아 둘 점: `RSW_EARLY_WARNING_HANDOFFS`에 빈 값이나 모르는 값을 주면 켜진다. 조기 경보 오경보 ~16회/건·일(B-20)이 이제 기본으로 api에 간다.

## 6. 코드 규약

- 스크립트는 `.py/`, API는 루트 `main.py`(`uvicorn main:app`). `main.py`는 `sys.path`에 `.py/`를 넣어 `train`, `preprocess`, `rag_mapping`을 import한다 — 번들 언피클에 `train.PCADetector`/`train.EnsembleDetector`가 필요하다. `train.py`를 스크립트로 돌려도 이 클래스들은 `train.X`로 피클되게 고정했다(`__main__.X`로 저장된 번들은 서빙이 못 읽는다, 2026-09-29).
- 모든 경로는 `PROJECT_ROOT = __file__ 기준` 으로 잡는다. cwd 의존 금지 (IDE에서 `.py/`가 cwd가 되어 KeyError가 났던 적 있음). 파일을 못 찾으면 즉시 `SystemExit`로 경로를 찍는다.

- 데이터 폴더(`train/`, `preprocessed/`) 안에 산출물을 쓰지 않는다. 결과는 `eda_out/`, `models/`, `results/`로.

- 환경: Windows, CPU-only torch, darts 0.41, pandas 2.3, sklearn 1.7, fastapi 0.121, pydantic 2.13. `accelerator="gpu"` 하드코딩 금지.

11. **같은 물리적 건이 여러 파일에 있다(A-4, `history.md` 40절)** — 건 단위 CV(파일 단위)가 같은 데이터를 학습·검증에 나눠 넣는다. E03_10·E01_3, E01_16·E03_3은 같은 주를 몇 시간 차이로 두 번 녹화한 쌍이다. E04_17·E01_13, E03_2·E01_15는 며칠 겹친다. 겹치는 파일에서는 다른 파일의 고장이 "정상" 구간에 들어 있다. 테스트 test_0은 학습 E03_9와 같은 건이다. 낙관 크기는 B-19(2026-11-01, `history.md` 41절)에서 쟀다: 물리 폴드 4시드 0.707 / 0.660 vs 파일 폴드 0.698 / 0.652, 테스트에서 test_0을 빼도 오른다 — **수치 낙관 없음**. 남은 것: 건 독립을 가정하는 곳(논문의 표본 수·동시 고장)에서는 이 묶음을 적는다.
