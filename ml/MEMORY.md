# MEMORY.md — 설계 결정 기록

이 파일은 **왜 그렇게 만들었는지**를 남기는 곳이다. 무엇이 어디에 있는지는 `readme.md` 5절, 코드 동작은 각 스크립트 docstring을 본다.
결정이 바뀌면 해당 항목을 고치고 맨 아래 변경 이력에 한 줄 남긴다. 코드에서 읽을 수 있는 내용은 적지 않는다.

## 1. 프로젝트 목표

- 데이터: RSW 용접기 고장 예측 벤치마크(Wang et al., Sci Data 2024, `docs/RSW Paper.pdf`). train 72파일(E01~E04 × 18), test 8파일, 1 Hz × 7일.
- 논문의 2-stage(센서 예측 → 진단 규칙)는 오류 누적으로 정확도 68%/오알람 56% → **우리는 1-step 이상탐지**로 간다 (readme 2절).
- 최종 파이프라인: 이상탐지 시그널 → 온톨로지/RAG 원인 분석(E01~E04 매뉴얼) → LLM 리포트 → Slack (readme 3절). 지금은 이상탐지 API까지 구현.

## 2. 데이터에 대해 확정된 사실 (EDA, 72파일)

- **`error` 컬럼은 이벤트가 아니라 상태 코드**다. 같은 코드가 수 시간 지속(E003 중앙값 1.5~2h, 최장 28h). 샘플 수로 세면 안 되고 에피소드(연속 구간)로 센다. gap이 에피소드를 끊지 않도록 코드를 gap 너머로 carry한다.
- **클래스별 종료 코드는 거의 결정적**: E01→E012, E02→E016, E03→E028, E04→E029 (18/18, 17/18, 18/18, 18/18), 모두 고장 전 10분 안에만 등장. 파일 마지막 행의 error는 항상 `0`이라 "마지막 행"이 아니라 "마지막 수 분"을 봐야 한다.
- E003·E011·E029는 며칠 전부터 장시간 지속되므로 단독 전조로는 약하다. readme의 "잔고장 빈도 = 전조" 가설은 부분적으로만 성립.
- 결측은 행 단위 block-out. E01/03/04는 ~1%, gap 99%가 ≤35초. **E02 8개 파일(0,2,3,4,5,6,7,8)은 64~84%** → 논문 규칙(40%)으로 폐기. E02_2는 10분짜리 데모 파일.
- c16(판 두께 setpoint) **≤0 = 캡 드레싱 등 비용접 작업**, 파일당 0.1~44%(평균 10%). 학습 파일에서 `c16 > 5`는 행의 1.3% 미만이지만 그 행들은 시간당 800~980회 용접한다(얇은 판 구간 520~600회보다 빠름) — **`>5`는 두꺼운 판 setpoint이지 비용접이 아니다.** 학습 파일의 실제 비용접(카운터 정지)은 사실상 전부 `c16 == 0`. 벤치마크 코드의 `>5` 분기를 그대로 따랐던 2026-09-23 이전 규칙은 test_2·test_3(행의 85~92%가 `c16 = 8.7`)의 87~95%를 비용접으로 오분류했다. 단 그 두 건의 8.7 구간은 시간당 27~72회로 대부분 대기 상태다 — 저활동은 `welds_10min`·`weld_duty_10min`이 표현하고, `non_welding`은 setpoint 상태만 뜻한다.
- c7·c8·c9는 파일 내 상수(건 고유 속성). c11·c12는 누적 카운터라 절대값이 건마다 다르다. c4·c18은 거의 이진, c17 거의 상수.
- 시각은 CSV의 `...Z`를 **naive UTC**로 통일한다(`pd.to_datetime(utc=True).tz_localize(None)`). 로컬(KST) 변환 금지 — `hour_sin/cos`가 틀어진다.
- E02 일부는 2019-12~2020-07, 나머지는 2021-08~10 수집. 시기 차이가 분포 차이를 만들 수 있음(미검증).
- 논문 타깃: E02는 c2(전극 압력), 나머지는 c5(밸런스 압력). 원본 벤치마크 코드는 이와 달리 c1~c5를 타깃으로 씀.
- **c19("offset value in robot")는 센서가 아니라 초당 ~55씩 단조 증가하는 카운터**(경과 시간과 상관 1.000). 모든 파일이 정확히 7일이고 고장에서 끝나므로 건별 centering 후 c19 = 168h − 잔여 시간 = **레이블 누설**. 지도학습이 c19로 AUROC 0.98, 없이 0.62. `train.py` 기본 `--drop-features c19`(번들 `dropped_features`). 2026-09-23 발견(`history.md` 구 test.md 8.1절). 2026-09-26 재점검: 다른 피처의 건 안 경과 시간 상관은 |ρ| ≤ 0.32로 추가 누설 없음.
- **"고장" = 종료 코드 + 10분.** 적중 트리거 72건의 선행이 중앙값 10.0분, IQR 10.0~10.0(2026-09-26). 규칙 선행 ~10분은 상한이자 데이터셋의 정의다. 그래서 짧은 레이블 창의 AUROC 이득은 전부 이 마지막 10분(종료 상태)에서 나온다.
- **`_std` 피처는 프로그램 전환 지표다.** c2~c5·c13·c18의 `_std`는 `c16_std`(판 두께 설정 전환)와 건 안 경과 시간 상관은 |ρ| ≤ 0.32로 0.8~0.9. 현재 데이터에서 고장 전 1h 효과 크기 < 0.05 — `history.md` 3.1절의 "흔들림이 전조"(d 0.57)는 구 c16 규칙 시절 값이라 성립하지 않는다.

## 3. 전처리 결정 (`.py/preprocess.py`)

| 결정 | 이유 |
|---|---|
| 결측률 >40% 파일 폐기 | 논문 규칙. 80%대 파일은 ffill해도 상수 덩어리 |
| gap ≤60초 ffill, 초과 gap은 행 삭제 + `segment_id` 분리. 구현은 `preprocess.fill_gaps` 하나이고 `main.py`도 이것을 import한다 | gap 99%가 ≤35초. 윈도우가 구멍을 넘지 않게. **2026-09-22판은 `ffill(limit).bfill(limit)`이라 실제로는 120초까지 메꿨다**(학습 15개 파일·test_5에 해당 gap 존재) — 합성 데이터 스모크 테스트가 잡아냄. 같은 로직을 두 곳에 복제하지 말 것 |
| 비용접 = `c16 <= 0`만(`--outlier-hi` 기본 None; `--outlier-hi 5`로 논문·벤치마크 규칙 복원) | §2 c16 항목. `>5` 분기는 두꺼운 판 용접을 비용접으로 오분류해 test_2·test_3에서 오탐의 전부를 만들었다 |
| 비용접 행은 센서값 blank → 직전 용접값 carry(길이 제한 없음), 행은 유지 + `non_welding` 플래그 | 논문 방식. 60초 제한을 걸었더니 고장 직전 1시간이 날아가는 파일(E01_0)이 있었음 |
| c11·c12 → `welds_delta`, `pos_delta`, `welds_10min` | 건 간 비교 가능한 값으로 |
| `error_active`, `error_share_10min`, `terminal_code` 파생 | 상태 코드를 피처와 레이블 양쪽으로 쓰기 위해 |
| `weld_duty_10min`은 비용접 carry **전의 실측 c2**로 센다(2026-09-29) | carry 후 값으로 세면 캡 드레싱 중에도 직전 용접값(c2>0)이 "용접 중"으로 잡혔다. `main.py`도 같은 순서 |
| `ttf_s` + `label`(마지막 3600초=1) | 지도/비지도 양쪽에서 쓸 수 있게. 윈도우 길이는 옵션 |
| z-score를 **정상행(`label==0 & error_active==0`)** 으로만 fit, `scaler.json` 저장 | 비지도 학습 관례. 테스트/서빙에 동일 변환 적용 |
| `error_share_10min`, `weld_duty_10min`은 스케일링 제외 | 이미 0~1 비율. 정상행 기준 z-score가 30 같은 값을 만들었음 |
| 기본은 global 스케일, `--scale per-file`·`--drop-static` 옵션 | 건 간 오프셋 제거는 실험 대상 |
| 테스트 8파일은 `--split test`로 **같은 코드 경로**를 타되, 옵션은 train의 `preprocess_config.json`, 스케일러는 `scaler.json`을 읽어서 적용(재적합 금지). 출력은 `preprocessed/test/` | 학습/테스트 변환이 한 글자라도 다르면 평가가 무의미. train 산출물(manifest, scaler)을 덮어쓰지 않으려고 하위 폴더 |
| 테스트 파일 클래스는 **마지막 10분의 종료 코드**로 추론(`class_source`에 근거 기록). 여러 코드가 있으면 고장에 가장 가까운 것 | 파일명(`test_N`)에 클래스가 없다. 2절의 종료 코드 매핑이 71/72로 결정적이라 신뢰 가능. test_3은 E016→E029 순이라 E04 |

## 4. 모델링 결정 (`.py/train.py`)

- 60초 윈도우 집계(연속 피처 mean+std = 46 피처; c19 제외 전에는 48). 37M 초 단위 행을 그대로 쓰지 않는다 — 메모리와 시간 문제, 그리고 윈도우 통계가 시간 맥락을 준다.
- **B-2 실험 결론(2026-09-23, `history.md`(구 test.md 8절), `.py/experiments.py`, `results/B-2/`)**: 이력·추세 피처, 5분 창, 점수 EWMA/CUSUM, LSTM-AE, E02 전용 모델 — 전부 채택 안 함. 정직한 지도학습 상한선(c19 제외)이 검증 0.705 / 테스트 0.619로 비지도(0.647/0.636)와 같다 → **이 윈도우 통계에는 고장 1시간 전 정보가 없다(피처 문제, 모델 문제 아님)**. 운영점(선행 30분·오탐 1/일) 충족 테스트 건 0. **B-5(2026-09-26, `history.md` 11절, `results/B-5/`)**: 설정값 조건부 잔차, 정비 이력 피처(캡 드레싱·c1 변경, 6h 상한), 짧은 레이블 창 — 전부 채택 안 함(정비 피처는 IF 4-fold +0.03·테스트 −0.05로 매번 반대 방향 = 과적합). 데이터셋 안에서 만들 수 있는 정보는 소진 — 고장 10분 이전 분리력 AUROC ~0.6이 천장. **전제(2026-09-28 사용자 지시): 제공된 데이터 외에 다른 데이터는 없다** — "데이터셋 밖 정보원"은 다음 단계가 아니다. **B-7(2026-09-28, `history.md` 13절, `.py/physics.py`, `results/B-7/`)**: 상태별 물리 피처·점수 건별 이동 정규화 채택 안 함. IF + LightGBM 앙상블(`--model ensemble`)만 CV에서 폴드 sd 이상 올랐다(규칙 이전 0.585→0.681, 테스트 동률) — 운영 경로 검증 전 후보(techspec B-9). 구성은 CV로만 고르고, 테스트 안 순위(전이적)는 쓰지 않는다.
- **논문 비교는 논문 프로토콜로(B-6, 2026-09-28, `history.md` 12절, `.py/paper_task.py`, `results/B-6/`)**: 논문 68.62%/오탐 56%는 "다음 60초의 상태(정상/E01~E04) 분류"다. 우리 AUROC(고장 1h 전)와 직접 비교하지 말 것. 같은 프로토콜에서는 **현재 종료 코드 → 클래스(persistence = `known_code_class_hint`)만으로** 테스트 정확도 0.999·정상 재현율 1.000·고장 재현율 0.986, E02~E04 클래스 재현율 논문 이상(E01은 3윈도우라 동률 범위) — 상태가 수 분~수일 지속되기 때문이지 예측력이 아니다. 예측이 필요한 onset(정상→고장 전이)은 onset AUROC 0.61~0.73, 오탐 0.1%에서 테스트 0/22. "논문 수준 이상" 요구에는 이 표로 답하고, 개선 목표는 계속 `auroc_pre_rule`로 잡는다. 에러 코드 이력 피처(51개)는 1h 과제 4-fold +0.003·테스트 −0.09로 채택 안 함(정비 이력과 같은 과적합 패턴).
- **평가 설계(B-4)**: `evaluate()`가 운영점(`operating_point`: 선행 ≥30분 & 오탐 ≤1/일/건 충족 건 수)과 종료 코드 규칙 기준선(`rule_terminal_code`)을 항상 같이 낸다. 규칙 기준선은 **서빙과 같은 방식**(4개 코드 전부 = 윈도우 플래그 `terminal_any`, 에피소드 시작 시 1회, `RULE_COOLDOWN_S` 30분 쿨다운, `train.rule_triggers`)으로 적중(고장 전 1h 안 첫 트리거의 선행)과 오트리거/일을 낸다: 테스트 8/8건·9.2분·0.25회/일, 검증 14/14·9.4분·0.05회/일. 2026-09-24 전에는 파일 자기 클래스의 코드만 셌다(`terminal_code`) — 서빙은 클래스를 모르므로 다른 클래스 코드의 오트리거가 평가에서 빠져 있었다. `--cv k` 건 단위 층화 k-fold(폴드 간 AUROC 0.59~0.70, 한 분할 수치는 ±0.04 흔들림 — 구성 비교는 4-fold로), `--label-window`로 레이블 창 변경. **레이블 창은 1시간 유지**(2026-09-26): 좁히면 AUROC가 오르지만(IF 4-fold 15분 0.78 / 30분 0.68 / 60분 0.63) 고장까지 남은 시간 구간별로는 0~10분만 0.77~0.84, 10분 밖은 0.59~0.67 — 이득이 규칙이 덮는 구간에서만 나온다. 대신 **AUROC를 세 가지로 본다**: 풀링 `auroc`, 건별 평균 `auroc_gun_mean`(건 간 점수 오프셋 제거; 테스트 건별 0.24~0.89), 규칙 이전 `auroc_pre_rule`(고장 10분 이전 전조만 양성 = 모델이 규칙에 더하는 몫, `RULE_LEAD_S`). 규칙 기준선의 오트리거는 **critical 발화**(반복 제외) 기준이고 `all_triggers_false_per_day_mean`이 반복까지 센 값.
- **분할은 파일(=건) 단위**, 클래스별 층화. 같은 건의 행이 train/val에 섞이면 안 됨.
- 정상 = `label==0 & error_active==0`. **기본 학습은 `--exclude-non-welding`**(비용접 비율 > 0 윈도우 제외, 464k → 418k 윈도우). 성능 장치가 아니라 "비용접 중에는 판단하지 않는다"는 운영 규칙이다.
- **비용접 게이트**: 윈도우의 비용접 비율이 `--alarm-max-non-welding`(기본 0.5, `none`으로 해제)을 넘으면 점수가 임계값을 넘어도 알람이 아니다(보류). 평가와 서빙이 같은 규칙을 쓰도록 번들 `alarm_max_non_welding`에 넣는다. 지표에 `held_windows`(보류된 알람 수), `held_share_of_windows`(게이트 대상 윈도우 비율), `auroc_welding_windows`가 같이 나온다. 게이트가 사실상 두 건 전체를 가리는 구성(구 규칙 + 게이트: test_2·test_3의 99.8%)은 채택하지 않았다 — 오탐률은 0이 되지만 모델이 그 건을 보지 않는 것이다.
- **건별 정규화(B-1, 2026-09-23)**: 건마다 센서 오프셋이 최대 1.7σ라 글로벌 z-score + 글로벌 임계값은 건별 정상 알람률을 0~13%로 흩어 놓는다. `--scale per-file`은 서빙이 재현 못 하므로 **워밍업 방식**: 파일/스트림 첫 6시간의 정상·용접 행(600행 이상) 평균을 이후 행의 z-score 입력 19개에서 뺀다(`--gun-norm center`, c7~c9는 0이 됨). 워밍업 구간은 글로벌 스케일로 점수화하고 `warmup` 플래그. 구현은 `train.window_file()`(오프라인)과 `main.Detector.gun_normalise()`(온라인) 한 쌍이고 레시피는 번들 `gun_norm`.
- **건별 임계값** = max(글로벌, 워밍업 윈도우 중 알람이 날 수 있는 창을 건별 통계로 재정규화한 점수의 99% 분위수; 10창 미만이면 없음). 기본 켜짐(`--no-gun-threshold`). 올리는 방향으로만 쓴다 — 360윈도우의 분위수는 거칠다.
- **`--gun-norm scale`(std까지 나눔)은 쓰지 말 것.** 워밍업 동안 대기 상태였던 건(검증 E04_4)은 std가 하한에 걸려 이후 정상 알람률 56.5%. 워밍업이 정상 운전을 대표한다는 보장이 없으면 평균만 빼는 것이 안전하다. 같은 이유로 E04_4는 center에서도 4.9%로 남는다(워밍업 조건을 "정상 용접 N행"으로 바꾸는 것이 후보).
- 임계값 = 학습 정상 점수 99% 분위수(=오탐률 1% 설계). `sustain=3` 연속 초과를 "지속 알람"으로 정의 — readme 3절의 "연속 N회일 때만 RAG 트리거"에 대응.
- 평가는 AUROC/AUPRC(고장 전 1h vs 정상) + 정상 알람률 + 클래스별 + 파일별 "고장으로 이어지는 마지막 알람 구간 시작 시각"과 "24h 이전 오탐 에피소드/일". "최초 알람 시각"은 초반 오탐에 걸려 무의미해서 버렸다.
- 워밍업 윈도우(글로벌 스케일)는 학습 정상 집합에 **일부러 남긴다**. 서빙도 워밍업 구간을 같은 모델·글로벌 스케일로 판정하기 때문 — 빼면 AUROC는 같고 정상 알람률이 3배(검증 1.0→3.2%, 테스트 0.5→1.5%, 2026-09-26).
- 번들(joblib dict)에 `feature_reference`(정상 윈도우 중앙값)를 넣는다 — 서빙에서 피처 기여도 계산용.
- **지표 정의 정정(2026-09-29, `history.md` 14절)**: AUROC·규칙 이전 AUROC·AUPRC·클래스별 AUROC는 **고장 전 창 vs 정상 창**(에러 상태 창은 음성에서 뺌 — 건별 AUROC와 같은 정의). 운영점의 "고장으로 이어지는 마지막 지속 알람"은 **고장 24h 이내에 시작한 것만**(상시 알람이 선행 168h로 통과했다). 규칙 기준선의 적중 창은 `--label-window`와 무관하게 1h(`RULE_EVAL_WINDOW_S`). 건별 임계값 보정은 **알람이 날 수 있는 워밍업 창만**(에러 상태 아님, 비용접 비율 ≤ 게이트, 10창 이상 — `train.calibration_windows`/`gun_threshold`, 서빙 동일). 앙상블 양성에도 음성과 같은 비용접 필터.
- 베이스라인(IsolationForest, 2026-09-23 c19 제거 후 재학습, 46피처, 글로벌 임계값 0.5251) 검증 결과: AUROC 0.647, recall@1h 3.0%, 정상 알람률 1.0%, 건별 0.1~4.0%; 4-fold AUROC 0.631 ± 0.038. (c19 포함 B-1 시점 0.684 / 3.9% / 1.1%; A-1 후 0.642; A-1 전 0.630.) **기준선일 뿐이고 종료 상태(E029 등)는 규칙이 잡는다.** **2026-09-29 재전처리·재학습 + 지표 정의 정정 후: 검증 0.662(규칙 이전 0.623), 4-fold 0.639 ± 0.043(규칙 이전 0.594 ± 0.045), 글로벌 임계값 0.5232, 건별 정상 알람률 0.1~6.1%(E04_4) — `history.md` 14절.**
- 번들에는 `scaler.json`과 `preprocess_config.json`을 같이 넣는다. 서빙이 전처리 파라미터(gap 한도, c16 임계)를 번들에서 읽어야 학습·서빙이 어긋나지 않는다.
- 테스트 8파일 평가는 검증과 **같은 함수, 같은 임계값**(학습 정상 99% 분위수)으로 한다. 학습 직후 `metrics["test"]`에 들어가고, `--evaluate`는 저장된 번들만 읽어 `models/baseline_<model>_test_metrics.json`과 `models/scores/test_N_<model>.csv`를 쓴다(번들은 건드리지 않음). 테스트 클래스별 수치는 "추론된 클래스 기준"이다.
- 베이스라인 테스트 결과(8파일, 80,533 윈도우, c19 제거 후): AUROC 0.636, recall@1h 2.9%, 정상 알람률 0.5%, **건별 0.02~1.0%(sd 0.3%)**. 클래스별 AUROC E01 0.346 / E02 0.894 / E03 0.683 / E04 0.644. 고장으로 이어지는 지속 알람 0/8건, 운영점 충족 0/8. ## 5. 서빙 계약 (`main.py`)

- 입력은 CSV 컬럼 그대로(`time, c1~c19, error`). 서버가 건별 30분 링버퍼를 유지하고 전처리를 온라인으로 재현한다. 클라이언트는 아무 전처리도 하지 않는다.
- 출력 `AnomalyResult` 필드는 온톨로지 단계와의 **계약**이다: `is_anomaly, anomaly_score, threshold, score_z, severity(normal|warning|critical), sustained_alarm, consecutive_alarms, contributing_features[], context{latest_error_code, known_code_class_hint, ...}, model{}`. 필드를 빼거나 의미를 바꾸면 하류가 깨진다 — 추가는 자유.
- `severity: critical` = 임계 초과(게이트 통과)가 **`sustain × window` 초(180초) 이상 연속**(`alarm_duration_s`, 알람 시작 시각 기준). 이게 RAG 트리거 기준. 요청 횟수로 세면 호출 주기에 따라 3초~75분으로 바뀌었다(2026-09-24 수정). 청크 안의 완결 윈도우(최신 행부터 window 간격)를 모두 스코어링해 알람 상태를 윈도우마다 갱신하고, 청크 중간에 critical이 있었으면 `critical_in_request`/`sustained_in_request` — 하류 트리거는 `critical_in_request`를 본다.
- `contributing_features`는 모델 무관 perturbation(피처 하나를 정상 기준값으로 치환했을 때의 점수 감소). 모델을 바꿔도 이 방식은 유지 가능.
- `known_code_class_hint`는 모델과 무관하게 2절의 종료 코드 매핑으로 채운다. 모델이 약할 때 온톨로지가 쓸 수 있는 안전장치. **B-3(2026-09-23)**: 그 규칙이 뜨면 `severity=critical` 강제, `rule_triggered=true`, `severity_source`(model/rule/model+rule/none). 모델이 종료 상태를 임계값 아래로 보는 문제(에러 상태 알람률 ~1%)를 규칙으로 메운다. 규칙이 보장하는 선행은 마지막 ~10분(코드가 그때 뜬다). **2026-09-24 수정: 상태가 아니라 에피소드 시작에서 1회 발화 + 건별 쿨다운 30분**(번들 `rule`). 코드가 떠 있는 동안 계속 critical이면 E029가 다른 클래스 건에서 수 시간(테스트 test_0 16.2h·test_4 9.4h, EDA 최장 24h) critical을 냈다. `rule_code`/`rule_class_hint`는 발화시킨 코드(청크 끝에서는 코드가 이미 0인 경우가 대부분이라 `known_code_class_hint`로는 클래스가 사라진다). `rule_triggered`의 의미를 바꾼 것은 이 계약 변경의 예외 — 상태 의미는 `rule_code_active`로 남겼다. **반복 강등(2026-09-26)**: 같은 코드가 같은 건에서 `rule.repeat_s`(24h) 안에 이미 발화했으면 `rule_triggered=true` + **`rule_repeat=true`, severity `warning`, `critical_in_request=false`, 핸드오프 없음**. 80건에서 반복 발화는 18회 중 17회가 오트리거(적중 손실 1/72). 테스트 critical 오트리거 0.25→0.18회/일/건. 발화 시점 특징(코드, 주변 에러 코드, 점수, 센서)으로 진짜/오트리거를 가르는 분류기는 건 단위 CV AUROC 0.62로 버렸다. 구현은 `train.rule_repeats()` / `main.Detector.rule_check()` 한 쌍(쿨다운과 같은 구조), 윈도우의 `terminal_idx`가 코드를 나른다.
- 완결된 분 경계 윈도우(표본 30개 이상)가 아직 없으면 202 + `WarmingUp` 스키마.
- **이상 추적(2026-09-28)**: `GET /guns/{id}/trace`(스키마 `Trace`, 새 엔드포인트라 `AnomalyResult` 계약은 불변) + `/trace/view`(`static/trace.html`). 건 상태에 판정한 창 360개(6h)의 피처 벡터·판정을 링버퍼로 둔다. 차트 축 결정: 센서는 원 단위가 아니라 **모델 입력 − 정상 기준값(σ), ±4 고정**이다. 센서가 마스킹돼 단위가 섞여 있고, 모델이 본 값과 같아야 기여도와 맞기 때문이다. 1초 원시값이 아닌 60초 창 값을 쓰는 이유는 c2·c3·c5가 가압/해제 두 상태를 오가 빗살이 되기 때문이다. 점수 축도 고정한다(정상 점수 흔들림이 자동 스케일에서 이벤트처럼 보인다). 이중 축 없이 패널을 쌓는다. 기본 차트 피처에서 `error_share_10min`을 뺀다(코드 띠와 중복). 제목은 "이상 기여 센서"로 한다 — 물리적 원인이 아니다.
- 서빙의 건별 정규화(B-1): 건마다 첫 6시간(번들 `gun_norm.warmup_s`)의 행을 모아 두었다가 워밍업이 끝나면 건 평균과 건별 임계값을 고정한다. 그 전 응답은 `gun_norm: warming_up`(글로벌 기준), 이후는 `gun`; 정상·용접 행이 600개 미만이면 `global`. 응답의 `threshold`는 **그 윈도우를 판정한 값**(건별 있으면 건별), `model.threshold`는 글로벌. 요청당 최대 `MAX_CHUNK` = 1,200행(버퍼 `BUFFER_S` 1,860초 = 청크 + 롤링 이력 10분 + 다음 요청으로 넘어가는 미완결 분 1개)이고 넘으면 422 — 예전에는 3,600행까지 받아 버퍼를 넘는 행을 조용히 버렸다(50분 청크 → 워밍업 21,600행 중 13,688행만 수집). `DELETE /guns/{id}`가 워밍업을 재시작한다. test_0 실측: 25분 청크로 6.5시간 보내면 점수 동일, 건별 임계값 차이 0.0002.
- **서빙 견고화(2026-09-29, `history.md` 14절)**: `/predict`는 동기 함수(스레드풀, 건별 `threading.Lock`) — 요청당 ~40 ms 판다스 작업이 이벤트 루프를 막지 않게. 입력은 NaN/inf 거부(422, 오류 응답도 JSON 안전), 초 미만은 초로 내림. 한 요청의 시각 폭 > 30분이면 422, 건의 최신 시각보다 30분 넘게 과거면 409(잘못된 시각 한 줄이 30분간 건을 먹통으로 만들던 결함). 202 응답 중 뜬 종료 코드 발화는 `pending_rule`로 다음 200 응답에 싣는다. 규칙은 버퍼의 모든 세그먼트 코드를 본다(긴 gap 앞 코드 누락 수정). 발화 조건은 **종료 코드가 하나도 없다가 생길 때**(E016→E029 전환은 같은 에피소드 — 오프라인 `terminal_any`와 일치). 비용접 carry는 **버퍼에서 밀려난 마지막 용접 행**(이전에는 버퍼 안 이후 값으로 덮였다). `context.welds_*`는 건별 centering **전** 프레임으로 원 단위 복원(이전에는 워밍업 후 +180/창 같은 값 — 증상 P4가 발동 불가). `critical_source`(요청 단위 위험 근거, 추가 필드)를 핸드오프 `trigger.source`가 쓴다. trace는 겹치지 않는 창만 쌓는다(요청 주기와 무관하게 6h).
- **상태 영속화(C-1·D-1, 2026-09-29, `history.md` 16절)**: `RSW_STATE_DIR`(기본 `state/`, gitignore; 빈 값 = 메모리만)에 건 상태 `guns/<gun_id>.json`(요청마다 원자적 쓰기)과 핸드오프 `outbox/<event_id>.json`. 결정: **버퍼·trace·진행 중 워밍업은 저장하지 않는다**(워밍업 행 최대 6h×1Hz를 요청마다 쓰는 비용 대비 이득 작음 — 워밍업 중 재시작은 워밍업 재시작). 번들 `created`가 다르면 건은 워밍업으로(건별 임계값은 옛 모델 점수 분위수), 규칙 이력은 유지. 재시작 직후 첫 창은 직전 창과 `gap_fill_limit + window` 안이면 같은 알람 런으로 본다(`GunState.restored`). push는 `outbox_worker`(1초 폴링) — 백오프 10s·30s·2m·10m, 5회 뒤 failed, 4xx(408·429 제외)는 "rejected"로 즉시 failed·재큐 안 함. `event_id` = sha1(건|창 끝|critical_source|규칙 시각)[:32] — 결정적이라 재생성돼도 같은 id, 수신 쪽이 `event_id`로 중복 제거(계약). `HandoffRecord`에 `attempts`·`last_attempt_at`·`next_attempt_at` 추가.
- **운영 모델 = IsolationForest + LightGBM 앙상블(2026-09-29, `history.md` 18절)**: `models/baseline_ensemble.joblib`(`main.MODEL_PATH` 기본). 4-fold 규칙 이전 0.594 → 0.644, 테스트 0.619 → 0.671, 정상 알람률 CV 0.8%·테스트 0.6%, 건별 최대 7.8 → 5.5%(E02_13; 5% 게이트는 근소 초과, IF보다 개선이라 채택). **선택 규칙(사용자 지시: robustness 중시)**: 조합은 CV로만 고르되 4-fold 평균 − SD와 최저 폴드로 순위, 정상 알람률 ≤ 1.5%·건별 ≤ 5%, 테스트는 현재 모델보다 떨어지면 탈락(선택에 쓰지 않음). B-9에서 CV 1위인 IF+LGBM+LGBM6h+ET(0.736 ± 0.027)는 운영 경로 테스트 0.607로 탈락 — 지도학습 구성이 늘수록 학습 건에 맞춰진다; 비지도(IF)를 빼면 새 건에서 무너진다(LR 0.42, LGBM 0.54). 서빙의 창 통계는 `train.window_features`를 그대로 호출한다(Series 통계는 1e-7 달라 LightGBM 분기가 뒤집혀 점수 최대 0.026 차이 — IF에서는 안 보이던 것).
- **워밍업 알람 보류(B-8, 2026-09-29, `history.md` 17절)**: 번들 `warmup_alarms: false`(기본; 구 번들은 true로 읽음) — 워밍업 창은 점수만 내고 모델 알람은 없다(`train.alarm_mask(warmup=)` / `Detector.in_warmup`, 응답 `alarm_held` + `hold_reason` "gun warm-up…"; `alarm_held` 설명을 "비용접 또는 워밍업"으로 넓힘 — 핸드오프는 critical에만 나가므로 하류 영향 없음). 워밍업이 `global`로 끝나는 건(정상·용접 행 < 600)은 온라인은 보류, 오프라인은 워밍업이 없어 첫 몇 시간 판정이 다르다(학습 64건 중 2건). 원인: 글로벌 스케일에서 건 상수 c7~c9가 최대 14σ. 기각: 24h 재센터링(테스트 규칙 이전 −0.02, 드리프트 신호 제거), c7~c9 제외(단독 효과 없음).
- **운영 모니터링(C-4, 2026-09-29)**: 건 상태 파일에 일 단위 카운터(`STAT_KEYS`, 31일). 창은 trace와 같은 조건(새로 채점된 비중첩 창)에서 한 번씩 센다. `GET /guns/{id}/stats`, `GET /stats`. `drift_warning`(응답·`/guns` 추가 필드): 워밍업 뒤 정상 알람률 3일 연속 > 3%(하루 정상 창 ≥ 360) 또는 하루 critical 규칙 ≥ 2. "정상" = 에러 코드 없는 창(서빙은 레이블을 모른다) — 오프라인 `alarm_rate_normal`(고장 전 1h 제외)과 테스트 8건 최대 0.05%p, 알람 수 전부 일치(앙상블).
- **서빙은 버퍼의 모든 연속 구간을 채점한다(2026-09-29, `history.md` 19절)**: `features()`가 버퍼 전체 + `segment` 열을 주고 `windows()`가 (구간, 분) 단위로 완결 창을 고른다. 전에는 마지막 구간만 — 한 요청이 긴 공백을 걸치면 공백 앞 완결 분이 채점·워밍업 수집에서 빠졌다(test_5 33창). 알람 런 초기화는 창 단위(직전 창과 `gap_fill_limit`+1초 넘게 떨어지면, 재시작 직후는 + window). "새 창 없음" 재채점은 현재 구간의 창만(공백 앞 창을 최신으로 돌려주지 않는다 → 202).
- **핸드오프 증상 임계값(D-5, 2026-09-29)**: `rag_mapping.MIN_SHARE` 0.03·`MIN_DEV` 0.5 — 80건 마지막 12h 재생의 이벤트 132개에서 0.05·1.0은 62%가 증상 0개(중앙값 0). 규칙(중앙값 1~3, 증상 0개 ≤ 25%, 현재 값에 가장 가까운 점)으로 골랐다; 정답 없음 → 정확도 근거는 아니다(`results/D-5/symptom_sweep.json`). 예시 JSON은 `docs/make_examples.py`로 다시 뽑는다.
- 서빙은 게이트도 번들(`alarm_max_non_welding`)에서 읽는다. 보류 윈도우는 `is_anomaly`는 그대로 두고 `alarm_held=true`·`hold_reason`을 붙이며 `severity=normal`, `consecutive_alarms`를 0으로 리셋한다(비용접 중 점수는 신뢰하지 않으므로 지속 알람 카운트를 이어가지 않는다). `AnomalyResult`에는 필드 추가만 했다.
- 서빙은 번들의 `preprocess_config`에서 gap 한도·c16 임계를 읽고(없으면 기본값 + 경고; `outlier_hi`는 None 허용), `per-file` 스케일이나 `--resample`로 만든 번들은 기동 시 거부한다 — 온라인으로 재현할 수 없는 변환이라 조용히 틀린 점수를 내느니 실패하는 쪽을 택했다.
- 비용접 행은 **버퍼에서 밀려난 마지막 용접 행**(`GunState.carry`)을 버퍼 시작에 채우고 ffill한다. 버퍼 안에서만 ffill하면 30분보다 긴 캡 드레싱/대기 구간에서 버퍼 전체가 NaN → HTTP 500(2026-09-24), 버퍼 안의 최신 용접값을 쓰면 앞쪽 행이 미래 값으로 채워진다(2026-09-29). 한 번도 용접 행을 못 본 스트림은 202.
- 온라인 전처리가 오프라인과 같은 점수를 내는지는 `tests/test_pipeline.py`(합성)와 실데이터(test_3 마지막 30분, 점수 일치)로 확인했다. 요청당 ~40 ms.

- **ML → RAG 핸드오프(2026-09-25, `.py/rag_mapping.py`, readme 5.10)**: 역할 분담 결정 — ML은 ① 이상 감지와 ② 증상 번역(기여 피처 → 방향 → 증상 P1~P9 → 고장 유형 → **상황 ID S01~S10**)까지만 하고, 원인·점검·매뉴얼(③)은 온톨로지(지현), 리포트(④)는 RAG가 맡는다. 핸드오프에 부품·점검·매뉴얼을 넣지 않는다(테스트로 고정). 상황 ID는 팀 문서 「RSW 용접건 MVP 오류 상황 정의서」의 키. 트리거는 critical 에피소드 첫 요청 + 규칙 발화마다(반복 발화 제외; 모델 critical과 겹친 반복 발화는 핸드오프의 규칙 근거 — `trigger.rule_code`, `fault_class.basis=rule_trigger` — 로 쓰지 않는다. `GunState.was_critical`, `replay.py`와 같은 규칙). `/predict` 응답에 `handoff` 필드 **추가**(평소 null), outbox → `GET /handoffs`(pull), `RSW_RAG_URL`이면 백그라운드 POST(push; 2026-09-29부터 영속화·재시도 — §5 상태 영속화), `POST /handoffs/preview`. 스키마 `RagHandoff` v1.0. 신뢰도 low/medium뿐. 실데이터 재생(테스트 8건 마지막 12h): 9 이벤트 중 8건이 고장 직전 올바른 상황을 맨 앞에, 센서 증상이 매뉴얼 패턴과 맞은 건 1건 — 믿을 키는 `situation_ids[0]`(고장 유형 유래).

## 6. 코드 규약

- 스크립트는 `.py/`, API는 루트 `main.py`(`uvicorn main:app`). `main.py`는 `sys.path`에 `.py/`를 넣어 `train`, `preprocess`, `rag_mapping`을 import한다 — 번들 언피클에 `train.PCADetector`/`train.EnsembleDetector`가 필요하다. `train.py`를 스크립트로 돌려도 이 클래스들은 `train.X`로 피클되게 고정했다(`__main__.X`로 저장된 번들은 서빙이 못 읽는다, 2026-09-29).
- 모든 경로는 `PROJECT_ROOT = __file__ 기준` 으로 잡는다. cwd 의존 금지 (IDE에서 `.py/`가 cwd가 되어 KeyError가 났던 적 있음). 파일을 못 찾으면 즉시 `SystemExit`로 경로를 찍는다.
- 수치는 float32, 저장은 parquet(pyarrow 없으면 csv 폴백).
- 데이터 폴더(`train/`, `preprocessed/`) 안에 산출물을 쓰지 않는다. 결과는 `eda_out/`, `models/`, `results/`로.
- 그래프 색은 클래스 고정: E01 `#2a78d6`, E02 `#eb6834`, E03 `#1baf7a`, E04 `#eda100`. 이중 축 금지.
- 환경: Windows, CPU-only torch, darts 0.41, pandas 2.3, sklearn 1.7, fastapi 0.121, pydantic 2.13. `accelerator="gpu"` 하드코딩 금지.
- 무거운 작업(72파일 EDA 40분, 벤치마크 학습 수십 시간)은 백그라운드로 여러 개 띄우지 않는다 — 메모리 부족으로 강제 종료된 적 있음. `--max-files`/`--pattern`으로 축소 테스트 먼저. 참고: 전처리 72파일 ~7분, `train.py` 전체 ~1분.
- `pytest`(`tests/test_pipeline.py` 10개 + `tests/test_rag_mapping.py` 13개)는 합성 CSV로 전처리→테스트 분할→학습(IF·앙상블)→평가→API·서빙 회귀까지 임시 폴더에서 돌린다(~40초). API 스트림은 `.py/replay.py`(원본 CSV → `/predict`)로 재현하고, 테스트도 `replay_file()`을 TestClient로 돌린다. 파이프라인 코드를 고치면 먼저 이걸 돌린다. 실데이터 폴더는 건드리지 않는다.
- **문서 역할 분리**(2026-09-24, 사용자 지시): `readme.md`·`test.md`는 **항상 최신 상태·결과만** 담는다(이전 수치, "〔수정〕 처음엔 …" 같은 경위, 날짜별 진행 표를 두지 않는다). 수정 기록·이유·절제 실험·이전 모델 수치는 `history.md`에 시간순으로 쌓는다. 실험이나 변경을 하면 history.md에 절을 추가하고 readme·test.md는 결과를 덮어쓴다. `techspec.md`(2026-09-26 추가)는 **앞으로 개발할 것**만(ML 파트 + RAG 핸드오프 범위) — 항목을 끝내면 거기서 지우고 결과를 readme·test.md·history.md에 반영한다.
- 린트/포맷 설정은 `pyproject.toml`(줄 120자, `Benchmark.py`·`pic code/`는 원본이라 제외). 의존성은 `requirements.txt`. `__pycache__`는 git에서 뺐다. 모델 번들(`*.joblib` 등)·`models/scores/`·실험 캐시·압축 파일도 git에 올리지 않는다(재학습으로 재생성하거나 readme §0 드라이브에서 받음; 지표 JSON은 유지).
