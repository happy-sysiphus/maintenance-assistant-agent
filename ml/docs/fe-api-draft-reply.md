## 1. 최신 모델 파일

- 맞는 파일은 10/06 재학습본이다. 번들 `created`가 `2026-10-06T10:17:47`이다.
  - 모델 단독 critical은 10분 지속이 필요하고, 재가동 뒤 30분 동안 보류하며, 쿨다운은 코드별이다.
  - "9/29 파일은 모델 단독 긴급 알림이 더 많다"는 관찰이 맞다. 10/06에 C-5로 줄인 부분이다(`history.md` 27·30절).
- ML 담당이 드라이브의 `baseline_ensemble.joblib`을 이 파일로 바꾼다.
- 받은 파일 확인: ML 서버 `GET /health`의 `model.created`가 `2026-10-06T10:17:47`이면 맞다.
- 라이브러리 버전: 이 번들은 scikit-learn 1.7.0 · lightgbm 4.6.0에서 경고 없이 불러진다.
  - `requirements.txt`는 `>=`라 더 새 버전이 깔리면 경고가 나거나 불러오지 못할 수 있다. 같은 버전을 권장한다.

## 2. 핸드오프 push를 api가 받아도 되나 → 네

- v1.2부터 핸드오프는 RAG로 보내지 않는다(`sensor_features_for_rag.md`). 그래서 받는 곳이 api여도 계약상 문제가 없다.
  - RAG에는 매분 센서 문서(`RSW_RAG_SENSOR_URL`)만 지금처럼 간다.
- 설정: `RSW_RAG_URL=http://127.0.0.1:9000/api/ml/handoffs`.
  - 이름에 RAG가 들어 있지만 "핸드오프 push 주소"라는 뜻이다.
  - Windows에서는 `localhost`가 IPv6(::1)부터 시도해 매번 늦어질 수 있어 `127.0.0.1`을 권장한다.
- 데모는 push를 권장한다(08의 의견과 같다). ML은 알림이 생기고 약 1초 안에 보낸다. 그래서 빠른 재생에서도 api가 알림 직전 30분 trace를 놓칠 일이 거의 없다.
- ML이 응답을 처리하는 방식은 아래와 같고, 지금 api 코드와 맞는다.

| 응답 | ML 처리 |
|---|---|
| 2xx | 전달 완료. 본문이 JSON이면 `rag_response`로 보관만 하고 쓰지 않는다. 7칸 리포트는 필요 없다 |
| 4xx (408·429 제외) | 거절로 본다. 다시 보내지 않는다 |
| 5xx, 연결 실패, 10초 초과 | 10·30·120·600초 뒤 다시 보낸다. 5번 실패하면(약 13분) `failed`. ML을 다시 켜면 다시 시도한다 |

- 이미 받은 알림도 200으로 답하면 된다. 지금 api의 `{"result": "duplicate"}`가 그렇다. 헤더 `Idempotency-Key`는 `event_id`다.
- **api 쪽 주의:** push를 켠 채 `GET /api/cases`의 5초 당기기도 돌면, 같은 알림이 거의 동시에 두 번 들어와 케이스가 2개 생길 수 있다.
  - 원인: `ingest`가 "이미 받았나" 확인(`store.seen`)과 기록(`store.mark_seen`) 사이를 잠그지 않는다. 그런데 두 경로는 서로 다른 스레드에서 돈다.
  - 권장: `ingest` 전체를 lock 하나로 감싼다.
  - 당기기는 남겨 두면 좋다. push가 끝내 실패한 알림(api가 13분 넘게 꺼져 있던 경우 등)을 메워 준다.

## 3. test_0의 E029 반복

- api가 같은 설비 · 같은 코드의 열린 케이스로 묶는 것이 맞다.
- ML 규칙: 같은 코드가 이 설비에서 직전 발화 뒤 24시간(86,400초) 안에 다시 발화하면 반복(`rule_repeat`)이다. 반복은 warning이고 핸드오프가 없다. 24시간이 지나 다시 뜨면 새 critical이라 핸드오프가 간다.
- test_0의 E029는 09-06·07·08·10일 19:30:09~10(데이터 시각)에 뜬다.
  - 하루 간격일 때 간격이 정확히 24시간(86,400~86,401초)이라 반복 기준(86,400초 미만)에 걸리지 않는다. 그래서 날마다 새 알림으로 온다.
- test_0은 E01 파일이라 이 E029들은 오트리거다.
  - 설비 프로파일(`PUT /guns/{id}/profile`, 그 설비에 기대하는 고장 유형)을 주면, 그 밖의 코드는 핸드오프 없는 warning(`rule_out_of_profile`)이 된다.
  - 단 데모에서 파일 이름의 고장 유형을 프로파일로 주는 것은 정답을 미리 아는 셈이다. 이렇게 줄인 알림 수를 성능처럼 보여 주면 안 된다.

## 4. 조치 뒤 "재발 없음" — 10-08 답변 갱신 (05 요청 6)

10-08 답변은 "`/handoffs`에 새 이벤트가 없고 trace `events`에 `rule`·`rule_repeat`가 없으면 재발 없음"이었다. 코드로 다시 확인하니 이 방법으로 놓치는 경우가 있어 아래처럼 고친다.

**판정 근거:** trace `points[].error_codes`를 본다. 그 1분에 뜬 0이 아닌 코드 목록이다. 기준 시각 뒤 모든 분에 케이스의 코드(`trigger.rule_code`)가 없으면 "재발 없음"이다. 다른 방법으로는 다음 경우를 놓친다.
- `/handoffs`만 보면: 같은 코드가 24시간 안에 다시 뜨면 반복이라 warning만 되고 핸드오프가 없다.
- `events`(`rule`·`rule_repeat`)를 봐도: 같은 코드가 마지막 발화 뒤 30분(쿨다운) 안에 다시 뜨면 이벤트 자체가 남지 않는다.
- 코드가 꺼지지 않고 계속 떠 있으면 새 이벤트가 생기지 않는다. `error_codes`로 보면 이 경우도 잡힌다.
- 모델 단독 케이스(`rule_code`가 null)는 볼 코드가 없다. 같은 설비에 새 핸드오프(`detected_at`이 기준 시각 뒤)가 있는지로 본다.

**기준 시각:** 데이터 시각으로 비교한다.
- 조치를 저장할 때 `/api/guns`(ML `GET /guns`)에 있는 그 설비의 `last_time`(UTC, `Z` 없음)을 같이 저장하고, 그 뒤의 분만 본다.
- 조치 저장 시각은 작업 시각이라 데이터 시각과 비교할 수 없다. 05의 "작업 시각과 데이터 시각을 섞지 않는다"와 같은 원칙이다.

**얼마나 볼지:** 공개 데이터에 조치 후 구간이 없어서 데이터로는 정할 수 없다. ML 기준으로 말할 수 있는 범위:
- 최소 30분: ML은 30분 안에 다시 뜬 같은 코드를 같은 사건으로 묶는다.
- 최대 약 6시간: trace는 최근 360분(판정한 창 360개)만 들고 있고, ML을 다시 켜면 비워진다. 더 길게 보려면 api가 중간중간 저장해 둬야 한다.
- 데모는 30분을 권장한다. 공개 데이터는 고장 뒤 10분에서 끝나므로 "시뮬레이션" 표시가 맞다.

**`DELETE /guns/{id}`:** 10-08 답변대로 부품 교체·캡 교체·축 보정처럼 센서 기준값이 바뀌는 조치 뒤에만 부른다. 부르면 아래 일이 생긴다. 10-08 답변의 "그동안 모델 알람은 글로벌 기준"은 틀렸다.
- 그 설비의 버퍼·워밍업·경보 상태·규칙 이력(쿨다운, 24시간 반복)·통계·trace가 지워진다. 프로파일은 남는다.
- 데이터 시각으로 6시간 워밍업을 다시 한다. 그동안 모델 경보는 나오지 않는다(번들 `warmup_alarms: false`). 종료 코드 규칙은 바로 동작한다.
- 규칙 이력이 지워졌으므로, 그 뒤 같은 코드가 다시 뜨면 반복이 아니라 새 critical 알림(핸드오프)으로 온다.
- **코드가 아직 떠 있을 때 부르면 안 된다.** 그 코드가 곧바로 새 critical 알림으로 다시 잡혀 재발처럼 보인다. 코드가 꺼진 뒤, 즉 trace 최근 분의 `error_codes`에 없을 때 부른다.

## 5. 10-26 ML 변경 중 FE에 영향 있는 것

**c4·c18 한국어 이름**
- 영향받는 칸: 핸드오프, trace, `contributing_features`의 `sensor_name_ko`와 `text_ko`.
- 바뀐 점:
  - c4 "힘 형성 시간" → "힘 도달 신호"
  - c18 "힘 형성 설정값" → "건 닫기·힘 형성 명령"
  - 둘 다 0/1 비트라 평균 소견은 "켜진 비율 평소보다 높음/낮음"으로 쓴다(`history.md` 35절).
- FE에서: `ui/docs/03`과 fixture의 "힘 형성 시간"을 바꿔 주세요.

**`error_timeline`**
- 바뀐 점: 규칙 발화 시각까지 모은다. 전에는 마지막 완결 창 끝에서 끊겨서, 다음(미완결) 분에 뜬 발화 코드가 빠질 수 있었다(C-7).
- FE에서: 코드 지속 시간이 정확해진다. 고칠 것은 없다.

**push 본문**
- 바뀐 점: NaN·inf는 null로 보낸다. 전에는 그런 알림이 매 시도 전송에 실패했다(C-7).
- FE에서: 숫자 칸에 null이 올 수 있다.

**예시 JSON (`docs/*.example.json`)**
- 바뀐 점: 실데이터로 다시 만들었다. `rag_handoff.example.json`은 test_3의 E029 사건이다.
  - 타임라인: E016(09:23:36~09:25:33)과 발화 코드 E029(09:26:09)
  - `sensor_trend`: 4피처 × 30분
- FE에서: mock을 이 파일로 바꾸면 실제 모양과 같아진다.
