# 현장 기록 점검 순서(R2): 다른 파트 요청

2026-11-07 · ML(D-8)
- 설계: `ml/docs/superpowers/specs/2026-11-07-feedback-card-order-design.md`
- 시연과 루프 전체: `ml/docs/hitl-loop.md`

## 1. 무엇이 바뀌나

- **언제:** api가 `FIELD_MEMORY=1`일 때만 새 케이스 카드의 **점검 순서**를 바꾼다. 끄면 지금과 같다. 단, 켜고 만든 케이스(`field_order`가 있는 행)는 끈 뒤에도 순서와 고정을 지킨다(스펙 4.5). 시연은 새 `API_DB`로 한다.
- **조건:**
  - 같은 코드의 해결 종료 케이스에서 '이상'으로 기록된 점검을 센다. 카드 밖 원인(`MANUAL`)으로 해결한 케이스는 세지 않는다.
  - 가장 많은 점검 하나만 본다(같으면 매핑에서 앞선 것). 그 수가 매핑에서 그 앞에 있는 모든 점검보다 3건 이상 많고, 설비 2대 이상에서 나왔어야 한다.
  - 그러면 다음 새 케이스는 그 점검과 그 점검이 든 원인부터 보인다. 글 · 근거 · 기준 · 조치는 RAG가 만든 그대로다.
- **조치 보호:** 앞세울 점검이 든 원인 앞의 원인에, 앞세울 원인이 갖지 않은 조치가 있으면 순서를 바꾸지 않는다. 같은 조치(글 · 근거가 같은 항목)를 앞세울 원인도 가지면 옮긴다. 어느 원인을 골라도 그 조치가 보이기 때문이다.
- **카드 고정:** 순서는 케이스가 생길 때 한 번 정한다. R2로 순서를 정한(`field_order`가 있는) 케이스는 판단 · 조치 · 결과가 기록되면 카드를 다시 만들지 않는다.
- **저장:** 결정은 케이스 최상위 `field_order`에 저장되고, 케이스 상세 응답과 케이스 쓰기 응답에 실린다. 목록(`/api/cases`, `/api/history`)에는 없다.
- **합의:** 다른 파트와 합의한 변경이 아니다. UI 주석의 "카드 순서는 바꾸지 않는다"를 뒤집는다. 머지 전에 FE · RAG 담당이 이 문서를 본다.

`field_order` 예:

```json
{"lead": "E029-K2", "counts": {"E029-K1": 0, "E029-K2": 3}, "guns": 2,
 "note_ko": "현장 기록(사람 판정, 매뉴얼 근거 아님): 이 케이스가 생길 때 해결 종료 케이스의 이상 기록이 E029-K2 3건 · E029-K1 0건(설비 2대)이라 E029-K2부터 보도록 순서를 바꿈. 내용은 매뉴얼 그대로."}
```

## 2. FE 요청 (`ml/docs/hitl-loop.md` ④의 11-13)

### 11. 순서를 바꾼 이유 보이기

- **무엇:**
  - 카드의 첫 점검이 `field_order.lead`이면 `field_order.note_ko`를 점검 화면과 Overview에 보인다. 첫 점검은 첫 원인의 첫 점검이고, 원인 목록이 비면 `candidates[0].checks[0]`이다.
  - 그 점검 항목에 "현장 기록으로 먼저" 같은 표시를 붙인다. 작업자는 점검 id(E029-K2)를 보지 않는다.
- **모양:** `FieldMemoryNote`처럼 회색 바탕에 쪽 칩 없이 그린다. 사람 판정이라 매뉴얼 근거와 다르게 보여야 한다.
- **왜:** 지금은 순서만 바뀌고 이유가 화면에 없다. 이유 없이 바뀐 순서는 매뉴얼 순서처럼 읽힌다. 이 요청이 들어가기 전까지 R2는 시연용이다.
- **어디:**
  - `ui/src/pages/case/CheckPage.tsx`(점검 목록)
  - `ui/src/pages/case/OverviewPage.tsx`(원인 목록 위)
  - `ui/src/pages/case/parts.tsx:289-292`(`FieldMemoryNote`)
- **참고:** `field_order`는 쓰기 응답에도 실려 저장 뒤에 사라지지 않는다. `field_memory`는 GET에만 붙는다.
  - `field_order`에는 점검 id만 있다. 점검 이름은 카드(`guidance`)에서 같은 id의 점검을 찾아 읽는다.
  - `field_memory.note_ko`에 같은 R2 문장이 이미 들어 있다. 둘 다 그리면 두 번 나온다.

### 12. 타입 · 주석 · 안내

- `CaseDetail`(`ui/src/types/case.ts`)에 다음 필드를 더한다:

  ```ts
  field_order?: { lead: string; counts: Record<string, number>; guns: number; note_ko: string }
  ```

- `FieldMemory.applied` 주석에 "R2 = 현장 기록으로 카드 점검 순서를 바꿈"을 더한다.
- 틀리게 된 주석 세 곳을 고친다:
  - `ui/src/pages/case/parts.tsx:286` "원인 카드 순서는 바꾸지 않는다"
  - `ui/src/pages/case/OverviewPage.tsx:79` "카드 순서는 바꾸지 않는다"
  - `ui/src/lib/caseFlow.ts:2` "원인 후보는 ML이 준 순서(rank)대로"
- 안내 문구를 고친다:
  - `field_order`가 있고 판단 · 조치 · 결과 기록이 있는 케이스는 api가 카드를 다시 만들지 않는다.
  - 그래서 그 케이스에서는 `ui/src/pages/case/OverviewPage.tsx:84`의 "잠시 뒤 새로고침하면 다시 만들어요"가 틀린다. 다른 말로 바꾼다.

### 13. (제안) 아래 항목까지 기록하기

- **무엇:** 원인의 점검 항목을 모두 기록해야 '다음'으로 넘어가게 한다. 아니면 기록하지 않은 항목이 있을 때 알린다.
- **왜:**
  - '다음' 버튼은 한 항목만 기록해도 눌린다(`ui/src/pages/case/CheckPage.tsx:240`).
  - 그래서 위 항목만 기록이 쌓여, 위에 있는 점검이 유리하다.
  - 일지의 '못 한 점검'에는 해결한 원인의 점검만 나온다(`ui/src/pages/case/LogPage.tsx:37-40`). 스펙 10절에 적었다.
- 화면 흐름은 FE가 정한다.

## 3. RAG 요청 (코드 변경 없음)

- **알림:**
  - api는 RAG 카드를 만든 뒤 원인 안의 점검 위치와 원인의 위치만 바꾼다. 글은 그대로다.
  - `PROMPT_VERSION`을 올려도 괜찮다. 새 카드에도 같은 순서를 다시 적용한다. 단, 카드 고정에 걸린 케이스는 예외다.
- **요청:** 점검 id(`E0xx-Kn`)를 바꾸지 말아 달라(`rag/data/error_mapping.json:3`의 약속). id가 바뀌면 그 id로 쌓인 현장 기록이 조용히 사라진다.
- **제안:** E029 재시작 주의(`rag/data/error_mapping.json:293-303`)는 원인 1(E029-C1)에만 있다.
  - 원인 2를 '맞아요'로 고르면 조치 화면에 이 문구가 나오지 않는다. 지금도 그렇다.
  - 점검 화면의 쪽 버튼 설명에도 실리지 않는다. 같은 문서의 같은 쪽은 한 번만 남기기 때문이다(`ui/src/lib/guidance.ts:36-38`).
  - 코드 단위 주의로 옮기거나 두 원인 모두에 두면 좋겠다. 그러면 어느 원인을 골라도 이 문구를 보이게 할 수 있다.
  - 둘 다 api가 매핑대로 나뉜 E029 카드에서도 원인을 옮길 수 있게 한다. 두 원인에 둘 때는 카드에서 같은 항목(글 · 근거가 같음)이어야 한다.
  - 지금은 조치 보호로 막혀, E029는 두 점검을 한 원인에 묶은 RAG 캐시 카드에서만 순서가 바뀐다.

## 4. api 담당 (알림)

- **위험:** 기록이 생긴 케이스에서 카드를 다시 만들면, 원인 묶음이 바뀌어 기록의 원인 번호(`E029-1` 꼴)가 다른 원인을 가리킬 수 있다.
  - 카드를 다시 만드는 때는 대체 카드에서 RAG 카드로 바뀔 때와 `PROMPT_VERSION`이 바뀔 때다.
  - 플래그와 상관없이 지금도 있는 위험이다.
- **이 작업이 한 일:** R2로 순서를 정한 케이스만 고정한다(`api/main.py`의 `get_case`, `api/field_memory.py`의 `order_pinned`).
- **정할 것:** 나머지 케이스를 어떻게 할지 api 담당이 정한다.
- **플래그를 끄면:** 켜고 만든 케이스(`field_order`가 있는 행)는 끈 뒤에도 순서와 고정을 지킨다(스펙 4.5). 시연은 새 `API_DB`로 한다.
