### Key Point 2 : Assessment Framework (툴)

##### 1. RAGAS (프로토타입/평가용)
Pandas 기반으로 모델의 답변 결과를 오프라인에서 정량적으로 채점하는 데 특화

Pros
- 제조업에 필수적인 엄격한 환각 검증: 공장 설비 매뉴얼을 다루는 만큼 hallucination을 막는 것이 가장 중요한데 RAGAS가 특화되어이씀
- 가벼운 파이프라인 결합: 별도의 서버나 UI 창을 띄울 필요 없이 Python 스크립트 내에서 질문가능
   검색된 문서, 생성된 답변을 표 형태로 밀어 넣으면 점수가 바로 산출되므로 초기 연구/실험단계에서 가볍게 쓸 수 있음

Cons
- 시각적 대시보드 부재: 시스템의 실시간 흐름을 보여주는 UI가 없음
   E2E 파이프라인의 전체적인 동작 과정을 멘토나 팀원들에게 시각적으로 보여주기에는 불리
- 최종 운영 모니터링 한계: 개발 과정에서의 '성능 평가'에는 훌륭하지만 실제 슬랙 알림이 지속적으로 발송되는 운영 환경에서 시스템이 잘 돌고 있는지 추적하는 기능은 부족

##### 2. TruLens (모니터링 대시보드)
평가 지표 산출부터 LLM 애플리케이션의 동작 과정을 웹 UI를 통해 실시간추적, 시각화

**Pros**
- **파이프라인 시각화 최적:** 센서 데이터 입력부터 AI의 이상 감지, 매뉴얼 검색, 최종 출력까지 이어지는 전체 흐름을 앱 형태로 추적함
   웹 대시보드를 통해 "E01 에러 감지 시 **어떤 프롬프트를 탔고 어떤 문서를 가져왔는지**"를 한눈에 증명할 수 있음 >> 포트폴리오 발표 시 **설명력**, tied to XAI

- 비용 및 **지연 시간 추적**: 단순한 답변 정확도를 넘어 RAG 리포트를 하나 생성할 때마다 **걸리는 시간**과 토큰 비용을 대시보드에 기록가능
  **신뢰성, 가용성, 보전성등 정통적 운영관리지표 관리하기 좋음**

Cons
- 무거운 초기 세팅: RAGAS와 달리 로컬 DB를 세팅하고 백그라운드에서 웹 서버를 띄워야 하므로 초기 코드 작성 시 프레임워크 자체를 학습하고 파이프라인 코드에 래핑하는 작업이 번거로울수도 있고, 시스템이 동작할 때마다 평가와 로깅을 동시에 수행하므로 코드가 다소 무거워지고 실행 시간이 길어질 수 있음

##### 3. (이상적) 결론

>> 1. **초기엔 RAGAS**를 활용해서 DB에 E01~E04 case에 대한 정비 지침서 (혹은 구해온 manual)를 처음 밀어 넣고 LLM이 halucination 없이 정확하게 답변을 생성하는지 성능을 끌어올린 뒤
>> 2. **실제 serving, 유지보수는 TruLens**를 통해 단순한 RAG 성능 튜닝을 넘어 센서에서 이상 징후가 포착되었을 때 자동 필터링을 거쳐 처리하도록 이식하는것이 이상적일것 같다. (아직은 모호)

### Key Point 3 : RAG Assesment Dataset (수급방안)

1. 공공 벤치마크 데이터셋 (일반 QA/검색 평가용)
	- 특징: 일반적인 상식, 뉴스, 위키피디아 기반 질문과 정답 세트로 구성되어 있다
	   RAG 평가 프레임워크의 기본 동작을 테스트할 때 쓸 수 있지만 도메인 특화 프로젝트의 평가용으로는 부적합
 
2. **LLM 기반 합성 데이터 자동 생성 (Synthetic Data Generation)**
    - **종류:** **RAGAS의 `Testset Generator`** 또는 **LangChain/LlamaIndex의 합성 데이터 생성** 기능
    - **특징:** 프로젝트가 보유한 매뉴얼 텍스트 문서를 LLM에 밀어 넣으면 문맥을 분석하여 가상의 question-ground truth 쌍을 자동으로 수십~수백 건 생성해 줌

3. **자체 매뉴얼 기반 Dataset 직접 수동 구축**
    - **특징:** 개발자나 현업 정비 전문가가 주요 장애 시나리오별로 질문과 모범 정답 리포트를 직접 작성하는 방식
    - 품이 들고 데이터 개수는 적더라도 평가의 정확성과 신뢰도가 가장 높음

- 우리는 **RSW 설비의 에러 코드와 센서 이상 시그널**을 다루는 특수한 B2B/제조 도메인이므로 외부 공공 데이터셋(1)은 사용할 수 없고 **'합성 생성(2) + 직접 수거(3)'** 방식을 혼합한 전용 데이터셋을 구성해야 할 예정.

##### 평가 데이터셋의 4대 핵심 구성 항목 (3번)

1. **Question (입력 질문 / 이상 시그널 컨텍스트):**
    - 예: "E01 에러 감지: 카운터밸런스 보상 압력이 1800ms 동안 목표 수치에 도달하지 못함. 현재 c5 압력 수치 이상 발생."

2. **Contexts (검색된 매뉴얼 단락):**
    - Vector DB에서 가져온 E01 조치 지침서 단락 텍스트

3. **Answer (RAG 파이프라인이 생성한 리포트):**
    - LLM의 최종 출력 or 리포트

4. **Ground Truth (이상적인 모범 정답):**
    - 정비 매뉴얼 기반으로 작성된 완벽한 원인 분석 및 수정 조치 가이드 문장.

##### 데이터셋 구축 프로세스 (3번)

1. 매뉴얼 텍스트 준비:
    - E01-04 각각의 원인과 조치 절차가 담긴 사내 **정비 지침서** 마련

2. LLM 합성 생성으로 기본 데이터 확보 (1차)
    - **RAGAS의 `Testset Generator`를 활용해 준비된 E01-E04 매뉴얼 문서를 바탕으로 질문-정답 세트 20-30개를 자동으로 1차 추출**

3. 핵심 시나리오 수동 검수 및 최종 정제 (2차):
    - E01-E04 핵심 장애 시나리오별로 최소 5건씩, 적어도 20-30건의 평가세트로 **수작업 정제**

### 추가) RAGAS-Testset Generator

1. 작동 매커니즘

- **문서 분할 및 분석:** 입력된 매뉴얼을 청킹하고 각 단락에서 중요한 키워드와 개념 추출
- **지식 관계망 구축 (Onthology):** 추출된 개념들 간의 물리적, 논리적 관계를 분석하여 문서 내용에 대한 내부적인 지식 그래프를 만듬
- **질문 생성 및 진화:** 구축된 지식을 바탕으로 생성용 LLM이 가상의 질문들을 만들어냅니다. 단순한 질문에서 시작해 복잡도를 점진적으로 높여가는 일종의 진화과정을 거침
- **정답 및 문맥 매핑:** 만들어진 질문에 완벽하게 부합하는 이상적인 정답을 생성하고 정답의 근거가 된 실제 매뉴얼 단락을 짝지어 최종 데이터셋을 완성

2. 생성하는 질문의 난이도 유형 
단순한 텍스트 매칭이 아닌 RAG 파이프라인의 실질적인 추론 능력을 평가하기 위해 다음과 같이 다양한 유형의 질문을 섞어서 생성함

- **단순 질문 (Simple):** 특정 단락의 사실을 그대로 묻는 직관적인 질문
	- (예: "E01 에러를 판정하는 기준 시간은 몇 ms인가?"

- **추론 질문 (Reasoning):** 문서의 내용을 바탕으로 논리적 인과관계를 묻는 질문
	- 예: "c5 압력이 목표치에 도달하지 못했을 때, 가장 먼저 확인해야 할 센서는 무엇인가?"

- **다중 문맥 질문 (Multi-context):** 여러 단락이나 서로 다른 페이지에 흩어진 정보를 종합해야만 대답할 수 있는 질문입니다.
	- 예: "E01(압력 부족)과 E02(전극 파손) 에러 발생 시 공통적으로 적용할 수 있는 안전 조치는 무엇인가?"

### 사전 배경지식) RAG를 평가하는 기준

1.  **검색성능 평가 (Retrieval) / 문맥의 타당성**

- 문맥 관련성 (Relevance): 발생한 이상 시그널(ex, E01)과 관련이 있는 정비 지침서 혹은 해당 부분만 정확하게 검색했는가
- 문맥 정밀도 (Precision): 검색된 문서 리스트 중 정답에 해당하는 핵심 매뉴얼의 중요도가 올바르게 평가되었는가 
- 문맥 재현율 (Recall): 특정 에러를 해결하는 데 필요한 모든 매뉴얼과 절차를 누락 없이 가져왔는가 

2. **생성성능 평가 (Generation) / 결과물 퀄리티**

- 사실성/충실성 (Faithfulness): LLM이 생성한 조치 가이드가 검색된 사내 정비 지침서 내용에만 근거하는가, hallucination이 없는가
- 답변 관련성 (Relevance): 최종 생성된 리포트가 이상 감지 시그널에 대한 원인 분석 및 수정 조치 방향을 묻는 본래 목적에 부합하게 생성되었나

### 기타1) 산업공학 도메인 : 운영관리 (+Operation Research)
##### 1. MTTR (장애 평균 복구 시간): 프로젝트의 핵심 KPI

- **기존의 문제 (문제정의):** 기존에는 시스템 이상 징후 발생 시 담당 개발자나 작업자가 복잡한 서버 메트릭 그래프와 수만 줄의 에러 로그를 수동으로 일일이 조회하느라 장애 원인 파악(MTTR) 시간이 심각하게 지연된다
- **RAG의 기여:** LLM 기반 RAG가 에러에 부합하는 사내 정비 지침서를 즉시 검색해 요약 리포트 혹은 알림을 발생시켜 작업자는 원인 분석 건너뛰고 바로 수정 조치에 돌입할 수 있게되므로 **장애 인지부터 복구까지의 MTTR을 단축**시킬 수 있다는 접근 - TruLens를 통해 Latency, 선제적알림(csv파일 내 타겟값) 만 추적하면 구할 수 있음
##### 2. MTBF (평균 무고장 시간): 예측 유지보수의 가치 증명

- **기존의 문제 (문제정의):** 고장이 터진 후에야 고치는 사후 정비 방식으로는 예기치 않은 가동 중단을 막을 수 없어 전체 공정의 효율이 떨어질 것이다.
- **RAG의 기여:** 모델이 E01~E04라는 치명적 고장으로 파멸하기 전 E016이나 E028 같은 자잘한 경고 로그들을 전조 증상으로 미리 포착하여 RAG 알람을 발생시킨다.
  작업자가 기계가 멈추기 전에 RAG 가이드를 보고 미리 윤활유를 보충하거나 영점을 맞추면 **기계가 멈추는 치명적 고장 주기를 늘려 MTBF를 극대화**할 수 있게될것이다.
##### 3. MTTF (평균 고장 시간): 소모성 부품수명 관리

- **RAG의 기여:** RAG 시스템이 매뉴얼에 근거해 마찰력이나 압력의 미세한 이상 패턴을 짚어주며 "현재 상태에서 마모를 늦추기 위한 조치"를 가이드할 수 있다. 예를 들어 E02(전극 파손)와 같은 부품의 파국적 손상을 늦추어 **핵심 소모품의 실질적인 수명(MTTF) 연장에 기여**한다고 볼수있다.

### 기타2) 평가지표 참고 (수식적인 부분)

##### 1. 문맥 정밀도

- **의미:** 검색된 정비 지침서 중 정답에 해당하는 핵심 매뉴얼이 상위에 잘 랭크되었는지를 0~1 사이의 값으로 산출합니다.
- **산출 수식 (MAP@K 활용):**
$$\text{Context Precision@K} = \frac{\sum_{k=1}^{K} (\text{Precision@}k \times v_k)}{\text{관련 있는 총 매뉴얼 수}}$$

- **작동 원리:** $K$는 검색된 문서의 순위입니다. $v_k$는 $k$번째 문서가 실제 관련이 있으면 $1$, 아니면 $0$을 부여하는 지시 함수(Indicator function)입니다. 예를 들어 E01(카운터밸런스 시간 초과) 시그널이 발생했을 때, E01 조치 매뉴얼이 1순위로 검색되면 높은 점수를 받지만, 3순위나 4순위로 밀려나면 점수가 페널티를 받아 크게 깎이게 됩니다.

##### 2. 문맥 재현율 (Context Recall)

- **의미:** 완벽한 조치를 위해 필요한 정답(Ground Truth) 정보가 검색된 매뉴얼 안에 누락 없이 얼마나 포함되었는지 계산합니다.
- **산출 수식:**
$$\text{Context Recall} = \frac{\vert{}\text{검색된 매뉴얼 내용에 포함된 정답(Ground Truth) 문장 수}\vert{}}{\vert{}\text{정답(Ground Truth)의 총 문장 수}\vert{}}$$

- **작동 원리:** 심판 역할을 하는 LLM이 사전 구축된 이상적인 '정답 리포트'를 여러 개의 문장(Statements)으로 쪼갭니다. 그런 다음, 검색해 온 문서들을 읽고 정답의 각 문장 내용이 문서 안에 존재하는지(True/False) 매핑하여 비율을 계산합니다.

##### 3. 사실성 및 충실성 (Faithfulness)

- **의미:** 모델이 검색된 매뉴얼에 없는 내용을 지어내지 않았는지(환각 현상)를 철저히 검증하여 0~1 사이로 수치화합니다.
- **산출 수식:**
$$\text{Faithfulness} = \frac{\vert{}\text{검색된 매뉴얼(Context)로 증명 가능한 답변 내 주장(Claim) 수}\vert{}}{\vert{}\text{답변에서 추출된 총 주장(Claim) 수}\vert{}}$$
- **작동 원리:**
    1. 평가용 LLM이 최종 생성된 리포트에서 개별 주장(Claim)들을 추출합니다. (예: "카운터밸런스의 압력을 확인해야 한다", "센서를 교체해야 한다" 등)
    2. 각 주장이 검색된 문서 내용으로 뒷받침(Entailment)되는지 검사합니다. 만약 검색된 매뉴얼에 "센서 교체"라는 말이 없는데 LLM이 리포트에 적었다면 분자가 줄어들어 점수가 깎입니다.

##### 4. 답변 관련성 (Answer Relevance)

- **의미:** 생성된 리포트가 애초에 감지된 에러(예: E01, E02 등)에 대한 원인과 조치 방법을 묻는 본래의 목적에 얼마나 부합하는지 임베딩 공간에서 계산합니다.

- **산출 수식 (코사인 유사도 활용):**
$$\text{Answer Relevance} = \frac{1}{N} \sum_{i=1}^{N} \cos(E(q), E(q_i))$$
- **작동 원리:**
    1. 생성된 리포트를 바탕으로 평가용 LLM이 역으로 $N$개의 '가상의 질문($q_i$)'을 생성합니다.
    2. 임베딩 모델($E$)을 사용해 원래의 실제 질문/시그널($q$)과 가상의 질문들($q_i$)을 벡터로 변환합니다.
    3. 이 벡터들 간의 코사인 유사도(Cosine Similarity)를 평균 내어 점수를 산출합니다. 원래의 목적에 맞게 답을 썼다면, 역으로 생성한 질문도 원래 질문과 벡터 공간상에서 매우 가까울 것이라는 원리를 이용한 정량화 기법입니다.

### 기타3) RAG 공공 벤치마크 데이터셋

- MS MARCO
	- 마이크로소프트에서 공개한 대규모 기계 독해 및 딥러닝 검색 연구용 데이터셋입니다. 실제 Bing 검색 엔진의 로그를 기반으로 구축
	- **질의응답:** 실제 사용자가 검색한 질문과 사람이 직접 작성한 답변을 포함합니다
	- **패시지 랭킹:** 질문에 가장 알맞은 문서를 찾아 순위를 매기는 모델 학습에 쓰입니다.
	- **연구 활용:** 인공지능이 문맥을 이해하고 정답을 찾아내는 자연어 처리(NLP) 성능 평가에 널리 사용됩니다

- SQuAD
	- 컴퓨터가 지문을 읽고 질문에 답하도록 훈련하고 평가하는 기계 독해(MRC) 벤치마크 데이터셋
	- **정의**: 스탠퍼드 대학에서 구축한 대규모 질의응답(QA) 데이터셋입니다.
	- **구성 요소**: 위키피디아 문서의 **지문**, 이에 대한 **질문**, 그리고 지문 내에 존재하는 **정답으로 이루어져 있습니다.
	- **목적**: AI 모델이 문맥을 정확히 이해하고 정답 텍스트와 위치를 찾아내는지 객관적으로 평가합니다

- HotpotQA
	- 복수의 문서(멀티홉, Multi-hop)를 탐색하고 추론해야 답을 구할 수 있는 113,000개의 위키피디아 기반 질의응답 데이터셋
	- **멀티홉 추론**: 정답을 찾기 위해 최소 두 개 이상의 서로 다른 문서나 단락을 연결해서 읽고 추론해야 합니다.
	- **문장 수준의 근거 제공**: 모델이 어떤 문장을 근거로 추론했는지 문장 단위의 정답 레이블(Supervision)을 제공하여 설명 가능한 AI 연구를 지원합니다.
	- **다양한 질문 유형**: 기존 지식 베이스 스키마에 구애받지 않으며, 두 엔티티를 비교하는 팩토이드 비교 질문 등을 포함

- BEIR
	- 다양한 도메인과 작업에서 정보 검색(IR) 모델의 **제로샷 성능과 일반화 능력을 평가**하기 위해 만들어진 이질적인 벤치마크 데이터셋 모음
	- **제로샷 평가**: 학습 데이터를 제공하지 않고, 곧바로 다양한 도메인에 적용해 성능을 측정합니다.
	- **다양한 구성**: 9개의 서로 다른 검색 작업과 18개의 공공 데이터셋을 포함하고 있습니다.
