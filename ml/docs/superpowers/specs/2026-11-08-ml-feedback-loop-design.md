# ML 피드백 루프 (D-9): 설계

2026-11-08 · ML · 상태: 설계 합의(11-08, 대화에서 ①~⑥절 사용자 승인), 기준값 보정과 미탐 우선 보정 반영(11-08), 사용자 승인(11-08, 7.5 한 줄을 고친 뒤), 최종 검토 반영(11-08: 6.1, 7.2, 7.4, 7.5, 7.6, 8.2), 현장 Q+ · Q− 평가 임계값 변경(11-09: 2절, 3.2, 7.2)

대화의 절 번호와 이 문서의 절: ① → 4절, ② → 6절, ③ → 7절, ④ → 8절, ⑤ → 9절, ⑥ → 10절. 5절(창 기록 세부)은 ①을 풀어 쓴 것이다. 3.2절(기준값 보정)과 11.1절(api 변경)은 설계 승인 뒤의 사용자 결정으로 더했다.

## 1. 목표

지금 피드백 고리는 사람 기록 → api 현장 기억 → RAG 카드(R1 문장, R2 순서)에서 끝난다. 사람 기록은 ML로 가지 않는다(`api/store.py:3`). 이 설계는 같은 기록과 종료 코드로 **ML 운영 규칙을 바꿀지 판단하는 보고서**를 만든다.

- 루프는 제안만 한다. 반영은 사람이 이미 있는 손잡이로 한다(8.4).
- 1단계(이번 구현): 규칙 수준 도전자, 판정 관문, 보고서, 그리고 그에 필요한 api 변경(11.1).
- 2단계(설계만, 9절): 모델 수준 도전자(다시 학습한 모델, 새 정보를 넣은 모델).

ML에 이 고리가 필요한 이유:

- B-2·B-5의 결론은 "이 윈도우 통계에는 고장 1시간 전 정보가 없다(피처 문제, 모델 문제 아님)", "데이터 안에서 만들 수 있는 정보는 소진, 고장 10분 이전 분리력 AUROC ~0.6이 천장"이다(`MEMORY.md` 4절). 모델을 바꿔서는 오르지 않고, 새 정보가 들어와야 오른다.
- 운영 중에 c1~c19 밖의 정보가 들어오는 통로는 사람 기록뿐이다.
- "새 정보를 넣을지 말지" 판정은 오프라인으로 이미 해 왔다. B-5 정비 이력, B-6 에러 코드 이력, A-5 전원 깜빡임은 모두 채택하지 않았다. 이 루프는 그 관문을 현장 데이터와 현장 라벨로 계속 돌리는 장치다.

성공 기준:

1. `RSW_WINDOW_LOG=1`이고 `RSW_STATE_DIR`가 있으면, 서버가 새로 채점한 창마다 창 기록 한 줄을 쓴다. 끄면 파일이 생기지 않고 모든 응답이 지금과 같다.
2. `python .py/feedback_loop.py`가 상태 폴더와 닫힌 케이스(api DB 파일, `/api/history` JSON, api 주소 중 하나)를 읽어 `report.md`와 `report.json`을 쓴다. 입력 일부(창 기록, 닫힌 케이스, 실험실 캐시)가 없어도 그 부분만 "해당 없음"으로 적고 끝까지 돈다.
3. 새 평가기가 B-19 캐시에서 B-20 고정 규칙의 수치(오알람 16.40회/건·일, 적중 0.488, 우연 0.343, 초과분 +0.146 [+0.059, +0.221])와 11-08 점검의 GATE 수치(15.10회, 초과분 +0.080 [−0.009, +0.162], D −0.066 [−0.128, −0.013])를 소수 셋째 자리까지 그대로 낸다.
4. 오프라인 실행 ①(테스트 8파일 + 시뮬레이션 라벨)의 보고서 맨 위에 "시뮬레이션 라벨 포함 — 성능 아님" 경고가 있고, 종합 판정이 GATE·Q− "반영 안 함"(실험실 탈락), Q+ "보류"(실험실 통과, 현장 증거 부족)다. 실행 ②(10-29 시연의 실제 라벨)의 보고서에는 test_0의 E04 프로필 제안이 있다.
5. 한 파일 이상에서 창 기록의 점수가 오프라인 평가 CSV(`models/scores/test_N_ensemble.csv`)와 창 단위 1e-4 안에서 같다.
6. `ui/`, `rag/`를 바꾸지 않는다. `api/`는 11.1의 변경만 한다. ML의 API 응답, 핸드오프 계약(v1.4), 서빙 판정, outbox를 바꾸지 않는다.
7. ML `pytest`(기존 130개 + 새 시험)와 api 시험(기존 + 새 시험)이 통과하고, `ruff check .`에 새 오류가 없다.

범위 밖:

- 루프가 스스로 서빙을 바꾸는 일(자동 반영).
- `ui/`·`rag/` 수정. 필요한 것은 요청 메모로 남긴다(11.2).
- 1단계에서 모델을 다시 학습하거나 새 정보를 받는 일. 9절에 설계만 둔다.
- 실서버(ML·api·UI) 시연, 보고서의 화면 표시.
- 24시간 반복 규칙 조정(B-9 관문 대상).
- 실제 외부 데이터 사용. `ml/CLAUDE.md`의 데이터 제약(train·test 밖 데이터 없음)은 1단계에서 그대로다.

## 3. 배경: 11-08 점검과 기준값 보정

### 3.1 점검: 현장 사유가 시키는 대로 바꾸면

질문: 현장에서 "설비 정지 · 전원 꺼짐" 오알람 사유가 쌓여, 조기 경보에 비용접 게이트(일반 알람과 같은 "비용접 비율 > 0.5면 보류")를 넣자는 결론이 나오면 관문은 받아들일까.

방법: `results/A-5/overlap.py`와 같은 틀이다. B-19 캐시의 폴드 밖 점수 8회분(64건)을 B-18 평가 그대로 썼고, 판정 기준은 계산 전에 고정했다. 버림용 스크립트라 저장소에 없다. 같은 수치는 3.2의 보정 스크립트와 10.1의 실험실 대조 시험이 저장소 안에서 다시 낸다.

|---|---|---|---|---|
| 지금 (게이트 없음, q 0.975) | 16.40 | 0.488 | 0.343 | +0.146 [+0.059, +0.221] |

- 게이트 − 지금: D −0.066 [−0.128, −0.013]. 게이트 − q 0.98: −0.044 [−0.112, +0.021]. 판정은 "반영 안 함"이었다.

- 사람 라벨이 못 보는 쪽: 게이트는 적중 7.5건을 없앤다(지금 적중 31.3건의 24%). 고장 10–60분 전 알람 창의 66%가 비용접 창이고, 평소 오알람 창은 40%다.

교훈: 사람의 오알람 라벨만으로 도는 고리는 이 변경을 채택한다. 종료 코드로 세는 미탐 라벨이 있어야 막는다. 그래서 이 설계는 두 라벨을 같이 쓴다(6절).

- "덜 울림" 통과에 "놓침이 늘었다는 통계적 증거 없음(D의 CI 상한 ≥ 0)"을 더하고, 비교 대상을 고정 기준점으로 둔다(7.4). 같은 추출로 다시 계산해도 최소 고장 수는 10건 그대로다(표본이 작으면 CI가 넓어 이 조건이 판정을 바꾸지 않았다).
- 프로필 건수 = 1 + 견딜 오클릭 수(1번) = 2. 일수는 보정의 동률 처리(건수가 같으면 일수가 큰 쪽)로 2일. 학습 33건 중 1건, 테스트 11건 중 3건 줄인다(잘못 뺌 0). 현장처럼 오래 돌면 기록이 쌓여 더 줄인다.

현장 판정력은 낮다. 고장 64건을 모아도 실행 하나로는 GATE만 한 차이를 39%만 잡아낸다(Q+는 64%). 현장 판정은 오랫동안 "증거 부족"이나 "탈락"이 많을 것이다.

재검사(11-09, `results/D-9/apply_threshold_check.py`, 기준은 실행 전에 고정): 7.2를 바꾼 뒤 같은 추출로 최소 고장 수를 다시 구했다. 실행 r의 Q+ · Q−에는 나머지 7회의 평균 임계값을 썼다. 잘못된 반영 제안은 10건에서 2.5%, 10건 이상 전체에서 4.5% 이하라 `MIN_FAILURES` 10은 그대로다. Q+를 잡아낼 확률은 고장 64건에서 64%가 53%로 줄었다.

## 5. 창 기록

### 5.1 켜는 조건

- `RSW_WINDOW_LOG=1`이고 상태 폴더(`RSW_STATE_DIR`, 기본 `./state`)가 비어 있지 않을 때만 쓴다.
- `RSW_WINDOW_LOG=1`인데 `RSW_STATE_DIR=""`(메모리만)이면 시작할 때 경고를 한 번 남기고 쓰지 않는다.

### 5.2 위치와 모양

- `<상태 폴더>/windows/<gun_id>/<YYYY-MM-DD>.jsonl`. 날짜는 창 시작의 UTC 날짜이고, 한 줄이 한 창이다.
- `<상태 폴더>/windows/models.json`: 모델 id → `{model_cols, threshold, early_warning: {rule, threshold, quantile}}`. 기록을 켠 채 시작할 때 지금 번들의 항목을 더한다. 있던 항목은 지우지 않는다.

### 5.3 쓰는 때

`Detector`가 trace에 새 창을 붙이는 바로 그 자리에서 쓴다(`main.py:1086`의 조건: 새로 채점했고 앞 창과 겹치지 않음). trace와 같은 조건이라, 요청을 어떤 크기로 보내도 창마다 한 번이다.

### 5.4 필드

| 필드 | 값 |
|---|---|
| `window_start`, `window_end` | UTC ISO 8601, 끝에 `Z` |
| `model` | `<번들 이름>@<created>` (`models.json`의 키) |
| `score`, `threshold` | 모델 점수, 그 창의 알람 임계값 |
| `alarm`, `held`, `sustained`, `critical` | trace와 같은 값 |
| `early_warning`, `early_warning_onset` | 조기 경보 상태, 그 창에서 시작했는지 |
| `ew_threshold` | 조기 경보 임계값 |
| `warmup` | 조기 경보 조건이 쓴 워밍업 여부(`Detector.in_warmup`, `main.py:859`) |
| `gun_norm` | `warming_up` / `gun` / `global` |
| `non_welding_share` | 그 창의 비용접 비율 |
| `error_codes`, `error_code` | 그 창의 0 아닌 코드(나온 순서, 중복 없음), 마지막 코드 |
| `vec` | 모델 입력 벡터(`models.json`의 `model_cols` 순서, float) |

`vec`은 스케일링, 창 집계, 건 정규화를 다 거친 뒤 모델에 바로 들어가는 값이다(`main.py:986-991`). 2단계 M1이 이 값을 그대로 다시 채점한다(9.2).

### 5.5 실패, 크기, 재시작

- 쓰기 오류는 그 건에서 처음 한 번만 경고 로그를 남기고 넘어간다. 응답, 상태 저장, outbox에는 영향이 없다.
- 크기는 `vec`을 포함해 건당 하루 약 1~2 MB다. 1단계에서는 지우지 않는다(`state/`는 git 제외).
- 재시작 뒤 같은 창이 다시 써질 수 있다. 루프는 (설비, `window_start`)마다 마지막 줄만 쓴다.
- 서버 여러 대가 상태 폴더 하나를 같이 쓰는 구성은 지금처럼 지원하지 않는다(`MEMORY.md` 7절 10).

## 6. 라벨 규칙

### 6.1 고장 T

- 후보: outbox 기록 중 `event_type`이 `critical`이거나 없는(v1.2까지의) 핸드오프로, `trigger.rule_code`가 있는 것. T = `trigger.rule_trigger_time`(없으면 `detected_at`).
- outbox는 30일만 보존한다. 지워진 핸드오프는 케이스에 남은 대표 알림으로 대신한다(조건은 같다, 11-08 최종 검토). 조기 경보 시작 시각도 api DB의 케이스 기록으로 대신한다. 반복으로 묶인 알림은 시각이 없어 복구하지 못한다.
- 실험실에서는 고장 T가 `meta.csv`의 `fault_time`이다(B-18과 같음). 실험실 평가에는 outbox와 사람 판정을 쓰지 않는다.
- 반복 발화와 프로필 밖 발화는 서버가 경고로 낮추고 핸드오프를 만들지 않는다(`main.py:532-538`). 그래서 후보에 없다.
- 사람 판정: 그 핸드오프가 든 케이스가 오알람으로 닫혔으면 **거부**(고장 아님), 해결 종료면 **확인**, 그 밖(열림, 미해결, 인계)은 **추정**이다.
- 판정에 쓰는 고장은 확인 + 추정이다. 보고서는 확인된 고장만으로 계산한 결과도 같이 쓴다.

### 6.2 조기 경보 자동 라벨 (창 기록)

정의는 B-18 `Frame`(`results/B-18/early_warning.py`)을 한 설비에 고장이 여러 번 있는 경우로 넓힌 것이다. 설비마다 고장이 기록 끝에 한 번이면 B-18과 같다.

- 설비 순서는 이름순이다(B-18의 `pd.factorize`와 같음).
- lead(창) = 다음 고장 T − (창 시작 + 60초). 고장 T부터 60분 안의 창은 모든 셈에서 뺀다(B-18은 T 뒤 창을 지운다).
  - 60분은 데이터로 정할 수 없는 가정이다. 모든 파일이 고장 10분 뒤에 끝나서 고장 이후 구간이 없다. 보고서의 "고장 뒤 조기 경보" 진단(8.2)으로 현장 기록이 쌓이면 다시 정한다.
- 쓸 수 있는 창: 워밍업이 아닌 창.
- 연속 구간: 같은 설비에서 창 시작이 60초 간격으로 이어지는 창들(B-18 `brk`와 같음).
- 고장마다 **적중 / 미탐**: lead가 600~3600초인 쓸 수 있는 창이 25개 이상이면 판정한다. 그중 조기 경보가 켜진 창이 하나라도 있으면 적중, 없으면 미탐이다. 25개 미만이면 판정하지 않는다.
- **우연**: 같은 판정을 기준점 T − k×24시간(k = 1..6)에서 한다. 기준점 구간(기준점 앞 600~3600초)이 다른 고장의 앞 60분과 겹치거나 기록 밖이면 그 k는 쓰지 않는다. 고장마다 쓸 수 있는 k의 평균을 낸다.
- 조기 경보 **시작**: 조건 연속 구간의 첫 창(지속 k창이면 k번째 창)이다. 그 창의 lead가 3600초를 넘으면(다음 고장이 없으면 무한대) **오알람**이다. 그 창이 설비 기록 끝 60분 안이면 결과를 아직 모르니 **대기**이고, 세지 않는다.
- **감시 일수**: lead가 3600초를 넘는 쓸 수 있는 창의 수 / 1440. 기록 끝 60분 안의 창은 뺀다.
- 지표: 오알람/건·일 = 오알람 시작 수의 합 / 감시 일수의 합. 적중 = 판정된 고장의 적중 평균. 우연 = 고장별 우연의 평균. 초과분 = 적중 − 우연.

### 6.3 조기 경보 사람 라벨

- 조기 경보 핸드오프(`event_type` = `early_warning`)를 켰을 때만 생긴다(`RSW_EARLY_WARNING_HANDOFFS=1`). 건별 쿨다운(3600초)이 있어 시작 중 일부만 케이스가 된다.
- 핸드오프와 시작 창은 같은 설비, 그리고 `early_warning.onset_at`(시작 창의 끝, `main.py:368`)으로 잇는다.
- 케이스가 오알람으로 닫힘 → 그 케이스에 든 모든 시작에 **사유**(`closure.reason`, `closure.note`)를 붙인다. 오알람·대기 판정은 자동 라벨 그대로다.
- 케이스가 해결 종료로 닫힘 → **조치함**: 그 케이스에 든 시작을 오알람 셈에서 빼고 따로 센다(고장을 막았을 수 있음). 고장 쪽의 적중·미탐 판정은 바꾸지 않는다.
- **불일치**: 사람은 오알람으로 닫았는데 자동 라벨은 오알람이 아닌 시작(뒤 60분 안에 고장이 있음). 자동 라벨을 따르고 보고서에 목록으로 적는다.
- 사유는 FE 초안의 칩 4종이다(`ui/src/types/case.ts:325`): 설비 정지 · 전원 꺼짐 / 정상 작업 중 변동 / 센서 · 신호 문제 / 기타. 목록 밖의 글은 기타로 센다. api는 `FIELD_MEMORY=1`일 때만 사유를 저장한다(`api/main.py:361-366`).

### 6.4 critical 사람 라벨

- 케이스 하나를 1건으로 센다. 반복으로 묶인 알림은 따로 세지 않는다.
- 종료 결과: 오알람 / 실제(해결 종료) / 미확인(그 밖).
- 집계 단위는 설비 × 고장 유형이다(`preprocess.TERMINAL_TO_CLASS`: E012→E01, E016→E02, E028→E03, E029→E04). 코드 없는 critical(모델 단독)은 프로필 셈에 넣지 않는다.

### 6.5 케이스와 ML 알림 잇기

- 케이스의 대표 알림: `event.event_id` → outbox 기록.
- 반복으로 묶인 알림
  - api DB를 읽을 때: `events` 표(event_id → case_id).
  - `/api/history`(JSON 파일이나 주소)를 읽을 때: 11.1의 `repeat_event_ids`.
  - 11.1 이전 api의 `/api/history`만 있을 때: 같은 설비, 같은 `trigger.rule_code`(없음끼리는 같다고 봄), outbox `detected_at`이 케이스의 `detected_at` 이상 `closure.at` 이하이고, 다른 케이스의 대표가 아닌 알림.
- api DB는 읽기 전용(`mode=ro`)으로 연다. 표 모양은 `api/store.py`의 것(`cases.data` JSON, `events`)이다.
- 닫힌 케이스 항목에 `"simulated": true`가 있으면 보고서 맨 위에 경고를 단다. 실제 api에는 없는 필드이고, 10.2의 스크립트 작업자만 넣는다.

### 6.6 정리

- 창 기록의 중복은 (설비, `window_start`)마다 마지막 줄로 정리한다.
- 시각은 모두 UTC로 맞춰 비교한다(`MEMORY.md` 2절의 naive UTC 규칙).

### 6.7 한계

- 11.1 이전에 만든 api DB에서는 코드 없는 알림(조기 경보, 모델 단독 critical)이 설비마다 열린 케이스 하나에 묶여 있을 수 있다(`api/store.py:90-98`). 그 케이스를 닫으면 묶인 알림이 모두 같은 라벨을 받는다. 11.1 뒤에는 둘이 따로 묶인다.
- 프로필 밖 코드는 사람에게 가지 않는다. 그래서 프로필이 틀려도 루프는 알아챌 수 없다.
- 종료 코드 상태가 길게 이어지는 동안의 조기 경보 시작도 오알람으로 센다(B-18과 같음).
- critical의 정답은 사람 판정뿐이다. "실제"는 사람이 해결 종료했다는 뜻이지 검증됐다는 뜻이 아니다.

## 7. 도전자와 판정

### 7.1 지금 규칙(챔피언)과 기준점

- **지금 규칙**

  - 실험실에서는 실행마다 정상 창의 0.975 분위수다(지금 규칙과 같음).

### 7.2 1단계 도전자

모든 조기 경보 도전자에서 워밍업 창은 늘 조건 밖이고, 지속은 1창이다.

| 이름 | 조건 | 임계값 | 연결 사유 | 적용 방법 |
|---|---|---|---|---|
| GATE | 점수 ≥ 임계값이고 비용접 비율 ≤ 0.5 | 지금 규칙과 같음 | 설비 정지 · 전원 꺼짐 | `train.py --early-warning-rule model_k1`로 다시 학습, B-9 절차로 번들 교체 |
| Q+ | 점수 ≥ 임계값 | 실험실: 실행마다 정상 창의 `Q_PLUS`(0.980) 분위수. 현장: 그 값의 8회 평균 | 정상 작업 중 변동 | `train.py --early-warning-q 0.98`로 다시 학습, 번들 교체 |
| Q− | 점수 ≥ 임계값 | 실험실: 실행마다 정상 창의 `Q_MINUS`(0.960) 분위수. 현장: 그 값의 8회 평균 | 없음(미탐 우선 쪽) | `train.py --early-warning-q 0.96`로 다시 학습, 번들 교체 |
| Q0.975 | 점수 ≥ 임계값 | 정상 창의 0.975 분위수(현장 데이터로 다시 맞추기) | 없음 | 지금은 손잡이가 없다. "검토 필요"가 나오고 사람이 반영하기로 하면 임계값을 직접 지정하는 옵션을 만든다 |
| PROFILE(건) | 7.6 | — | critical 오알람 | `PUT /guns/{id}/profile` |

- Q+와 Q−의 분위수는 3.2의 규칙으로 실험실 오알람 곡선에서 정했다. 번들을 바꾸면 같은 규칙으로 다시 정한다.
- 현장의 Q+ · Q−는 적용 명령이 만들 임계값으로 평가한다(11-09 사용자 결정 "바꾸기"). 적용 명령은 학습 데이터의 분위수로 다시 학습하므로, 그 값의 추정으로 실험실 8회의 같은 분위수 평균을 쓴다(지금 규칙의 실험실 평균 0.9460, 서빙 값 0.9464). 전에는 현장 정상 창의 분위수로 평가했는데, 테스트 8파일 재생에서 Q+가 0.916으로 지금(0.946)보다 낮아 적용 방향과 반대쪽을 재고 있었다.
- `--lab`이 없으면 적용 값을 모르므로 현장 정상 창의 분위수로 평가하고 보고서에 경고한다. 이때는 실험실 판정이 "해당 없음"이라 종합 판정이 "검토 필요"를 넘지 않는다(7.5).
- 평가에 쓴 임계값이 지금 임계값을 기준으로 적용 명령이 움직이는 방향의 반대쪽이면(현장 분위수, 또는 지금 번들과 맞지 않는 실험실 캐시) 그 현장 수치는 적용 명령의 근거가 아니다. 보고서는 지금 임계값, 현장 평가 임계값과 그 근거(json `threshold_basis`), 실험실 평균을 같이 적는다(11-08 최종 검토, 7.5).
- "센서 · 신호 문제"는 도전자를 만들지 않고, 해당 설비를 점검 권고 목록에 올린다(7.7).
- 정상 창(분위수를 구하는 모집단)은 워밍업 아님, 에러 코드 없음, lead > 86400초인 창이다. 번들의 보정 모집단과 같은 정의다(`early_warning.calibration.population`).
  - 현장에서는 설비 기록 끝 하루 안의 창도 뺀다(lead를 아직 모름). 모든 설비의 정상 창을 합쳐 분위수를 구한다.
  - 실험실에서는 실행마다 그 실행의 창으로 구한다. B-20과 같은 계산이다.
  - 임계값을 정한 데이터로 평가도 하므로 오알람 수는 조금 좋게 나온다. B-20도 같은 방식이다.
- 실험실에서 Q0.975는 지금 규칙과 똑같으므로 실험실 판정은 "해당 없음"이다. 그래서 Q0.975의 종합 판정은 현장에서 통과해도 "검토 필요"까지다(7.5).
- 도전자는 "창 표 → 점수 → 조건" 함수 하나로 정의한다. 2단계의 모델 도전자도 같은 자리에 들어간다(9.7).

### 7.3 짝 비교

- 같은 고장, 같은 설비로 짝짓는다. 설비 단위로 복원 추출(뽑힌 설비의 고장을 모두 가져감)을 2000번 한다.
- 실험실: 고장마다 8회 실행의 평균을 먼저 내고 같은 방식으로 추출한다(`results/A-5/overlap.py`의 `stack`). 오알람/건·일은 8회를 합쳐서 낸다.
- 씨앗: 규칙 하나의 CI는 42, 두 규칙의 차이 CI는 7이다. A-5와 11-08 점검과 같은 방식이라 성공 기준 3의 수치가 그대로 나와야 한다.
- D(지금 규칙) = 초과분(도전자) − 초과분(지금 규칙). D(기준점) = 초과분(도전자) − 초과분(기준점).

### 7.4 증거 출처별 판정

- **통과**: 둘 중 하나.
  - 더 잘 잡음: D(지금 규칙)의 CI 하한 > 0이고, 도전자 오알람 ≤ 24회/건·일.
  - 덜 울리면서 놓침이 늘었다는 증거 없음: D(기준점)의 CI 하한 > −`MARGIN`(−0.120)이고 CI 상한 ≥ 0이다. 그리고 도전자 오알람 ≤ 기준점의 `CHEAPER`배(0.843배)이고 지금 규칙보다 적다.
- **증거 부족**(현장만): 판정된 고장이 `MIN_FAILURES`(10건) 미만이거나, 판정된 고장이 있는 설비가 `MIN_GUNS`(5대) 미만.
- **해당 없음**: 그 출처에 증거가 없음(실험실 캐시 없음, 실험실의 Q0.975, 창 기록 없음).
- **탈락**: 그 밖.

"덜 울림"의 CI 상한 조건과 고정 기준점은 3.2 후속 검사에서 나온 미탐 우선 보정이다. 매번 지금 규칙과 비교하면 한 단계씩 계속 내려갈 수 있어서(3.2의 표), 놓침이 통계적으로 늘어나는 지점에서 멈추게 했다.

D는 초과분(적중 − 우연)의 차이다. 우연이 같이 줄면 적중이 줄어도 D는 0 근처에 남는다(실험실 Q+: 적중 변화 −0.062 [−0.090, −0.039], D −0.022 [−0.050, +0.002]). 이 절의 "놓침"은 이 D 기준의 말이고, 보고서는 적중 변화와 CI를 따로 싣는다(11-08 최종 검토). 통과 규칙을 D로 두는 것은 사용자 결정이다(11-09, 2절).

### 7.5 합치기

| 실험실 | 현장 | 보고서 판정 |
|---|---|---|
| 통과 | 통과 | 반영 제안 |
| 통과 | 증거 부족 | 보류(현장 증거 쌓는 중) |
| 통과 | 탈락 | 검토 필요(실험실과 현장이 다름) |
| 탈락 | 통과 | 검토 필요(실험실과 현장이 다름) |
| 탈락 | 증거 부족 또는 탈락 | 반영 안 함 |
| 해당 없음 | 통과 | 검토 필요(실험실 확인 없음) |

- 마지막 두 줄은 대화에서 승인한 표에 "현장 해당 없음"(창 기록이 없는 실행 ②)을 채워 넣은 것이다.

### 7.6 critical 프로필 제안

- 설비 g, 고장 유형 c에 대해 아래를 모두 만족하면 제안한다.
  - c의 오알람 케이스가 `PROFILE_CASES`(2건) 이상이다.
  - 그 케이스들의 감지 날짜(UTC)가 `PROFILE_DAYS`(2일) 이상이다.
  - c의 실제 케이스가 0건이다.
  - 지금 프로필(`<상태 폴더>/guns/<g>.json`의 `profile`, 없으면 모든 유형)에 c가 들어 있다.
- 2건 = 1 + 견딜 오클릭 1번이다. 이 데이터에는 잘못 뺄 기회 자체가 없어서 위험을 잴 수 없었다(3.2). 2일은 보정의 동률 처리 결과다.
- 제안 본문: `{"expected_fault_classes": 지금 프로필(없으면 E01~E04) − 조건을 넘은 모든 유형}`. 빈 목록이 되면 제안하지 않고 "검토 필요"로 적는다.
- c에 미확인 케이스(열림, 미해결, 인계)가 있으면 제안하지 않고 "검토 필요(미확인 케이스 n건)"로 적는다. 미확인은 고장 셈에 추정으로 들어가므로, 유형을 빼는 제안의 근거가 될 수 없다(11-08 최종 검토). `--history` · `--api`는 닫힌 케이스만 담으므로 열린 케이스는 막지 못한다. 그때는 보고서 경고로 알리고, 열린 케이스까지 막으려면 `--cases`로 돌린다(11-09 실서버 확인 뒤 사용자 결정 "경고 넣기").
- 오알람이 있지만 조건에 못 미치면 "지켜보는 중(2건 중 n건, 2일 중 m일)"으로 적는다.
- 제안 옆에 위험 문장을 붙인다: "이 유형의 진짜 고장이 나도 경고로만 남고 케이스가 생기지 않음(C-3, `main.py:659-663`)."

## 8. 보고서

### 8.1 위치와 이름

- `ml/results/D-9/runs/<이름>/report.md`와 `report.json`. 이름은 `--tag`로 정한다.
- `results/D-9/runs/`는 `.gitignore`에 넣는다(D-8의 `results/D-8/runs/`와 같음). 현장 메모와 케이스 번호가 들어가므로 그대로 올리지 않고, 남길 숫자는 history.md에 적는다.

### 8.2 md 순서 (한국어)

1. **머리말**: 만든 시각, 설비별 기록 기간, 모델 id, 입력 경로, 7.8의 상수와 출처, 그리고 "이 보고서는 제안만 하며, 루프는 아무것도 바꾸지 않음". 시뮬레이션 라벨이 섞였으면 맨 위에 "시뮬레이션 라벨 포함 — 성능 아님" 경고를 단다.
2. **한눈에 보기**: 판정별 도전자 목록(반영 제안 / 검토 필요 / 보류 / 반영 안 함 / 평가 안 함)과 프로필 제안 수.
3. **라벨 현황**
   - 고장: 확인 / 추정 / 거부
   - 조기 경보 시작: 오알람 / 대기 / 조치함
   - critical 케이스: 오알람 / 실제 / 미확인
   - 사유 분포, 사람-자동 불일치 목록
4. **조기 경보**: 지금 규칙의 성적(오알람/건·일, 적중, 우연, 초과분과 CI)과 도전자 표(실험실·현장 각각의 수치, D와 CI, 출처별 판정, 종합 판정). 판정마다 적용 방법(7.2)과 임계값을 한 줄 붙이고, 표에 적중 변화(지금 규칙 대비)와 CI를 싣는다. 확인된 고장만으로 한 결과도 같이 싣는다.
5. **critical 프로필**: 설비, 뺄 고장 유형, 근거 케이스(번호, 날짜), 위험 문장, 적용 명령(`PUT /guns/<id>/profile` 본문). "지켜보는 중" 목록도 싣는다.
6. **사유별 메모**: 7.7 표에 따라 사유마다 연결된 판정, 점검 권고 설비, 기타 메모.
7. **고장 뒤 조기 경보 진단**: 고장 T 뒤 0~120분을 10분 단위로 나눠 조기 경보가 켜진 창의 비율. 6.2의 60분 가정(`POST_FAILURE_S`)을 현장 기록으로 다시 정하기 위한 것이다.
8. **한계**: 판정된 고장 수, 조치함으로 뺀 수, 같은 데이터로 정한 임계값, 낮은 현장 판정력(3.2), 6.7의 한계.

### 8.3 json

- `schema: "feedback_report/1"`.
- 최상위 키: `meta`, `criteria`, `inputs`, `labels`, `early_warning`(`champion`, `reference`, `challengers`), `critical`(`proposals`, `watching`), `reasons`, `post_failure`, `warnings`.
- 나중에 다른 도구나 피드백 에이전트가 읽을 수 있게, md에 있는 숫자는 모두 json에도 있다.

### 8.4 반영은 사람이 한다

보고서가 제안해도 루프는 아무것도 바꾸지 않는다. 사람이 7.2의 "적용 방법"으로 반영한다. 조기 경보 규칙을 바꾸는 것은 지금처럼 다시 학습한 뒤 B-9 절차로 번들을 교체하는 일이고, 프로필은 `PUT /guns/{id}/profile` 한 번이다. 기준점은 사용자 결정으로만 바꾼다(7.1).

### 8.5 재현성

입력이 같으면 `report.json`도 같다(`meta.generated_at`만 다름). 부트스트랩 씨앗이 고정돼 있기 때문이다.

## 9. 2단계: 모델 수준 피드백 (설계만, 이번에는 만들지 않음)

### 9.1 목표

1단계의 라벨, 판정 관문, 보고서는 그대로 두고 도전자 자리에 "다른 모델"을 넣는다. 반영은 여전히 사람이 번들을 바꾸는 방식이다.

### 9.2 도전자 두 종류

| 종류 | 무엇 | 학습 데이터 | 채점 방법 |
|---|---|---|---|
| M1 다시 학습 | 전처리(스케일러, 건 정규화, `model_cols`)는 그대로 두고, 현장 라벨을 더해 모델만 다시 학습 | 학습 72파일 + 현장 창(9.3) | 창 기록의 `vec`을 그대로 다시 채점한다. 서빙은 건드리지 않는다 |
| M2 새 정보 | 새 정보 열을 더한 모델 | 현장 기록만(새 정보는 과거 데이터가 없음) | `vec` + 새 정보 열 |

M1이 전처리를 고정하는 이유: `vec`은 지금 번들의 전처리를 거친 값이다(`main.py:986-991`). 전처리가 바뀌면 `vec`을 그대로 쓸 수 없다.

### 9.3 M1에서 현장 창을 학습에 넣는 규칙

- 양성: 확인·추정 고장 T 앞 60분의 창. 학습 때와 같은 1시간 레이블 창이다(`MEMORY.md` 4절).
- 정상: 고장 1시간 밖, 에러 없음, 비용접 아님. 학습 정상과 같은 정의다.
- 빼는 것
  - "조치함" 케이스 뒤 몇 시간(조치로 상태가 바뀌었을 수 있음). 데이터에 조치 기록이 없어 지금은 정할 수 없고, 2단계 설계 때 현장 기록으로 정한다.
  - "센서 · 신호 문제" 사유가 달린 구간.
  - 사람이 오알람으로 닫은 종료 코드 앞 60분(양성으로 쓰지 않음).

### 9.4 M2용 새 정보의 최소 형식

- 새 정보의 형식이 아직 없으므로, 받는 쪽 형식을 하나로 정해 둔다. 긴 표 `(gun_id, time, name, value)`다. 시계열 센서든 정비 기록이든 자재 로트든 이 모양으로 바꿀 수 있다.
- 루프는 창마다 "창 끝 시각 이전에 들어온 마지막 값"만 붙인다(as-of). 알림 뒤에 적힌 정보가 섞이지 않게 하는 장치다(시점 누설 차단, c19의 교훈).
- 고장이 `MIN_FAILURES`(3.2, 지금 10건) 이상 쌓일 때까지는 학습하지 않고 "쌓는 중"으로만 보고한다.
- 창 기록에 새 정보 칸(`extra`)을 더하는 일은 2단계에서 한다. 1단계에서는 만들지 않는다.

### 9.5 평가에 더할 것

1. **시간 순서 분리**: 도전자는 평가 기간보다 앞선 현장 데이터로만 학습한다. 같은 창으로 학습하고 평가하지 않는다. 예를 들어 앞 4주로 학습하고 다음 2주로 평가하며, 기간을 앞으로 밀어 가며 반복한다.
2. **서빙 경로 확인**: 반영 제안이 나오면, 번들을 바꾸기 전에 그 번들로 main.py를 재생해 점수가 오프라인과 창 단위 1e-4 안에서 같은지 확인한다. 지금의 B-9 절차와 같다(`MEMORY.md` 7절 3).

### 9.6 모델 수준에서 조심할 것

- **모델이 자기 결과를 배우는 문제**: 조기 경보를 보고 조치한 창을 정상으로 학습하면, 모델은 "막힌 고장"을 정상으로 배운다. 그래서 조치함 구간을 뺀다.
- **두 고리가 같은 라벨을 씀**: R1이 "오알람부터 확인"을 띄우면 오알람 닫기가 늘 수 있다. 그 라벨로 학습하면 ML이 덜 민감해지고, 그게 다시 R1을 키울 수 있다. 2단계에서 라벨을 학습에 쓰기 전에, 닫을 때 R1·R2가 적용돼 있었는지를 api가 함께 저장해야 한다(11.1의 4).
- **작은 데이터 과적합**: B-5 정비 이력 피처(4-fold +0.03 → 테스트 −0.05)처럼 처음엔 좋아 보이다 뒤집힌 일이 많았다. 판정은 시간 순서로 분리한 현장 증거로만 한다.
- **사유를 학습 신호로 바로 쓰지 않음**: "설비 정지" 오알람을 음성으로 강하게 학습하면, 3.1에서 본 것처럼 정지 무렵의 고장을 놓친다. 사유는 학습 데이터 거르기(센서 문제)와 보고서 설명에만 쓴다.

### 9.7 1단계가 미리 갖춰 둘 것

- 창 기록에 `vec`, 모델 id, `gun_norm`을 남긴다(5.4).
- 도전자를 "창 표 → 점수 → 조건" 함수 하나로 정의한다(7.2). 1단계 도전자는 기록된 점수를 쓰고, 2단계 도전자는 `vec`(+ 새 정보)로 새 점수를 내면 끼워 넣을 수 있다.

### 9.8 나중에 권한을 올린다면

루프를 주기적으로 돌리고 도전자 번들도 자동으로 만들되, 번들 교체만은 사람이 승인하는 방식이 가장 안전한 다음 단계다.

## 11. api 변경과 다른 파트 요청

### 11.1 api 변경 (우리가 한다, `api/main.py`·`api/store.py`)

1. **조기 경보 케이스의 `severity`**: 핸드오프의 `event_type`이 `early_warning`이면 `warning`, 아니면 `critical`. 지금은 v1.3 이전 가정대로 늘 `critical`이다(`api/main.py:124-125`, 주석 "알림은 ML이 critical일 때만 보낸다"도 고친다). UI는 `warning`을 "주의"로 이미 보여 준다(`ui/src/components/Tag.tsx:38-42`).
2. **코드 없는 알림의 묶음 나누기**: `store.put`이 `cases.code` 칸에 쓰는 묶음 키를 "`rule_code`, 없고 조기 경보면 `"early_warning"`"으로 바꾸고, `ingest`가 같은 키로 `store.open_case`를 부른다. 그러면 조기 경보는 조기 경보끼리, 모델 단독 critical은 그것끼리 묶인다. `cases.code`는 `open_case`만 읽는다(11-08 확인).
3. **목록 필드(추가만)**: `summary()`의 `event`에 `event_type`(없으면 `"critical"`)을 더한다. `/api/history` 항목에 `repeat_event_ids`(케이스의 `repeats`에 든 `event_id` 목록)를 더한다.
4. **(2단계 때)** 케이스를 닫을 때 그 순간의 현장 기억 적용 여부(R1·R2)를 `closure`에 함께 저장한다(9.6).

- 1·2는 조기 경보 핸드오프(`RSW_EARLY_WARNING_HANDOFFS`, 기본 꺼짐)를 켰을 때만 동작이 달라진다. 3은 응답에 필드가 늘 뿐이다. 셋 다 `FIELD_MEMORY`와 무관한 일반 변경이다.

### 11.2 FE 요청 (`ml/docs/feedback-loop-requests.md`, 새 파일)

1단계를 막는 요청은 없다. 루프는 지금 화면 그대로 돈다.

1. `event_type`이 `early_warning`인 케이스를 "조기 경보 · 확정 아님"으로 보여 주기. 11.1 뒤에는 `severity`가 "주의"로 보이지만, 문구는 여전히 "코드 없음 · 새 고장"이다(11-08 화면 점검).
2. 조기 경보 케이스 닫기 선택지: "이상 없음(오알람)" + 사유 칩, "이상 찾아 조치함". 뒤쪽은 지금의 해결 종료로 저장해도 된다(루프는 해결 종료를 조치함으로 읽음). 해결 종료가 일지 승인을 요구하는 지금 흐름(`api/main.py:358-359`, 409 "log not approved")이 조기 경보에 맞는지는 FE가 판단한다.
3. 오알람 사유 칩 4종을 팀이 확정하면 알려 주기. 루프의 사유 표(7.7)를 같이 고친다.

- **넓은 손실 한도**: `MARGIN` 0.120은 재학습 잡음이라 넓다. "덜 울림"에 CI 상한 조건과 고정 기준점을 더해 놓침이 통계적으로 늘어나는 지점에서 멈추게 했다(7.4).
- **프로필의 위험은 재지 못했다**: 데이터에 잘못 뺄 기회가 없었다(3.2). 오클릭 1번을 견디는 2건으로 정했고, 제안마다 위험 문장을 붙인다. 반영은 사람이 한다.
- **시뮬레이션 라벨**: 실행 ①은 고리가 도는 모습이지 성능이 아니다. 보고서와 history.md에 그렇게 적는다.
- **새 평가기의 버그**: 실험실 대조 시험(성공 기준 3)이 B-18과 같은 답을 내는지로 막는다.
- **창 기록 디스크**: 건당 하루 1~2 MB이고 1단계에는 정리가 없다.
- **사유 칩 변경**: 칩이 바뀌면 7.7 표를 고쳐야 한다.
- **두 고리의 같은 라벨**: 1단계는 보고서만이라 자동 증폭은 없다. 2단계에서 학습에 쓰기 전에 9.6을 지킨다.
- **api 변경**: 조기 경보 핸드오프를 켠 기존 DB에서는 조기 경보 케이스가 예전 묶음(`code` 비어 있음)에 남아 있다. 새 조기 경보는 새 묶음으로 간다. 데모 DB뿐이라 옮기지 않는다.
