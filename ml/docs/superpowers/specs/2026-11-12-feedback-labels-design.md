# D-12 사람 판정 반영: 정답 · 오답 재정의 설계

2026-11-12 · ML (+ api 읽기 주소 하나) · 상태: 사용자 승인 (11-12), 구현 · 실제 확인 (11-13, `results/D-12/runs/check-1/`), 검토 반영 (11-13: 판정 구간의 시작 = 경보가 시작된 창, 4절), 사소한 지적 반영 (11-13: 5 · 6 · 8절)

D-11 모델 루프(`2026-11-11-model-loop-design.md`)에 얹는 설계다. 아키텍처 그림의 ML 피드백 루프 12번 칸에 해당한다.

## 1. 목표

작업자가 화면에서 조기 경보 케이스를 닫으며 남긴 판정(해결 · 오알람)을 ML 루프의 다음 재학습과 A/B 판정에 넣고, 무엇을 넣었는지 기록으로 남긴다.

지금의 문제:

- ML의 정답은 전부 데이터에서 나온다. 경보 뒤 10~60분 안에 종료 코드가 뒤따르면 적중, 고장 60분보다 앞선 경보는 오알람, 그 구간은 정상이다.
- 작업자가 경보를 보고 제때 고치면 종료 코드가 나오지 않는다. 그러면 가장 쓸모 있었던 경보가 오알람으로 세어지고, 그 구간이 정상 데이터로 학습된다.

성공 기준(사용자 결정 11-12): **경로가 작동하면 성공이다.** 성능이 좋아졌다는 측정이나 주장은 하지 않는다.

1. api에서 "해결"로 닫고 점검에 이상을 남긴 조기 경보 케이스가, `feedback pull` 뒤의 다음 학습에서 정상 데이터에서 빠지고, 그 버전의 기록에 "사람 판정 n건 반영"이 남는다.
2. 그 파일이 섀도 파일에 들면 A/B 판정 기록에 판정 반영 전 수치와 반영 후 수치가 둘 다 남고, 교체 여부는 반영 후 수치로 정해진다.
3. 판정이 하나도 없으면 학습 결과와 판정 결과가 지금과 완전히 같다. 기존 ml 테스트 183개가 통과하고 `ruff check .`에 새 오류가 없다.
4. api의 기존 응답은 하나도 바뀌지 않는다. 기존 api 테스트가 통과한다.

용어:

| 말 | 뜻 |
|---|---|
| 케이스 | api가 같은 설비의 경보를 묶은 것. 대표 경보 하나와 반복 경보 여러 개 |
| 사람 판정 | 닫힌 케이스 하나에서 ML이 읽어 낸 결론: 이상 확인 / 오알람 / 모름 / 못 맞춤. 이 문서에서 그냥 "판정"이라고 하면 이것이다 |
| A/B 판정 | D-11의 판정. 지금 모델과 도전자를 섀도 파일로 비교해 교체 여부를 정하는 것 |
| 판정 구간 | "이상 확인" 케이스에서 정상으로 치지 않기로 한 시간 구간 |
| 판정 저장 파일 | 등록부 폴더의 `feedback.json`. api에서 가져온 케이스 사실을 쌓는다 |

범위 밖:

- 성능 향상의 측정. 재생 데이터는 작업자가 무엇을 누르든 기록된 고장이 그대로 일어나므로 실제 판정으로는 보일 수 없다.
- 판정 구간을 양성 예시(고장 직전과 같은 취급)로 학습하는 것. 실제 현장 판정이 쌓인 뒤의 후속 과제다(11절).
- 서버가 받은 센서 값을 학습 파일로 쌓는 것. 지금처럼 파일로 넣는다.
- `ui/`, `rag/` 코드 변경. Neo4j에서 읽는 것.
- E 코드(CRITICAL) 케이스. 종료 코드 자체가 정답이다.

## 2. 판정이 흐르는 길

```
서버(/predict) ─ 조기 경보 핸드오프 → api ─ 화면에서 종료(해결 · 오알람)
                                          │
                              GET /api/ml/feedback   (새 주소, 읽기 전용)
                                          │
              model_loop.py feedback pull --api-url …   (새 명령)
                                          │
                        <등록부>/feedback.json   (판정 저장 파일)
                                          │
                    tick: 학습과 판정에 판정 구간을 넘김, 기록
```

- 루프는 판정 저장 파일만 읽는다. api가 꺼져 있어도 점검은 그대로 돈다.
- 판정이 재학습에 닿으려면, 서버에 흘린 스트림의 `gun_id`가 루프가 학습하는 전처리 파일의 이름과 같아야 한다. `replay.py`는 파일 이름을 `gun_id`로 쓰므로, 루프에 들어갈 파일을 그대로 흘리면 된다. test 파일을 흘려 얻은 판정은 "못 맞춤"이 된다.
- 경보의 시각(`onset_at`, 없으면 `window_start`. 4절)은 센서 값의 시각(데이터 시각)이다. 핸드오프는 `Z`가 붙은 UTC, 전처리 파일은 시간대 없는 UTC라서, 시간대 표시만 떼고 그대로 비교한다. 종료 시각(`closed_at`)은 실제 시각이라 구간 계산에 쓰지 않는다.

## 3. api: `GET /api/ml/feedback`

새 파일 `api/ml_feedback.py`에 둔다(`APIRouter`). `api/main.py`에는 가져오기와 등록 두 줄만 더한다. 기존 주소의 응답은 바꾸지 않는다. `api/store.py`에는 전송 기록을 한 번에 읽는 함수 하나(`warning_deliveries`)를 더한다(11-13, 사용자 허락. 닫힌 케이스마다 DB를 열지 않기 위해서다).

닫힌 조기 경보 케이스의 **사실만** 내준다. 정답인지는 ML이 정한다.

대상: `event.event_type == "early_warning"`이고 `records.closure.outcome`이 `resolved` 또는 `false_alarm`인 케이스.

```json
{
  "schema_version": "1.0",
  "items": [
    {
      "case_id": "CASE-0007",
      "outcome": "resolved",
      "closed_at": "2026-11-12T08:00:00+00:00",
      "resolution_status": "saved",
      "selected_event_id": "11a9ca71eaa03037b93f5787ea797152",
      "checks": {"abnormal": 1, "normal": 2, "unchecked": 0},
      "events": [
        {"event_id": "11a9…", "representative": true, "gun_id": "E01_3",
         "window_start": "2021-09-01T10:00:00Z", "onset_at": "2021-09-01T10:00:59Z",
         "detected_at": "2021-09-01T10:00:59Z",
         "detector_created": "2026-11-01T18:46:47"}
      ]
    }
  ]
}
```

| 필드 | 출처 | 비고 |
|---|---|---|
| `outcome`, `closed_at` | `records.closure` | |
| `resolution_status` | 케이스의 `warning_resolution_status` | `saved` / `pending` / `not_linked` 등. 없으면 `null`. ML은 기록만 한다 |
| `selected_event_id` | `/warning/resolve`로 닫을 때 고른 경보(`warning_outbox`) | 예전 `/close` 경로면 `null` |
| `checks` | `records.checks`와 고른 경보의 점검 초안을 합쳐 값별 개수 | 두 곳의 값 형식이 다르다(`{"result": "abnormal"}` / `"abnormal"`). 둘 다 읽는다 |
| `events` | 대표 경보(`event`)와 `repeats[].handoff` | 원본이 없는 옛 반복 경보는 `event_id`와 `detected_at`만. `onset_at`은 핸드오프의 `early_warning.onset_at`(경보가 시작된 창의 마지막 초)이고 없으면 `null`이다(11-13 검토에서 더함) |

## 4. 사람 판정 규칙 (ML)

케이스 하나에서 판정 하나를 낸다. 순수 함수로 두고 표 그대로 테스트한다.

1. **경보 고르기**: `selected_event_id`가 있으면 그 경보, 없으면 대표 경보. 케이스당 경보 하나만 쓴다(사용자 결정 11-12). 반복 경보마다 구간을 빼면 설비당 하루 최대 24번이라 하루치 정상 데이터가 통째로 빠질 수 있다.
2. **파일 맞추기**: `gun_id`와 이름이 같은 전처리 파일이 있고 경보의 시각(`onset_at`, 없으면 `window_start`)이 그 파일의 시작~종료 시각 안이면 맞춘 것이다. 아니면 **못 맞춤**.
3. **결론**:

| 판정 | 조건 | 루프에서 하는 일 |
|---|---|---|
| 이상 확인 | `outcome == resolved`이고 `checks.abnormal >= 1` | 판정 구간을 정상에서 뺀다 |
| 오알람 | `outcome == false_alarm` | 기록만. 지금도 오알람이자 정상으로 계산된다 |
| 모름 | `resolved`인데 이상 점검이 없음 | 기록만, 쓰지 않는다 |
| 못 맞춤 | 2번에서 맞추지 못함 | 기록만, 쓰지 않는다 |

- `resolution_status`(Aura 연결 상태)는 조건이 아니다. 예전 `/close` 경로로 닫은 건도 점검에 이상이 있으면 이상 확인이다.
- **판정 구간** = 고른 경보가 시작된 창부터 `FEEDBACK_SPAN_S`(기본 3600초). 서버가 같은 설비의 조기 경보를 다시 보내는 간격과 같다.
- 구간의 시작은 `onset_at`(경보가 시작된 창의 마지막 초)이고, api가 주지 않으면 `window_start`다. 한 요청에 창이 여럿이면 `window_start`는 그 요청의 마지막 창이라 경보가 시작된 창보다 뒤일 수 있다. 두 값 모두 행의 시각이고 학습의 창은 분 단위 이름(`10:00`)으로 불리므로, `train.py`가 구간의 양 끝을 창 크기로 내림한다. 그래야 경보가 난 그 창이 구간의 첫 창이 된다. (11-13 검토에서 고침. 처음 구현은 `window_start`를 그대로 써서, 그 시각이 `:00`이 아니거나 한 요청에 창이 여럿이면 경보가 난 창이 정상으로 남고 그 경보가 오알람으로 계속 세어졌다.)
- 같은 케이스가 다시 닫혀 내용이 바뀌면 나중 것이 이긴다. 저장 파일의 열쇠는 대표 경보의 `event_id`다(화면 번호 `CASE-0001`은 api마다 겹칠 수 있다).

## 5. "정상에서 뺀다"가 적용되는 곳 (`train.py`)

`train.py`에 `--feedback <json>`을 더한다. 내용은 파일별 구간이다.

```json
{"confirmed":   {"E01_3": [["2021-09-01T10:00:00", "2021-09-01T11:00:00"]]},
 "false_alarm": {"E02_1": [["2021-09-03T04:00:00", "2021-09-03T05:00:00"]]}}
```

구간의 양 끝을 창 크기로 내림하고, 창을 만든 직후(학습과 `--evaluate` 양쪽) 창 시작 시각이 `confirmed` 구간에 드는 창에 `confirmed = 1` 열을 붙인다. 이 열을 읽는 곳은 네 군데다.

| 곳 | 지금 | 바뀌는 것 |
|---|---|---|
| 학습의 정상 데이터 (`fit_and_eval`) | `label == 0`이고 `error_active == 0` | 여기에 `confirmed == 0` |
| 조기 경보 임계값의 기준 창 (`early_warning_population`) | 코드 없음, 워밍업 아님, 고장에서 멀리 | 여기에 `confirmed == 0` |
| 평가의 정상 창 (`evaluate`의 `normal`) | AUROC의 음성, 정상 알림 비율 | 여기에 `confirmed == 0`. 고장 전 창도 정상 창도 아닌 창이 된다 |
| 조기 경보 오알람 (`early_warning_metrics`) | 고장 60분보다 앞선 경보 시작과 감시 일수 | `confirmed` 창의 경보 시작과 그 시간을 뺀다 |

바뀌지 않는 것:

- 고장 전 창(`label == 1`)과 적중 구간(고장 10~60분 전). 원래 정상이 아니므로 판정이 와도 같다.
- 종료 코드 규칙의 수치, 알림 구간(run) 통계, 운영점. 루프의 판정이 읽지 않는 수치다.
- `--feedback`이 없거나 구간이 비면 열을 붙이지 않는다. 결과가 지금과 완전히 같다. `--feedback`이 없으면 번들에 적는 인자(`args`)에도 `feedback` 키를 남기지 않는다.

`false_alarm` 구간은 계산을 바꾸지 않는다. 세기만 한다.

결과 JSON에 `feedback` 블록을 더한다.

```json
"feedback": {"spans": 1, "windows_excluded": 58, "windows_already_not_normal": 2, "false_alarm_conflicts": 0}
```

- `spans`: 읽은 파일에 걸린 `confirmed` 구간 수. 읽지 않은 파일의 구간은 세지 않는다.
- `windows_already_not_normal`: 구간 안이지만 원래 정상이 아니던 창(고장 전, 코드 발생).
- `false_alarm_conflicts`: 오알람이라 했는데 데이터에서는 경보가 난 그 창(구간의 첫 창)이 적중 구간(고장 10~60분 전)에 든 구간 수. 데이터를 따른다. 구간의 뒤쪽만 적중 구간에 걸친 경우는 세지 않는다: 그 경보 뒤 한 시간 안에 고장이 뒤따른 것이 아니다.

`--evaluate`에 `--feedback`을 주면 채점은 한 번 하고 집계를 두 번 낸다: `test`(반영 후)와 `test_no_feedback`(반영 전).

## 6. 루프 (`model_loop.py`, `model_registry.py`)

### 6.1 판정 저장 파일과 명령

`<등록부>/feedback.json`:

```json
{"schema_version": 1, "source": "http://localhost:9000", "pulled_at": "2026-11-12T09:00:00Z",
 "cases": {"<대표 event_id>": {…api가 준 항목…, "received_at": "…"}}}
```

- `model_loop.py feedback pull --api-url URL`: `GET /api/ml/feedback`을 읽어 저장 파일에 합친다. 같은 열쇠는 최신 내용으로 바꾸고, api가 더는 주지 않는 건은 남긴다. 임시 파일에 쓰고 바꿔치기한다. 등록부 잠금을 잡는다. 새로 들어온 건수와 바뀐 건수를 출력한다.
- `model_loop.py status`에 판정 한 줄을 더한다: 저장된 케이스 수와 판정별 건수.
- 등록부 폴더는 git이 무시하므로 저장 파일도 올라가지 않는다.

### 6.2 점검(tick)

- `tick`에 선택 인자 `feedback_fn`을 더한다(`notify_fn`과 같은 방식). 파일 이름 목록을 주면 그 파일들에 걸린 판정 구간과 건수를 돌려준다. 주어지지 않으면 지금과 똑같이 동작한다.
- **학습**: 그 버전의 학습 파일에 걸린 구간을 학습 함수에 넘긴다. 시드 모델도 같은 구간으로 학습한다.
- **A/B 판정**: 섀도 파일에 걸린 구간을 채점 함수에 넘긴다. 지금 모델, 도전자, 시드 모델을 모두 같은 구간으로 집계한다. 다섯 조건은 반영 후 수치로 본다(사용자 결정 11-12).
- **잠정 교체 확인**(D-11 6.1절)도 같은 방식으로 구간을 넘긴다.
- **사람 판정만으로는 학습하지 않는다.** 학습은 지금처럼 새로 끝난 파일이 `train_min_new`건 이상일 때만 일어나고, 그때까지 쌓인 판정이 함께 들어간다. 이미 등록된 버전은 다시 학습하지 않는다.
- 채점 결과의 캐시 열쇠에 구간을 넣는다. 구간이 달라지면 다시 채점한다(몇 분). 오알람 판정만 달라져도 다시 채점한다: 수치는 같지만 어긋남 건수(`false_alarm_conflicts`)는 데이터를 훑어야 셀 수 있어서, 예전 결과를 다시 쓰면 그 건수가 틀리게 남는다.
- 이어 하기: 폴더에 남은 학습 결과는 파일 목록과 구간이 둘 다 같을 때만 "이미 학습됨"으로 본다.

### 6.3 기록

버전 기록에 `feedback`을 더한다. 판정 저장 파일이 없으면 `null`이다.

```json
"feedback": {"confirmed": 1, "false_alarm": 3, "unknown": 2, "unmatched": 4,
             "spans": 1, "windows_excluded": 58, "false_alarm_conflicts": 0,
             "event_ids": ["11a9…"]}
```

- `confirmed` / `false_alarm` / `unknown`: 그 버전의 학습 파일에 맞춰진 판정.
- `unmatched`: 저장 파일 전체에서 어느 전처리 파일에도 맞지 않은 판정.
- `event_ids`: 구간으로 쓴 경보.

A/B 판정 기록과 잠정 확인 기록에는 같은 모양의 `feedback`(섀도 파일 기준)과 `values_before`(반영 전 수치)를 더한다. 기존 `values`와 `checks`는 반영 후 수치다. 구간이 없으면 `values_before`는 `null`이다. 반영 전 수치로 냈을 결론도 함께 남긴다: A/B 판정에는 `swap_before`, 잠정 확인에는 `revert_before`. 사람 판정이 결론을 바꾼 경우가 이 둘로 드러난다(7절). 반영 전 수치로는 우연 폭을 낼 수 없으면(시드 모델의 반영 전 수치가 없음) 결론을 지어내지 않고 `null`로 둔다.

- 보고서(`report`)에 "사람 판정" 절을 더한다: 버전별 반영 건수, A/B 판정별 · 잠정 교체 확인별 반영 전후 수치. 어느 파일에도 맞은 판정이 없으면 표 대신 한 문장으로 적는다.
- `GET /model/loop`는 버전 기록과 최근 판정을 그대로 돌려주므로 새 필드가 함께 보인다(더하기만).
- 설정에 `feedback_span_s`(기본 3600)를 더한다. 이 값이 없는 예전 등록부는 3600으로 읽는다.

## 7. 알려진 한계: 사람 판정은 지금 모델 쪽으로 기운다

사람 판정은 지금 모델(A)이 경보를 낸 구간에만 생긴다. 도전자(B)는 경보를 보내지 않으므로 판정을 받을 기회가 없다.

- A의 오알람은 "이상 확인"을 받으면 오알람 집계에서 사라진다. B가 다른 시각에 낸 오알람은 실제 이상이었더라도 그대로 남는다.
- AUROC에서도 A가 높은 점수를 준 정상 구간만 빠지므로 A 쪽이 올라간다.
- 그래서 사람 판정이 쌓일수록 A/B 판정이 "유지"로 기운다.
- 잠정 교체 뒤의 확인에서는 방향이 반대다. 그 기간에 서빙하는 것은 새로 올린 모델이므로 판정은 새 모델의 경보에만 생기고, 확인이 "확정" 쪽으로 기운다. 어느 쪽이든 그때 서빙 중인 모델에 유리하다.

대응: A/B 판정 기록에 반영 전과 후 수치를 둘 다 남겨, 사람 판정이 결과를 바꾼 경우가 드러나게 한다. 치우침 자체는 없애지 않는다. 없애려면 도전자의 경보도 사람에게 보여야 하는데, 이는 섀도 비교(D-11 사용자 결정)의 범위를 넘는다.

## 8. 실패 처리

| 상황 | 동작 |
|---|---|
| `feedback pull` 때 api가 응답하지 않음 | 오류로 끝난다. 저장 파일은 그대로다 |
| 항목에 필요한 값이 없음(경보 시각 등) | 그 항목은 "못 맞춤"으로 센다 |
| 저장 파일이 깨져 읽을 수 없음 | 점검이 오류로 멈춘다. 판정 없이 조용히 학습하지 않는다 |
| 저장 파일이 없음 | 판정 없이 지금과 똑같이 동작한다 |
| 구간이 파일 범위와 일부만 겹침 | 겹친 창만 뺀다 |
| 저장 파일의 케이스 하나가 객체가 아님(손으로 고친 파일) | 파일 경로와 그 열쇠를 적은 오류로 멈춘다 |
| 항목의 이상 점검 수가 숫자가 아님 | 이상 점검이 없는 것으로 읽어 "모름"으로 센다 |
| 저장 파일이 깨진 채 `status`를 부름 | 등록부 상태를 먼저 보이고, 그 뒤 오류로 끝난다 |
| 버전 폴더의 `feedback.json`을 읽을 수 없음(쓰다 끊김) | 끝난 학습으로 보지 않고 그 버전을 다시 학습한다 |
| api에 읽을 수 없는 케이스가 저장돼 있음 | api가 그 케이스만 건너뛰고 로그에 남긴다. 나머지는 그대로 준다 |

## 9. 테스트

실제 데이터 폴더(`train/`, `test/`, `preprocessed/`)는 건드리지 않는다.

| 대상 | 내용 |
|---|---|
| 판정 규칙 (ml 단위) | 이상 확인 / 오알람 / 모름 / 못 맞춤, 고른 경보와 대표 경보, 구간 길이, 시간대 표시, 구간의 시작(`onset_at`, 창 크기로 내림) |
| 저장 파일과 `feedback pull` (ml 단위) | 가짜 응답으로 새 건 · 바뀐 건 · 같은 건, api 오류 때 파일 그대로 |
| `tick` (ml 단위) | 구간이 학습 · 채점 함수에 넘어가고 기록에 남음. `feedback_fn`이 없으면 기록이 지금과 같음. 판정만으로는 학습하지 않음. 구간이 달라지면 "이미 학습됨"이 아님. 판정 기록의 `values_before`. 채점 함수가 구간을 `train.py`에 넘기고 반영 전 수치를 돌려줌(가짜 `train.py`) |
| `train.py` (합성 데이터) | `--feedback` 유무에 따라 정상 창 수가 구간만큼 줄어듦. 조기 경보 오알람 수가 줄어듦. 구간이 비면 결과 JSON이 같음. `test_no_feedback` 블록 |
| 보고서 · `status` · `/model/loop` | 새 절과 새 필드 |
| api | 새 주소: 해결(이상 점검 있음 / 없음), 오알람, E 코드 케이스 제외, 열린 케이스 제외, 두 가지 점검 값 형식 |

실제 확인 한 번(사람 손으로):

1. 새 등록부 폴더(`models/registry-d12`)를 쓴다. 기존 `models/registry`는 건드리지 않는다.
2. 첫 모델의 학습 파일 16건 중 하나를 서버에 흘려 조기 경보를 만든다(지금 서빙 모델 사용).
3. api는 임시 DB(`API_DB`)로 띄운다. 케이스에 이상 점검을 남기고 예전 `/close` 경로로 "해결" 종료한다. **`/warning/resolve`는 쓰지 않는다**: 팀이 함께 쓰는 Aura 이력에 가짜 해결 기록이 들어가기 때문이다. Claude 호출도 하지 않는다.
4. `feedback pull` 뒤 `replay --end 2021-09-07`로 첫 모델을 학습한다(학습 한 번, 약 5분).
5. v001 기록에 "사람 판정 1건 반영"이 남고 `windows_excluded`가 0보다 큰지 본다. 같은 파일 · 같은 시드로 판정 없이 학습한 replay-1의 v001과 임계값이 어떻게 다른지도 적는다.

실제 확인은 성공 기준 1(학습 쪽)만 본다. 성공 기준 2(A/B 판정의 반영 전후 수치)는 자동 테스트로 확인한다. 실제 데이터로 보려면 섀도 판정까지 재생해야 해서 학습이 여러 번 더 든다.

대조 실험(11-13, `results/D-12/runs/control-1/`): 실제 확인에서 판정 1건이 임계값을 크게 움직인 것이 그 한 시간 때문인지 보려고, 경보와 관계없는 정상 한 시간을 같은 수만큼 빼고 첫 모델을 세 번 다시 학습했다. 세 번 모두 비슷한 크기로 움직였다. 판정 1건의 변화는 아무 창 60개를 뺄 때의 흔들림과 구별되지 않는다.

api를 외부 서비스 없이 띄울 수 없으면 `api/tests/warning_demo_server.py`를 쓴다. 이 점은 구현 계획에서 먼저 확인한다.
