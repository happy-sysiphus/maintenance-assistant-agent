# D-11 모델 루프: 재학습 · 섀도 비교 · 자동 교체 설계

2026-11-11 · ML · 상태: 사용자 승인 (11-11)

## 1. 목표

같은 라인에서 새로 쌓인 데이터로 모델을 다시 학습하고, 지금 쓰는 모델과 비교해, 더 나으면 서빙 모델을 자동으로 바꾼다.

- 예: 2주 데이터로 모델 A를 배포한다. 1주가 더 쌓이면 3주 데이터로 모델 B를 학습한다. A와 B를 비교해 B가 나으면 B로 바꾼다. '주'는 예시이고, 자르는 간격은 설정값이다.
- 지금은 실제 라인이 없으므로 기존 데이터를 시간순으로 재생해 이 과정을 돌린다.
- 재생이 끝난 뒤에도 새 파일이 들어오면 같은 루프가 이어서 동작한다.

용어:

| 말 | 뜻 |
|---|---|
| 현재 모델(A) | 서빙 서버가 알림을 내는 모델 |
| 도전자(B) | 새로 학습했고 아직 알림을 내지 않는 모델 |
| 섀도 비교 | A와 B가 둘 다 처음 보는 같은 파일을 채점해 비교하는 것. B의 알림은 나가지 않는다 |
| 끝난 파일 | 종료 시각이 점검 시각 이전인 전처리 파일. 고장 라벨은 파일이 끝나야 알 수 있다 |
| 점검(tick) | 루프를 한 번 부르는 것. 한 번 부르면 점검 한 번이다 |

이 설계의 'A/B 테스트'는 섀도 비교(챔피언–도전자)다. 설비 일부에 B를 실제로 적용하는 방식이 아니다(사용자 결정 11-11).

성공 기준(사용자 결정 11-11): 루프가 자동으로 돌고 판정 근거가 남으면 성공이다. 모델이 좋아지는지는 보고하되 보장하지 않는다. 모든 판정이 'A 유지'로 끝나도 실패가 아니다.

1. 실제 데이터 64건의 재생이 점검 사이에 사람 손 없이 끝나고, 보고서에 점검마다 한 일, 판정마다 다섯 조건의 수치와 통과 여부, 테스트 8건 비교표가 있다.
2. 등록부를 쓰는 서버가 켜져 있을 때 교체 판정이 나면, 서버를 다시 시작하지 않아도 `/model/loop`와 `/health`가 새 버전을 보이고 `/predict`가 계속 동작한다.
3. 새 데이터가 없을 때의 점검은 아무것도 바꾸지 않는다. 중간에 끊긴 실행은 다시 부르면 이어진다.
4. `RSW_MODEL_REGISTRY`를 지정하지 않은 서버는 지금과 똑같이 동작한다. 기존 `pytest` 85개가 통과하고 `ruff check .`에 새 오류가 없다.

범위 밖(13절에 후속 과제로 적는다):

- 서버가 `/predict`로 받은 스트림을 저장해 학습 파일로 만드는 것.
- 교체 직후 워밍업 동안 옛 모델로 알림을 유지하는 것.
- api · 화면에 모델 버전과 판정 이력을 보이는 것. `api/`, `rag/`, `ui/` 코드는 바꾸지 않는다.
- 학습 레시피(모델 구성, 피처, 조기 경보 규칙)를 바꾸는 것.

## 3. 점검 한 번의 규칙

점검 시각 `now`를 받는다. 재생에서는 가상 시각이고, 운영에서는 실제 시각이다. `now`는 마지막 점검 시각보다 앞설 수 없다.

끝난 파일 = `manifest.csv`에서 빠지지 않았고 `end <= now`인 파일.

순서대로 한다.

1. 현재 모델이 없다.
   - 끝난 파일이 `INITIAL_MIN_FILES`건 이상이면 끝난 파일 전체로 첫 모델을 학습해 현재 모델로 둔다. 그리고 이 점검을 끝낸다.
   - 모자라면 아무것도 하지 않는다.
2. 도전자가 있다.
   - 섀도 파일 = 끝난 파일 중 도전자의 학습 파일에 없는 것. 재생에서는 `end`가 도전자의 학습 시점보다 뒤인 파일과 같다. 운영에서는 학습 시점 전에 끝났지만 그 뒤에 들어온 파일도 센다(두 모델 다 본 적이 없다. 최종 검토 뒤 정함, 11-12).
   - 섀도 파일이 `SHADOW_MIN_FILES`건 이상이면 판정한다(5절). 교체면 현재 모델을 바꾸고 서버에 알린다(8.4절). 유지면 도전자를 버린다. 어느 쪽이든 도전자 자리는 빈다.
   - 모자라면 판정을 다음 점검으로 미룬다. 3번으로 가지 않는다.
3. 도전자가 없다.
   - 새 파일 = 끝난 파일 중 가장 최근에 학습한 버전(채택 여부와 무관)의 학습 파일에 없는 것.
   - 새 파일이 `TRAIN_MIN_NEW`건 이상이면 끝난 파일 전체로 도전자와 시드 모델을 학습한다(4절).

규칙에서 나오는 성질:

- 도전자는 한 번에 하나다.
- 학습은 누적이다. 버전마다 그 시점까지 끝난 파일 전체를 쓴다.
- 섀도 파일은 A와 B 둘 다 학습에 쓰지 않은 파일이다. A의 학습 시점이 B보다 앞이기 때문이다.
- 같은 `now`로 다시 부르면 아무것도 바뀌지 않는다.

## 4. 학습

`train.py`를 별도 프로세스로 부른다. 운영 번들(`models/baseline_ensemble.joblib`, 2026-11-01)과 같은 레시피다.

```
--model ensemble --ensemble-components iforest,lgbm --lgbm-weight 0.5 --window 60 --val-frac 0.25
--threshold-q 0.99 --sustain 3 --critical-sustain 10 --restart-hold-min 30 --restart-idle-windows 30
--alarm-max-non-welding 0.5 --exclude-non-welding --drop-features c19 --gun-norm center --warmup-hours 6
--cv 4 --early-warning-rule model_ng_k1 --early-warning-q 0.975 --early-warning-cooldown-min 60 --seed 42
```

- 버전 모델: 위 레시피에 `--files-from`(8.3절)과 `--no-test`, `--model-dir <버전 폴더>`를 더한다. 서버가 그대로 읽는 번들이 나온다.
- 시드 모델: 우연 폭을 재는 데만 쓴다. 건별 AUROC만 필요하므로 `--cv`를 빼고 `--no-early-warning`을 더해 `--seed 43`, `--seed 44`로 학습한다. 도전자를 학습할 때 같이 학습한다. 첫 모델에는 만들지 않는다.
- 시드는 모델 난수와 학습 내부의 검증 분할(25%)을 함께 바꾼다. 둘 다 '같은 데이터로 다시 학습하면 달라지는 정도'에 들어간다.
- 레시피는 학습 파일의 25%를 검증용으로 떼고 나머지로 학습한다. 이 방식을 그대로 둔다. v001은 16건 중 12건으로 학습한다.

## 5. 판정

A, B, 시드 모델 둘을 같은 섀도 파일로 채점한다(`train.py --evaluate`, 8.3절). `evaluate`가 이미 내는 값만 쓴다.

| 값 | 출처 |
|---|---|
| 건별 AUROC 평균 | `auroc_gun_mean` |
| 파일별 AUROC | `per_file[파일]["auroc"]` |
| 조기 경보 적중 건수 | `early_warning.per_file[파일]["hit"]`의 합(값이 없는 파일은 뺀다) |
| 조기 경보 오알람 | `early_warning.false_alarms_per_gun_day` |

다섯 조건을 모두 만족하면 교체한다. 하나라도 어기면 A를 유지한다.

1. `AUROC(B) - AUROC(A) > 우연 폭`. 우연 폭 = B(시드 42)와 시드 모델 둘, 이 셋의 건별 AUROC 평균에서 두 개씩 뺀 차이의 절댓값 중 가장 큰 값.
2. 파일별 AUROC가 둘 다 있는 섀도 파일 중 `B >= A`인 파일이 절반보다 많다.
3. B에 조기 경보가 있고, B의 조기 경보 적중 건수가 A 이상이다.
4. B의 조기 경보 오알람이 A의 `FA_RATIO_MAX`배 이하다.
5. B의 조기 경보 오알람이 `FA_CAP` 이하다.

값이 없을 때:

- A나 B의 건별 AUROC 평균이 없으면(섀도 파일에 고장 전 윈도우가 없는 경우 등) 교체하지 않고 사유를 '판정 불가'로 남긴다.
- 조기 경보가 꺼진 번들은 적중 0건, 오알람 0으로 본다. A의 조기 경보가 꺼져 있으면 4번은 건너뛴다(통과로 기록하고 사유를 적는다).
- 서빙 모델에는 조기 경보가 반드시 있다(사용자 결정 11-12). B의 조기 경보가 꺼져 있으면 3번은 실패다. A의 적중이 0건이어도, A의 조기 경보가 꺼져 있어도 같다. 조기 경보가 없는 버전은 등록부에 들어가지도 않으므로(9절), 이 경우는 이 규칙 전에 만든 등록부에서만 생긴다.

판정 기록에는 다섯 조건 각각의 입력값, 통과 여부, 최종 결과, 사유 문장을 남긴다. 판정은 숫자만 받는 함수 하나로 두고 채점 · 등록부와 분리한다.

2 · 4번은 분기 세션 검토에서 나온 보강이다(사용자 결정 11-11). 1번만으로는 섀도 파일 수가 적어 생기는 흔들림을 못 걸러서 2번을 넣었다. 3 · 5번만으로는 알림을 많이 내는 모델이 유리해서 4번을 넣었다.

## 6. 되돌리기

`model_loop.py rollback`은 현재 모델을 바로 앞의 현재 모델로 되돌리고 서버에 알린다. `--to v00N`으로 물러났거나 떨어진 버전을 지정할 수 있다. 지금의 도전자는 판정을 거치지 않았으므로 받지 않는다. 도전자가 있으면 그대로 두고, 다음 판정은 되돌린 모델과 한다. 등록부 이력에 `rollback`으로 남는다. 사람이 부르는 명령이고, 루프가 스스로 되돌리지는 않는다.

## 7. 테스트 8건

판정에 쓰지 않는다(사용자 결정 11-11). 판정에 반복해서 쓰면 모델이 그 8건에 맞춰지고, 8건의 날짜가 학습 파일과 섞여 있어(2019-12 ~ 2021-10) '미래 데이터'도 아니기 때문이다.

`model_loop.py report`가 모든 버전을 테스트 8건으로 채점해 표로 남긴다. 채택되지 않은 도전자와 '대기' 도전자도 포함한다. 첫 모델과 마지막 현재 모델의 차이를 따로 한 줄로 적는다. 채점 결과는 버전 폴더에 저장해 다시 계산하지 않는다.

### 8.1 모델 등록부

```
models/registry/
  registry.json
  v001/  baseline_ensemble.joblib · baseline_ensemble_metrics.json · test_metrics.json
  v002/  (위와 같음) + seeds/s43/ · seeds/s44/
```

`registry.json`:

```json
{
  "schema": 1,
  "config": {"initial_min_files": 16, "train_min_new": 5, "shadow_min_files": 5, "seeds": [42, 43, 44],
             "fa_ratio_max": 1.2, "fa_cap": 24.0, "recipe": ["--model", "ensemble", "..."]},
  "last_tick": "2021-09-20T00:00:00",
  "champion": "v002",
  "challenger": "v003",
  "versions": {
    "v002": {"cutoff": "2021-09-13T00:00:00", "train_files": ["E01_0", "..."], "seed": 42,
             "created": "2026-11-12T10:03:11", "status": "champion"}
  },
  "decisions": [
    {"at": "2021-09-20T00:00:00", "champion": "v001", "challenger": "v002", "shadow_files": ["E02_9", "..."],
     "values": {"auroc_a": 0.0, "auroc_b": 0.0, "noise": 0.0, "files_b_ge_a": 0, "files_compared": 0,
                "hits_a": 0, "hits_b": 0, "fa_a": 0.0, "fa_b": 0.0},
     "checks": {"auroc_margin": true, "file_majority": true, "ew_hits": true, "fa_ratio": true, "fa_cap": true},
     "swap": true, "reason": "다섯 조건을 모두 만족"}
  ],
  "history": [{"at": "2021-09-20T00:00:00", "champion": "v002", "by": "decision"}]
}
```

(위 숫자는 형식을 보이는 자리표시이고 결과가 아니다.)

- 버전 상태는 `champion`, `challenger`, `retired`(교체되어 물러남), `rejected`(판정에서 떨어짐) 넷이다. 버전 폴더는 지우지 않는다.
- `cutoff`는 학습한 점검 시각이고, `created`는 번들이 만들어진 실제 시각이다(서버와 핸드오프의 `detector.created`).
- 쓰기는 임시 파일에 쓴 뒤 바꿔치기한다. 판정 기록과 현재 모델 변경은 한 번의 쓰기로 같이 들어간다.
- 실행기는 한 번에 하나만 돈다. 시작할 때 잠금 파일을 만들고 끝날 때 지운다. 잠금 파일이 있으면 시작하지 않고 알려 준다.
- 버전은 번들 파일이 생기고 읽히는 것을 확인한 뒤에 등록한다.
- `config`가 등록부에 있는 값과 다르면 실행기는 시작하지 않는다. 설정을 바꾸려면 새 등록부를 쓴다.
- `models/registry/`는 실행 상태라 git에서 뺀다(`.gitignore`). 기록으로 남길 것은 보고서다(8.2절).

### 8.2 루프 실행기

```
py -3.11 .py/model_loop.py tick   [--now 2021-09-20T00:00:00] [--server-url http://localhost:8000]
py -3.11 .py/model_loop.py replay --start 2021-08-16 [--end ...] [--interval-days 7] [--server-url ...]
py -3.11 .py/model_loop.py report [--out results/D-11/runs/replay-1]
py -3.11 .py/model_loop.py status
py -3.11 .py/model_loop.py rollback [--to v001] [--server-url ...]
```

공통 인자: `--registry`(기본 `models/registry`), `--data-dir`(기본 `preprocessed`), 3절의 설정값. 기본 경로는 다른 스크립트처럼 `PROJECT_ROOT` 기준이다.

- `tick`: 3절의 점검 한 번. `--now`가 없으면 실제 시각이다. 운영에서는 스케줄러가 이 명령을 부른다.
- `replay`: `--start`부터 `--interval-days` 간격으로 `tick`을 되풀이한다. `--end`가 없으면 마지막 파일 종료 시각을 지난 첫 점검까지다. 등록부의 `last_tick`보다 뒤의 점검만 하므로, 끊긴 뒤 같은 명령을 다시 부르면 이어진다.
- `report`: 등록부와 7절의 테스트 채점으로 `report.json`과 `report.md`를 쓴다. 내용은 설정, 점검마다 한 일, 버전 표(학습 시점 · 파일 수 · 유형별 수), 판정 기록 전부, 테스트 8건 표다.
- `status`: 현재 모델, 도전자, 마지막 점검, 마지막 판정을 출력한다.
- 학습과 채점은 실행기 안에서 함수 두 개(`train_version`, `evaluate_version`)로 감싼다. 점검 로직은 이 둘을 인자로 받아, 테스트에서는 가짜 함수로 바꿔 넣는다.
- 채점 결과는 판정 폴더에 JSON으로 저장한다. 같은 버전 · 같은 파일 목록이면 다시 계산하지 않는다.
- `--server-url`이 있으면 교체나 되돌리기 뒤에 `POST /model/reload`를 부른다. 실패하면 경고만 남긴다. 등록부가 기준이고, 서버는 다음 reload나 다음 시작 때 따라온다.
- `--server-url`이 있으면 `tick`과 `replay`는 끝날 때에도 reload를 한 번 부른다(현재 모델이 있을 때). 서버가 이미 그 모델이면 아무 일도 없다. 교체 알림을 놓친 서버가 다음 점검에서 따라오게 하려는 것이다(최종 검토 뒤 정함, 11-12).

### 8.3 학습 스크립트

옵션 세 개를 더한다. 학습 · 평가 로직은 바꾸지 않는다.

| 옵션 | 동작 |
|---|---|
| `--files-from 경로` | 한 줄에 파일 이름 하나(`E01_0`). `--data-dir`의 `E0*.parquet` 전체 대신 이 파일들만 쓴다. 없는 파일이 있으면 멈춘다 |
| `--eval-files-from 경로` | `--evaluate`와 같이 쓴다. `--test-dir`의 `test_*.parquet` 대신 `--data-dir`의 이 파일들로 저장된 번들을 평가한다 |
| `--eval-out 경로` | `--evaluate`의 지표 JSON을 이 경로에 쓴다. 없으면 지금처럼 `<model-dir>/baseline_<model>_test_metrics.json`이다 |

옵션을 주지 않으면 지금과 같다.

### 8.4 서빙 서버

- `RSW_MODEL_REGISTRY`(등록부 폴더)를 지정하면 시작할 때 등록부의 현재 모델을 읽는다. 현재 모델이 없으면 시작하지 않고 이유를 알린다. `RSW_MODEL_PATH`와 같이 지정하면 등록부가 우선이고 경고를 남긴다.
- 지정하지 않으면 지금과 똑같다(`RSW_MODEL_PATH` 또는 기본 번들).

`POST /model/reload`:

- 등록부가 없으면 409.
- 등록부의 현재 모델이 지금 읽은 버전과 같으면 아무것도 하지 않고 `{"changed": false, "version": "v002"}`.
- 다르면 새 번들을 먼저 읽는다(이 동안 서빙은 계속된다). 읽기에 실패하면 500이고 서버는 옛 모델로 계속 돈다.
- 그 뒤 한 번에 교체한다. 처리 중인 `/predict`는 옛 모델로 끝나고, 교체 뒤에 시작하는 요청은 새 모델을 쓴다. 한 요청이 두 모델을 섞어 쓰지 않는다.
- 설비별 상태는 '새 번들로 서버를 다시 시작한 것'과 같게 만든다. 지금의 저장 → 복원 경로(`GunState.snapshot` · `restore`)를 그대로 쓴다. 규칙 쿨다운 · 프로파일 · 통계 · 조기 경보 쿨다운은 이어지고, 모델에 묶인 워밍업 결과 · 설비별 임계값 · 알람 연속 횟수는 버려져 설비가 다시 워밍업한다(6시간).
- 전송 대기열(outbox)은 건드리지 않는다. 이미 만들어진 핸드오프는 옛 모델의 `detector` 값을 그대로 갖는다.
- 응답: `{"changed": true, "version": "v003", "previous": "v002", "created": "..."}`.

`GET /model/loop`(읽기 전용):

```json
{
  "registry": "models/registry",
  "loaded": {"version": "v002", "created": "2026-11-12T10:03:11"},
  "champion": {"version": "v002", "cutoff": "2021-09-13T00:00:00", "train_files": 33},
  "in_sync": true,
  "challenger": {"version": "v003", "cutoff": "2021-09-20T00:00:00", "train_files": 40},
  "last_tick": "2021-09-20T00:00:00",
  "decisions": []
}
```

- `decisions`는 최근 10건이고 형식은 8.1절과 같다. `?limit=`으로 바꾼다.
- `in_sync`가 false면 등록부의 현재 모델이 바뀌었는데 서버가 아직 reload하지 않은 것이다.
- 등록부가 없으면 `{"registry": null}`.

`GET /health`에 `model_version`(등록부가 없으면 null)을 더한다. 기존 필드와 `/model`, `/predict`, 핸드오프 형식은 바꾸지 않는다. 모델이 바뀌면 핸드오프의 `detector.created`가 달라진다. 이것은 지금도 번들을 바꿔 다시 시작하면 생기는 변화다.

### 8.5 전처리: 새 파일 추가

재생이 끝난 뒤 새 데이터는 파일로 들어온다(사용자 결정 11-11).

```
py -3.11 .py/preprocess.py --split append --input-dir <새 CSV 폴더>
```

- 기존 `preprocess_config.json`과 `scaler.json`을 그대로 쓴다. 표준화 값을 다시 계산하지 않는다. 다시 계산하면 예전 번들이 다른 척도의 데이터로 채점되어 섀도 비교가 틀어진다.
- 결과를 `preprocessed/`에 쓰고 `manifest.csv`에 줄을 더한다. 이미 있는 이름은 건너뛴다.
- 학습 코드가 파일 이름의 유형 접두(`E01_` ~ `E04_`)로 유형별 분할을 하므로, 이름에 접두가 없으면 마지막 10분의 종료 코드로 유형을 정해(`infer_class`, 테스트 파일과 같은 방식) `E0x_<원래 이름>`으로 쓴다.
- 마지막 10분에 종료 코드가 없는 파일은 고장으로 끝난 기록이 아니므로 건너뛰고 알린다. 결측률 기준도 기존과 같다.
- 이름이 이미 `E0x_N`인 파일은 이 검사를 하지 않고 이름의 유형을 따른다. 원래 train 파일과 같은 규칙이다(그중 한 건은 마지막 10분에 종료 코드가 없다). 고장으로 끝나지 않은 기록에 이 이름을 붙이면 안 된다.
- 구현하면서 정한 이름 규칙: 입력 이름은 `<앞부분>_<숫자>.csv`이고 숫자는 32767 이하다. 유형을 추정한 파일의 새 이름은 `<유형>_<그 유형의 다음 번호>`이고(예 `E03_18`), 원래 이름은 `manifest.csv`의 `source` 열에 남는다.

운영에서 스케줄러가 부를 명령은 이 둘이다(등록은 이번 범위가 아니고 README에 예시로 적는다).

```
py -3.11 .py/preprocess.py --split append --input-dir incoming
py -3.11 .py/model_loop.py tick --server-url http://localhost:8000
```

## 9. 실패 처리

| 상황 | 동작 |
|---|---|
| 학습 프로세스가 실패하거나 번들이 없다 | 점검을 오류로 끝낸다. 등록부는 바뀌지 않는다. 다시 부르면 그 학습부터 한다 |
| 버전 모델은 됐는데 시드 모델 학습 중 끊겼다 | 버전은 시드 모델까지 다 생긴 뒤에 도전자로 등록한다. 다시 부르면 이미 있는 번들은 건너뛴다 |
| 학습한 버전에 조기 경보가 없다(레시피에서 껐다, 임계값을 정할 윈도우가 모자라다) | 등록하지 않고 이유와 함께 오류로 끝낸다. 첫 모델도 같다. 시드 모델은 학습하지 않는다. 학습한 번들은 남겨 같은 파일로 다시 학습하지 않는다 (사용자 결정 11-12) |
| 채점이 실패한다 | 판정을 기록하지 않고 오류로 끝낸다. 도전자는 그대로다 |
| 서버 reload 호출이 실패한다 | 경고를 남기고 점검은 성공으로 끝낸다. `/model/loop`의 `in_sync`가 false로 보인다. `--server-url`로 부른 다음 점검이 다시 알린다 |
| 추가 전처리에서 파일 하나를 읽지 못한다 | 그 파일만 이유와 함께 건너뛰고 나머지는 더한다. `manifest.csv`는 파일마다 바로 쓴다. 건너뛴 파일은 다음에 다시 시도한다 |
| `now`가 `last_tick`보다 앞이다 | 시작하지 않는다 |
| 잠금 파일이 남아 있다 | 시작하지 않고 파일 경로를 알린다. 실행 중인 것이 없으면 사람이 지운다 |
| 서버가 새 번들을 못 읽는다 | 500. 옛 모델로 계속 돈다 |

## 10. 실행 시간과 8 GB PC

- 측정 전 추정이다. 64건 전체를 4겹 교차 검증까지 학습하면 약 10분이다(`CLAUDE.md`). 그중 윈도우 만들기가 85초였다(C-8 학습 로그). 버전 모델 하나는 학습 5번, 시드 모델은 1번씩이다.
- 재생 전체는 버전 5개(16 · 33 · 40 · 45 · 60건)와 시드 모델 8개, 판정 3번이다. 파일 수에 비례한다고 보면 버전 모델에 30분 안팎, 시드 모델과 채점을 더해 1시간 안팎으로 예상한다.
- 구현 첫 단계에서 버전 모델 하나와 시드 모델 하나의 시간을 잰다. 전체가 1시간 30분을 넘을 것 같으면 시드 수나 교차 검증을 사용자와 다시 정한다.
- 이 PC에서는 오래 도는 백그라운드 작업이 끊긴 적이 있다. 재생은 포그라운드에서 돌리고, 끊기면 같은 명령으로 이어 간다(8.2절). 학습 한 번이 10분에 가까우므로 이미 끝난 번들을 건너뛰는 것이 꼭 필요하다.
- 실측(2026-11-12): 버전 모델 5개 24분(126 ~ 422초), 시드 모델 8개 14분, 판정 채점 3분, 보고서 1.5분, 합쳐 약 45분이다. 점검 하나가 10 ~ 15분이라 10분 단위 호출로는 점검 안에서 나눠 이어야 했다(`history.md` 50절).

## 11. 테스트

단위(모델을 학습하지 않는다):

- 등록부: 버전 등록, 현재 모델 변경과 이력, 판정 기록, 바꿔치기 쓰기, 잠금, 설정 불일치 거부.
- 판정 함수: 다섯 조건 각각의 통과와 실패, 동률, AUROC 없음, 조기 경보가 꺼진 A · B.
- 점검 로직(가짜 학습 · 채점 함수): 첫 모델 조건, 새 파일 5건 미만이면 학습 안 함, 섀도 5건 미만이면 미룸, 교체와 유지, 판정 직후 새 도전자, 같은 `now` 재실행, 시간 역행 거부, 학습 실패 시 등록부 불변, 재생 중단 뒤 이어 하기. 3절 표의 점검일 · 파일 수가 실제 `manifest.csv` 형식의 입력에서 그대로 나오는지도 본다.

합성 데이터(기존 `workspace` 방식):

- `train.py`: `--files-from`이 준 파일만 학습 · 검증에 쓰는지, `--eval-files-from` · `--eval-out`이 그 파일들의 지표를 쓰는지, 옵션이 없으면 지금과 같은지.
- `preprocess.py --split append`: 표준화 값이 바뀌지 않는지, `manifest.csv`에 더해지는지, 유형 추정과 이름, 종료 코드 없는 파일 건너뛰기, 중복 건너뛰기.
- 루프 전체: 종료 시각이 다른 합성 파일로 작은 설정(예: 첫 모델 4건, 새 파일 2건, 섀도 2건)의 재생을 끝까지 돌려 등록부와 보고서 형식을 확인한다.

서버(TestClient):

- `RSW_MODEL_REGISTRY`로 시작하면 현재 모델을 읽는다. 지정하지 않으면 기존 동작이다(기존 시험이 본다).
- reload: 같은 버전이면 변화 없음, 다른 버전이면 `/health` · `/model` · `/model/loop`가 새 모델을 보임, 못 읽는 번들이면 500이고 옛 모델 유지.
- 교체 뒤 설비 상태: 워밍업으로 돌아가고, 규칙 쿨다운 · 통계 · 조기 경보 쿨다운은 이어진다. 재시작 시험(`test_7`, `test_17`)과 같은 결과여야 한다.
- 동시성: 여러 스레드가 `/predict`를 보내는 중에 reload한다. 오류 응답이 없고, 각 응답이 한 모델로만 처리됐는지 본다.
- 교체 전에 대기 중이던 핸드오프가 교체 뒤에도 그대로 전송되는지 본다.

실제 데이터:

- 64건 재생을 끝까지 돌리고 `report`로 보고서를 만든다(`results/D-11/runs/`).
- 서버를 등록부로 켠 채 재생의 한 구간을 돌려 성공 기준 2를 확인한다.

## 13. 한계와 후속 과제

한계:

- 전처리의 표준화 값은 train 64건 전체로 한 번 계산한 것이다. 학습 레시피(모델 구성, 피처 목록, 조기 경보 운영점 q 0.975)도 64건 전체와 테스트를 보고 고른 것이다. A와 B가 같은 혜택을 받으므로 비교는 공정하지만, 보고서의 절대 수치는 낙관적이다.
- 판정은 섀도 파일 5 ~ 15건으로 한다. 조건 1 · 2가 흔들림을 걸러 주지만, 판정 하나하나를 강한 증거로 읽으면 안 된다.
- 재생에서 판정은 세 번 안팎이다. 데이터 양의 한계다.
- 교체 직후 설비당 6시간은 모델 알림과 조기 경보가 나가지 않는다. 종료 코드 규칙 알림은 계속 나간다. 미탐을 우선하는 방침에서 보면 약점이다.
- 섀도 채점은 구간이 끝난 뒤 한꺼번에 한다. 판정 결과는 실시간으로 같이 채점한 것과 같지만, B의 점수를 실시간으로 볼 수는 없다.
- 재생에서 서버는 가상 달력과 따로 돈다. 서버가 받은 데이터가 학습으로 이어지는 것은 아니다.

후속 과제:

- 서버가 받은 스트림을 설비별로 저장하고, 종료 코드로 끝난 구간을 파일로 잘라 8.5절의 입력으로 넘기기.
- 교체 뒤 워밍업 동안 옛 모델로 알림을 유지하기, 또는 워밍업 통계를 새 모델로 이어 쓰기.
- 운영 화면에 모델 버전과 판정 이력 보이기(`GET /model/loop` 사용).
- 스케줄러 등록.
