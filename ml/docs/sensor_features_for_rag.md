# ML → RAG 매분 센서 문서 (sensor-features-v4) 설명서

2026-10-21 · ML

RAG 쪽이 이 문서만 보고 받는 쪽을 만들 수 있게 정리했다. 스키마: `ml/docs/sensor_features.schema.json`, 예시: `ml/docs/sensor_features.example.json`, 만드는 코드: `ml/.py/sensor_features.py`(순수 Python이라 RAG 쪽에서 그대로 import해 형식 확인에 써도 된다).

## 1. 무엇이 바뀌었나

- **ML은 해석하지 않는다.** 상황 번호(S01~S10), 증상(P1~P9), 모델 점수는 보내지 않는다. 예지보전이 이 데이터로 안 된다는 결론(고장 수 시간 전 전조 없음) 때문에, RAG가 받는 데이터는 측정된 사실만 남겼다.
- **RAG가 받는 건 이 매분 문서 하나다.** 고장 알림(핸드오프)은 UI용으로만 ML 안에 남고 RAG로는 보내지 않는다.
- **상황 번호가 없어졌으니 매뉴얼은 에러코드·고장유형으로 찾아야 한다.** 정의서의 S01~S04는 논문 고장 E01~E04와 같은 것이라 그 내용(정의, 매뉴얼 근거, 점검 순서)은 그대로 쓸 수 있다. S05~S10은 데이터 근거가 없어 쓰지 않는다.
  - (2026-10-28 D-8) api가 `FIELD_MEMORY=1`일 때만 S05~S08·S10을 안내 후보로 쓴다. 정의서의 매뉴얼 기반 연결과 사람 판정 기록으로만 쓴다. ML은 여전히 사실만 보낸다(`docs/hitl-loop.md`).
- RAG 쪽 원안 v2(센서 z 1~4개)에서 v4로 바뀐 점: 에러코드·고장유형·준비 상태 칸 추가, 센서를 3묶음으로 나눔, 측정값은 4개가 아니라 10개 전부.

## 2. 받는 방법

| 방법 | 내용 |
|---|---|
| push (기본) | ML 서버를 `RSW_RAG_SENSOR_URL=http://<RAG 주소>/sensor-features`로 켜면 1분마다 POST. 헤더 `Idempotency-Key: <gun_id>|<observed_at>` |
| 재전송 | 실패하면 10초 뒤 다시 보냄 → 같은 `gun_id`+`observed_at`이 두 번 올 수 있으니 두 번째는 버릴 것. 4xx로 답하면 형식 문제로 보고 다시 안 보냄 |
| pull | `GET /guns/{gun_id}/sensor-features?minutes=60` (최근 최대 360분) |
| 시험용 | `ml/.py/mock_rag.py`가 받는 쪽 흉내(받은 문서를 콘솔과 파일로 남김) |

데이터가 끊긴 1분은 문서가 오지 않는다(결측은 고장 신호가 아니었음).

## 3. 칸별 뜻과 쓰는 법

| 칸 | 뜻 | RAG에서 |
|---|---|---|
| `gun_id`, `observed_at` | 어느 건, 어느 1분(창의 끝, UTC) | 시간 흐름으로 묶기 |
| `error_code` | 그 1분에 뜬 컨트롤러 코드(마지막 것), 없으면 null | **가장 믿을 만한 단서** |
| `fault_class` | `error_code`가 종료 코드일 때만 E01~E04 (E012→E01, E016→E02, E028→E03, E029→E04). 학습 고장 파일 72개 중 71개가 고장 직전 10분에 이 코드를 띄움(README 5.3.4) | **매뉴얼 조회 열쇠** |
| `gun_norm` | `gun` = 이 건의 평소와 비교한 z / `warming_up` = 건을 켜고 처음 몇 시간, 아직 평소를 몰라 전체 평균과 비교 | `warming_up`이면 z를 덜 믿을 것 |
| `n_samples` | 그 1분의 1초 데이터 수(60 = 다 있음) | 적으면 값이 거침 |
| `measurements[]` | 측정값 10개(아래), z 절댓값 큰 순 | 위쪽일수록 평소와 많이 다름 |
| `states[]` | 켜짐/꺼짐 신호 3개의 1분 켜짐 비율 | 건이 일했는지 판단 |
| `setpoints[]` | 설정값 4개의 1분 평균·흔들림 | 측정값 흔들림의 원인 확인 |

### measurements — 측정값 (매분 10개 전부)

센서 c1 전극 캡 오프셋, c2 전극 힘, c3 전극 위치, c5 보정(밸런스) 압력, c6 마찰 × 평균(`_mean`)·흔들림(`_std`).

- `z`: 이 건의 평소 대비 차이(모델 기준값과의 차, 소수 셋째 자리). 표준정규 z가 아니다. 대략 |z| 1 이상이면 평소와 꽤 다름.
- `value`: 그 1분 CSV 숫자의 평균·표준편차. 단위는 데이터셋에서 가려져 있어 모른다 — 같은 건 안에서 비교용.

### states — 상태 신호 (켜짐 비율 0~1)

| 신호 | 1일 때 |
|---|---|
| c4, c18 | 건이 누르는 중 (데이터상 둘이 98% 같이 움직임) |
| c10 | 작동 허용(US2) 켜짐. 평소 거의 100% |

### setpoints — 설정값 (c13 보정 압력 설정, c14 전극 힘 설정, c15 전극 위치 설정, c16 판 두께 설정)

`mean`·`std`는 원래 값, `mean_z`·`std_z`는 평소 대비 차이.

## 4. 꼭 지켜야 할 해석 규칙

1. **셋 다 0이면 멈춘 1분이다.** `states`의 c4·c18·c10이 모두 0%면 건이 서 있었고, 측정값은 마지막 값이 그대로 고정된 것이다. 이때 측정값 z는 "벗어남"이 아니다(실데이터: 고장 몇 시간 전부터 멈춰 있는 건이 있음).
2. **설정값은 1분에도 여러 번 바뀌는 게 정상이다.** 로봇이 용접점마다 다른 설정으로 누른다(1분에 용접 9번이면 설정도 여러 개). 그래서 `std > 0`은 정상이고, 설정 z가 커도 "평소와 다른 조합으로 용접했다"는 뜻이지 고장이 아니다.
3. **측정값 흔들림(std)은 대부분 용접 활동이다.** 누름(2500~2800) ↔ 대기(0~100)를 오가니 용접을 많이 할수록 커진다. 측정값 흔들림 z가 클 때 설정 흔들림도 크고 c18 비율도 높으면 정상 작업일 가능성이 크다. 측정값 평균(`_mean`)이 벗어난 쪽이 더 의미 있다.
4. **c13은 이름과 달리 c5의 설정값이 아니다.** 데이터로 확인했다(크기가 300배 차이, 설정이 바뀌어도 실측이 안 따라감). c13은 대기 때 14.99, 누를 때 9 근처로 상태 따라 바뀐다.
5. **c2와 c14, c3과 c15는 같은 물리량이다.** 누르는 순간 전극 힘 c2는 설정 c14와 같은 숫자(99%), 대기 중 위치 c3은 설정 c15를 따라간다(95%). 다만 이 차이가 고장 전에 커지지는 않았다(79건 확인, history 34절).
6. **센서로 고장을 미리 알 수는 없다.** 고장 직전에도 센서는 평소와 크게 다르지 않았다. 고장을 알려주는 건 `error_code`다. 센서는 "그때 상태가 어땠나"의 보조 근거로 쓸 것.

## 6. RAG 쪽에 확인할 것

1. 이 v4 스키마로 받는 쪽을 바꿀 수 있나 (원안 v2와 칸이 다름)
2. 매뉴얼 조회를 상황 번호 대신 `fault_class`(E01~E04)·`error_code`로 바꿀 수 있나
3. 매분 문서를 어떻게 쓸 계획인가 — 에러코드가 뜬 분 앞뒤 몇 분을 모아서 답변에 쓸지, 매분 따로 볼지
4. 더 필요한 칸이 있나 (칸 추가는 쉽고, 빼는 건 받는 쪽이 깨지므로 어렵다)
