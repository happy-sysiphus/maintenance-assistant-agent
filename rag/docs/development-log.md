## 2026-11-10 — 조기 경보 센서 RAG와 해결 사례 재사용

### 개발 배경과 변경 전 상태

- 기존 RAG는 E012·E016·E028·E029의 검토된 매뉴얼 안내와 일반 질문을 처리했다. 기존 정비 기억은 E 코드 이력을 생성 문맥에 넣는 방식이었다.
- GitHub `develop-loop`의 ML 핸드오프 v1.4는 상위 기여 피처 최대 3개와 경보 시작 1분의 물리 센서 원시 블록을 별도로 보낸다. 공개 예시의 3개 피처 중 실제 채널은 c10 하나이고 두 항목은 10분 오류 비율 통계다.
- 기존 로컬 미커밋 변경을 기반으로 `rag/`만 추가 개발했다. 원격 API·UI·ML의 후속 변경과 로컬 구현은 이번에 병합하지 않았다.

### 합의한 판단 기준

- ML이 판정한 조기 경보를 입력으로 받는다. RAG는 선택된 물리 채널의 앞·뒤 구간 중앙값을 비교해 방향을 계산하고, 정상 범위와 고장 여부는 재판정하지 않는다.
- 서로 다른 실제 채널 세 개의 채널 ID와 변화 방향이 모두 같을 때만 같은 입력으로 본다. 기여도 순서, 값의 크기, 파생 피처는 일치 조건에서 제외한다. 두 구간 중 관측값이 절반 미만이거나 방향이 확정되지 않으면 해당 채널은 매칭에 사용하지 않는다.
- 선택한 매뉴얼 근거, 실제 수행 조치, 작업자 해결 확인이 있어야 해결 이력에 들어간다. 처음 확인한 사례는 후보에 넣고, 적용 범위가 확인된 서로 다른 설비 두 대에서 해결되면 자동 표시한다. 두 후보가 조건을 충족하거나 검토되지 않은 확정 반례 한 건이 있으면 자동 표시를 보류한다.

### 구현한 동작과 예시

- `warning_input.py`에서 변경 시점으로 압축된 ML 원시값과 결측을 해석한다. 실제 v1.4 예시에서 c10은 39초까지 0, 40초부터 1로 관측된다. 기여 피처는 세 개지만 방향이 있는 채널은 하나라 `pattern_key=null`이다. 별도 합성 입력의 매칭 키는 `direction-v1:c10:up|c3:up|c5:down`이다.
- `early_warning.py`에서 무모델 경보 조회, 명시적인 후보 생성, 수동 근거 검색·질문, 해결 등록·검토를 분리했다. 생성 후보는 검색된 근거와 대조한 등록 사례에서 최대 3개를 선택한다. 모델은 후보 이유만 작성하며 카드의 점검·조치·인용은 검토된 자료에서 가져온다. Festo 구판 US2 항목은 코드 밖 사례 검색을 확인할 수 있는 원문 근거 사례다. 센서와 이 항목을 잇는 규칙은 사전에 넣지 않았다.
- `warning_memory.py`에서 `WarningPattern`, `WarningResolution`, `WarningManualCase`를 기존 매뉴얼 그래프와 분리했다. 환경과 경보 ID의 고유 키로 같은 해결의 중복 전송을 막는다. 수동 선택은 현재 PDF 검색 결과와 대조한 뒤 저장하고, 검토 전에는 집계에서 제외한다. 매뉴얼 적용 범위가 없거나 불확실하면 후보까지만 보여준다.
- [조기 경보 연동 안내](early-warning-integration.md)에 CLI, Python 호출 계약, 해결·검토 JSON, API의 전송 대기 처리, UI의 고정 사례 ID와 화면 상태를 정리했다.

### 로컬 검증 결과

- 저장소의 `rag/.venv`에서 기존 RAG·API 회귀 검사 89개 통과를 확인했다.
- 격리된 Neo4j Community 5.26.0을 루프백 포트 17687에서 사용했다. 최종 명령은 `python -B -m pytest rag/tests api/tests -q -p no:cacheprovider`이며, 통합 테스트를 켠 결과 **97개 통과**했다.
- 실제 Neo4j에서 첫 해결 후보, 같은 설비 중복 제외, 두 번째 설비의 자동 표시, 반례와 복수 사례 보류, 근거 검증과 수동 사례 승인, 동일 요청 재시도, 매뉴얼 재구축 후 이력 보존을 확인했다. 실제 Neo4j 키워드 인덱스로 코드 밖 매뉴얼 항목을 찾는 경로도 검증했다.
- Claude 후보 선택은 테스트 응답으로 대체했고, 자동 조회에서는 검색·모델 호출이 없는지 검사했다. 합성 해결 기록은 동작 검증용이며 실제 현장 성공률이나 센서 패턴의 정비 적중률을 측정한 결과는 아니다. 공유 Aura에 테스트 기록을 쓰지 않았다.

### 남은 연동과 검증

- API가 반복 경보에서도 판단한 원본 이벤트를 보존하고, 해결 종료와 Neo4j 전송 대기 기록을 함께 저장하도록 연결해야 한다. UI에서는 조회와 후보 요청을 분리하고, 선택 근거와 실제 조치·작업자 확인을 고정 사례 ID에 연결해야 한다.
- 실서비스 자동 표시 전에는 실제 경보·오경보 재생으로 세 채널의 방향이 같은데 정비가 달랐던 경우를 검토한다. 이번 검증에서는 실제 Claude 호출이나 현장 화면 통합을 실행하지 않았다.

## 2026-11-11 — 자동 표시 집계를 해결 케이스 기준으로 변경

- 현장의 용접건은 동일 모델이고 센서 특성도 동일하다고 가정한다. 자동 표시는 같은 세 채널·방향과 매뉴얼 사례로 해결된 서로 다른 `case_id` 두 건을 기준으로 한다. 한 용접건에서 두 건을 해결해도 집계한다.
- `gun_id`는 입력에 없어도 되며, 제공된 값은 이력 정보로만 사용한다. 같은 케이스의 반복 경보는 한 건으로 집계하고, 같은 경보의 재시도에서 `gun_id`가 빠져도 기존 해결 기록을 재사용한다. 매뉴얼 적용 범위는 서비스에 현장 공통값으로 한 번 지정할 수 있다.
- 격리 Neo4j 통합 검증에서 같은 용접건의 두 케이스로 자동 표시가 적용되고, 같은 케이스의 반복 경보는 집계를 늘리지 않는 것을 확인했다. 용접건 ID 없는 조회와 저장도 검증했다. 기존 RAG·API 회귀 검사를 포함해 97개가 통과했다.
- 연동 문서와 단계별 예시는 설비 대수 대신 해결 케이스 건수를 표시하도록 수정했다.

## 2026-11-11 — 팀 공용 Aura에서 조기 경보 검증

- 운영·팀 시연에서 매뉴얼 검색과 조기 경보 이력에 같은 공용 Aura DB를 사용한다. CLI는 `NEO4J_DATABASE`와 `RAG_WARNING_NAMESPACE`를 읽고, 팀원은 같은 이력 이름을 사용한다.
- 공용 Aura의 기존 문서 버전을 유지하면서 Windows와 macOS·Linux의 Git 줄바꿈 차이에 따른 버전 오류를 수정했다.
- 공용 Aura의 기존 매뉴얼과 두 검색 인덱스를 확인하고 조기 경보 이력의 고유 제약과 인덱스를 초기화했다. E012 조회에서 근거 12개를 반환했다.
- 공용 Aura 통합 테스트 2개가 통과했다. 실제 매뉴얼 검색, PDF 근거를 선택한 해결 기록과 검토, 두 건 해결 이후 자동 카드, 반례와 복수 승격 보류를 확인했다. 합성 이력은 실행별 전용 이름에 저장하고 테스트 종료 시 그 이력만 정리했다.
- 기본 하이브리드 검색과 Claude 수동 답변을 공용 Aura로 실행해 매뉴얼 근거 6개와 답변 항목 4개를 받았다. 팀 ML 예시의 자동 후보 요청은 등록 사례와 일치하는 근거가 없어 `no_evidence`였다. DB 연결 없이 실행하는 RAG·API 회귀 검사는 133개 통과했고, 선택 실행하는 DB 테스트 6개는 건너뛰었다.
- 팀원 실행과 검증 명령은 [공용 Aura 실행 안내](early-warning-integration.md#공용-aura에서-실행하기)에 추가했다.

## 2026-11-11 — WARNING API·UI에서 공용 해결 이력 연결

- WARNING 화면과 API 연동을 공용 Aura의 `WarningMemory`에 연결했다. SQLite에서 케이스를 닫을 때 Aura 전송 대기를 함께 저장한다. 백그라운드 작업이 동일한 해결 요청을 재시도하고 UI는 반영 대기·완료·검토 대기·실패 상태를 표시한다.
- 화면 케이스 번호는 그대로 사용한다. 공용 이력의 집계 키는 대표 ML 이벤트를 사용해, 서로 다른 API에서 같은 화면 번호를 발급해도 서로 다른 경보의 해결을 두 건으로 센다. 반복 경보를 골라 종료하면 해당 원본으로 패턴을 계산한다.
- 이력 재사용은 기본 활성화했다. 거절한 자동 카드는 해당 경보의 후보와 선택에서 제거한다. 수동 모드는 질문별 매뉴얼 검색과 PDF 근거 선택을 제공한다.
- 임시 SQLite의 API 회귀 테스트로 전송 응답 유실 후 동일 요청 재시도와 중복 방지, 거절 카드 재선택 차단을 확인했다. 실제 공용 Aura의 테스트 전용 이름에서는 두 API 저장소의 `CASE-0001`을 별개로 집계한 뒤 자동 카드를 반환했다. 테스트 이력은 종료 시 정리했다.
- [WARNING API·UI 실행 안내](../../api/docs/warning-api-20261111.md)에 공용 설정, 저장 상태와 검증 방법을 반영했다.
