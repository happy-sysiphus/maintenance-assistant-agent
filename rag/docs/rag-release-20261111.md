# RAG 변경 보고서

2026-11-11 · 조기 경보 RAG, 매뉴얼 근거 검색, 해결 이력 재사용

이번 버전에서는 **E 코드 기반 정비 안내에 센서 기반 조기 경보 경로를 추가**했습니다. 조기 경보를 처음 열면 센서 소견과 저장된 사례를 조회합니다. 원인 후보를 요청하면 관련 매뉴얼을 찾아 Claude가 검토할 사례를 고릅니다. 작업자가 실제로 조치하고 해결을 확인한 결과는 Neo4j에 쌓아 다음 경보에 재사용합니다.

UI 작업자는 [조기 경보 화면 개발 안내](../../ui/docs/10-early-warning-rag-ui.md)부터 읽으면 됩니다. API 담당자는 [RAG 함수와 저장 계약](early-warning-integration.md)을 참고하세요.

## 이전 버전과 달라진 점

| 항목 | 이전 동작 | 이번 버전 |
|---|---|---|
| 입력 | E012·E016·E028·E029 또는 매뉴얼 질문 | 기존 경로에 ML v1.4 `early_warning` 핸드오프 경로 추가 |
| 문서 처리 | PDF 본문을 중심으로 청크 구성 | 표 구조와 행 경계를 보존하고, 여러 페이지에 걸친 표의 출처를 페이지별로 유지 |
| 모델 | OpenAI로 답변 생성 및 임베딩 | Claude로 답변 생성, OpenAI는 검색어 임베딩에 사용 |
| 현장 이력 | API가 E 코드 중심으로 이력 집계 | 기존 E 코드 응답 함수는 선택적 `maintenance_context`를 지원. 조기 경보에는 센서 패턴과 해결 사례를 연결하는 별도 Neo4j 이력 추가 |
| 작업자 확인 | 작업자가 케이스에서 조치와 결과를 기록 | 조기 경보에서 선택한 매뉴얼 사례 또는 PDF 근거, 실제 조치, 해결 확인을 함께 저장 |

E 코드 호출자는 기존 `answer_question()`을 계속 사용합니다. `maintenance_context`는 호출자가 전달했을 때 동작하는 선택 기능입니다. 이번 게시에는 RAG 코드와 연동 문서가 포함됩니다. API가 RAG에 정비 이력을 전달하는 연결과 새 조기 경보 화면은 담당 파트에서 연결합니다.

## 조기 경보 한 건의 흐름

1. **센서 해석.** ML이 보낸 상위 기여 피처 최대 세 개에서 물리 채널을 고릅니다. 경보 시작 1분의 원시값을 복원하고 앞·뒤 구간의 중앙값으로 상승·하락을 판단합니다. 상태 신호의 전환 시점과 결측도 기록합니다. 기여 피처에는 같은 센서의 평균·표준편차나 10분 오류 비율이 들어올 수 있습니다.
2. **이력 조회.** 비교 가능한 서로 다른 세 채널의 종류와 방향을 정렬해 패턴 키를 만듭니다. 예를 들어 `direction-v1:c10:up|c3:up|c5:down`입니다. Neo4j에서 같은 패턴의 해결 기록을 조회합니다. 한 케이스의 해결은 참고 후보로, 같은 사례로 해결한 별개 케이스 두 건 이상은 자동 카드로 표시할 수 있습니다. 두 건은 같은 용접건에서 발생해도 됩니다. 자동 카드에는 매뉴얼 적용 범위와 반례 여부도 확인하며, 모델 호출 없이 저장된 카드와 근거를 반환합니다.
3. **후보 생성.** 작업자가 **원인 후보 보기**를 누르면 센서 소견으로 Neo4j 매뉴얼을 검색합니다. 검색된 문서·쪽·근거 문구와 일치하는 검토 사례 중 Claude가 최대 세 개의 사례 ID와 이유를 반환합니다. RAG가 등록된 점검·조치·PDF 근거를 붙입니다. 비교 가능한 채널이 세 개 미만이어도 관측된 내용으로 후보를 검색할 수 있습니다.
4. **수동 검색과 해결.** 적절한 후보가 없으면 작업자가 매뉴얼을 검색해 적용할 PDF 근거를 선택할 수 있습니다. 선택한 사례 또는 근거와 실제 조치, 작업자 확인을 함께 저장합니다. 목록 밖의 매뉴얼 근거는 검토가 끝나면 재사용 후보에 포함됩니다.
5. **다음 경보.** 해결 저장으로 생성한 관계를 다시 조회합니다. 자동 카드를 거절한 뒤 다른 사례로 실제 해결한 기록이 확인되거나, 여러 사례가 동시에 자동 표시 조건을 충족하면 자동 표시를 보류합니다.

## Neo4j에서 읽고 쓰는 내용

- **매뉴얼 검색**은 문서·페이지·청크와 그 검색 인덱스를 읽습니다. 네 PDF의 출처와 개정 정보를 같이 사용합니다.
- **해결 이력**은 센서 패턴, 해결 기록, 매뉴얼 사례를 별도 라벨로 저장합니다. 경보 조회와 후보 생성에서는 이력 노드가 늘지 않습니다. 해결 종료가 확인되면 패턴과 사례를 해결 기록에 연결합니다.
- 같은 경보의 동일한 해결 요청은 한 번만 기록합니다. 같은 케이스의 반복 알림도 해결 건수를 늘리지 않습니다. 오알람·미해결은 확인된 해결로 집계하지 않습니다.

로컬 테스트 DB에서는 이력 저장과 조회를 검증했습니다. 실제 서비스에서는 매뉴얼 검색 인덱스와 이력 저장 대상 DB·namespace를 확인하고 [초기화 절차](early-warning-integration.md#로컬에서-호출하기)를 사용합니다.

## 팀에서 확인할 수 있는 검증 결과

- 최신 `main` 기반 게시 작업본에서 빈 로컬 Neo4j로 RAG·API 테스트 **134개가 통과**했습니다. 세 채널의 순서가 달라도 매칭되는지, 반복 케이스 중복 방지, 해결 두 건 이후 모델 호출 없는 자동 표시, 반례 보류, 수동 사례 검토와 매뉴얼 그래프 재구축 후 이력 보존을 확인했습니다. 전용 샘플 청크로 매뉴얼 검색도 검증했습니다. 이 테스트에서는 Claude의 사례 선택 응답을 테스트 데이터로 대체했습니다.
- 팀 ML의 [v1.4 조기 경보 예시](../../ml/docs/rag_handoff_early_warning.example.json)에서는 기여 피처가 세 개여도 물리 채널은 c10 하나입니다. RAG는 이 채널의 40초 전환을 읽었고 자동 매칭은 보류했습니다.
- 전체 매뉴얼을 넣은 로컬 DB의 키워드 검색에서는, 팀 ML 예시의 센서 소견으로 조회했을 때 US2 관련 근거가 상위 결과에 들지 않아 `no_evidence`가 반환됐습니다. 검색어를 좁힌 별도 시연에서는 공개 매뉴얼 근거를 읽고 합성 관측으로 Claude 후보 선택을 확인했습니다. 이력 기반 자동 카드 시연에서는 조회 전후 Neo4j 노드·관계 수가 동일했습니다. 실제 현장 경보의 후보 적중률은 별도로 검증해야 합니다.
- PDF 구조·검색·모델 변경의 11월 4일 50문항 비교는 [RAGAS 비교 보고서](../RAGAS/results-20261104/COMPARISON.md)에 있습니다. 실험 설계와 검증 조건은 [개발 일지](development-log.md)에서 확인할 수 있습니다.

## 먼저 실행할 명령

저장소 루트에서 RAG 의존성을 설치한 뒤 팀 ML 예시의 센서 해석을 확인할 수 있습니다.

```powershell
python -m pip install -r rag/requirements.txt
python -B -m rag.early_warning analyze --input rag/tests/fixtures/early_warning_v14.json
```

후보·수동 검색을 실행하려면 Neo4j 문서 인덱스가 준비돼 있어야 합니다. 기본 하이브리드 검색에는 OpenAI 키가, 답변 생성에는 Anthropic 키가 필요합니다. 환경 설정과 호출별 입력은 [조기 경보 연동 안내](early-warning-integration.md)를 따릅니다.
