## 평가 방식

1. 네 PDF에서 본문을 직접 추출합니다. 서비스의 검색 결과·생성 답변은 기준 답변 작성에 사용하지 않습니다.
2. 코드별 비율을 맞추는 자체 생성기로 질문·짧은 기준 답변·원문 인용을 생성합니다.
3. 인용문이 지정된 PDF 페이지에 실제 존재하는지 자동 검사합니다.
   별도 LLM 호출로 기준 답변의 근거 지지 여부도 검토하고 `reference_audit.jsonl`에 남깁니다. 지적된 문항도 점수에서 숨기지 않습니다.
4. 고정한 질문으로 기존 `answer_question()`을 캐시와 history 없이 실행합니다.
5. **공식 `ragas==0.4.3` 라이브러리의 collections API**로 아래 지표를 계산합니다.
6. 성공·실패·결측 분모를 함께 보고합니다. 실패한 RAG 답변을 재생성해서 성공 답변만 고르지 않습니다.

| 지표 | 입력 | 해석 |
|---|---|---|
| Faithfulness | 질문·전체 답변·실제 생성 문맥 | 답변의 주장들이 제공한 근거에 충실한가 |
| AnswerRelevancy | 질문·전체 답변 | 답변이 질문에 관련되는가 |
| ContextPrecision | 질문·검색 근거·reference | 기준 답변에 유용한 근거가 검색 결과 앞에 있는가 |
| ContextRecall | 질문·검색 근거·reference | 기준 답변의 사실을 검색 근거가 얼마나 뒷받침하는가 |
| FactualCorrectness (F1) | 전체 답변·reference | 기준 답변과의 사실 일치 및 누락 정도 |

Faithfulness에는 실제 생성 요청에서 사용한 검색 원문과 검토된 점검 매핑·적용 범위 안내를 포함합니다.
Context Precision/Recall에는 순서가 보존된 검색 원문만 사용합니다. JSON 응답을 렌더링한 전체 answer에 점검·정상 기준·조치가 포함됩니다.

**기준 답변은 자동 생성된 합성 reference이며, 전문가가 검증한 gold GT가 아닙니다.**
RAGAS의 전체 TestsetGenerator/KG 변환 파이프라인을 실행한 것은 아닙니다.
오류 코드별 비율과 비용을 통제하는 자체 데이터 생성기를 사용하고, 채점에는 공식 RAGAS 지표를 사용합니다.
원문 인용 존재 검사는 기준 답변 전체의 의미 검증을 대신하지 않습니다.
논문·발표에서는 “합성 기준 답변 기반 RAGAS 자동 평가”라고 표기하고 핵심 문항은 사람이 추가 검토하는 것이 좋습니다.

## Windows PowerShell 실행

저장소 루트(rag·api·ui·ml 폴더가 있는 위치)에서 실행합니다.
환경 설정은 기존 `rag/.env`에서 읽습니다. `.env`를 이 폴더에 복사하지 않습니다.
새 키를 `.env.txt`에 저장했다면 명령 끝에 `--credentials-file rag/.env.txt`를 추가합니다.
이 옵션은 해당 파일의 OPENAI_API_KEY만 평가 프로세스에 적용하며 기존 `.env`를 수정하지 않습니다.
Neo4j Aura는 읽기 조회만 수행하며, 매뉴얼은 `rag/data/`의 기존 파일을 읽습니다.

```powershell
py -3.13 -m venv rag/RAGAS/.venv
$evalPython = Join-Path (Get-Location) 'rag/RAGAS/.venv/Scripts/python.exe'
& $evalPython -m pip install -r rag/RAGAS/requirements.txt

# 유료 호출 없는 평가 도구 테스트
& $evalPython -B -m unittest discover -s rag/RAGAS -p test_evaluation.py -v

# 데이터 생성 후 다섯 유형에서 한 문항씩 예비 평가
& $evalPython -B rag/RAGAS/run.py --stage all --limit 5 --budget-usd 3

# 같은 results의 나머지 문항을 이어서 실행
& $evalPython -B rag/RAGAS/run.py --stage all --limit 50 --budget-usd 3

# API 호출 없이 보고서만 다시 계산
& $evalPython -B rag/RAGAS/run.py --stage report
```

`--stage generate / audit / answer / score / report / all`로 단계를 나눌 수 있습니다.
기존 문항·응답·채점 기록은 재사용하므로 같은 명령을 실행해도 완료된 항목은 재과금하지 않습니다.
한 결과 폴더에는 **한 실행 프로세스만** 사용합니다. 코드·문서 버전이 달라지면 새 `--output` 폴더를 지정해야 합니다.
실패한 채점도 보존되며 자동 재시도하지 않습니다.
일시적 API 오류나 평가 출력 잘림만 다시 계산하려면 아래처럼 실행합니다. 정상 점수는 재채점하지 않습니다.

```powershell
& $evalPython -B rag/RAGAS/run.py --stage score --limit 50 --budget-usd 3 --retry-failed --judge-max-tokens 8192 --ascii-math --credentials-file rag/.env.txt
```

재시도 전후 기록은 모두 남기고 집계에는 최신 결과를 사용합니다.
평가자 출력에서 ± 기호 이후 유니코드 이스케이프가 반복되는 문제가 관찰되어,
위 재시도는 평가 입력의 ±·≥·≤만 의미가 같은 +/-·>=·<=로 표기하고 출력 한도를 늘립니다.
원본 질문·기준 답변·RAG 응답은 보존하며, 변경 옵션은 채점 시도별로 기록합니다.
예산을 모두 소진한 결과에 새 출력 폴더를 지정해 추가 실행하지 마세요.

## 비용과 변경 범위

- 총 예산 상한은 **$3**, `costs.jsonl`의 기존 누적 금액까지 포함합니다.
- SDK 네트워크 재시도는 끄고, 모든 OpenAI 요청 전 예상 상한을 예약합니다. 미사용 잔여 예약은 응답 뒤 해제합니다.
- 요청별 입력·출력 토큰을 기록합니다. 사용량을 확인할 수 없는 실패 요청은 예약한 상한으로 보수적으로 합산합니다.
- 입력 캐시 할인 없이 표준 단가로 계산한 비용 추정치이며, 계정 실제 잔액·타 프로그램 사용액·세금은 조회하지 않습니다.
- 최종 질문·기준 답변 생성기는 `gpt-5.4-mini`, 평가자는 `gpt-4.1-mini`, 질문 임베딩은 `text-embedding-3-small`입니다. RAG 생성 모델은 기존 `.env` 설정 그대로 사용합니다.
- RAGAS 사용 통계 전송과 LangSmith 추적은 비활성화합니다. 문서·질문·답변 일부는 허용한 OpenAI API로 전송됩니다.
- `.venv/`와 임시 실행 폴더 `var/`는 Git에서 제외됩니다. 보고서·데이터·점수·비용 기록은 공유 가능한 결과입니다.
- 기존 RAG/API Python 파일의 해시를 실행 전후 비교합니다. 소스 파일·기존 답변 캐시·KG는 변경하지 않습니다.
- 이번 평가는 단일 시스템 측정이며 그래프/벡터 단독 대비 성능 향상을 입증하는 비교 실험은 아닙니다.

공식 정의 및 평가 한계는 [보고서](results/REPORT.md)의 공식 근거 링크를 참고하세요.

## 실제 사례로 이해하는 평균 수준의 성능

### 사례 선정: 전체 평균에 가장 가까운 E016-03

50개 실제 평가 결과에서 **다섯 지표의 전체 평균과 점수 차이가 가장 작은 문항**을 골랐습니다.
각 지표는 같은 비중으로 비교했으며, 사례 선정에만 사용한 방법입니다. 지표들을 합쳐 새로운 성능 총점을 만든 것은 아닙니다.
모든 점수가 평균과 정확히 같은 사례는 없으므로, 아래에는 **전체 평균과 해당 사례의 실제 점수**를 함께 표시합니다.

### 1. 사용자가 이렇게 질문했다면

> E016의 원인 관계를 전극 상태 관점에서 설명하면 무엇인가요?

### 2. 우리 RAG는 이렇게 답했습니다

아래는 **실제 응답의 발췌**입니다. 채점에는 발췌문이 아니라 점검·기준·조치까지 포함한 전체 답변을 사용했습니다.

> E016은 전극 감시 오류로, 전극 상태 관점에서는 전극이 기준 위치보다 과도하게 작아지거나 전극/캡에 이상이 있을 때 발생하는 것으로 해석할 수 있습니다. 매뉴얼에는 전극 파손·캡 누락을 보호 대상으로 설명하고, 가압(Force build-up) 중에 전극 위치가 설정된 감시 한계보다 작아지면 오류가 발생한다고 되어 있습니다.

실제 응답에는 다음 점검·조치도 포함됐습니다.

- 전극과 캡의 파손·누락 여부를 현장에서 확인합니다. [manual82 p.38]
- WinSPAS 전극 위치 감시 한계와 가압 시 전극 위치를 대조합니다. [manual82 p.38]
- 이동 보정 영점과 호밍 기준 위치의 의미·설정 상태를 확인합니다. [manual82 p.53]
- 조치: 별도로 이동 보정을 수행하는 경우, 새 전극 캡으로만 수행합니다. E016 발생만으로 재보정이 필수라고 판단하지 않습니다. [manual82 p.53] *(이 조치 문장은 가독성을 위해 요약)*

즉, 질문의 핵심인 **전극 파손·캡 누락과 위치 감시의 관계**에 답하면서, 관련 점검과 조건부 조치까지 설명하는 형태입니다.

### 3. PDF에서 자동 생성한 GT는 이 정도 범위였습니다

> 매뉴얼은 E016이 전극 파손 또는 캡 손실에 대한 보호라고 설명합니다. 따라서 전극 위치가 허용 한계보다 낮아지는 상황이 전극 손상과 연결될 수 있음을 뜻합니다.

근거는 `manual82` PDF 38쪽과 `diagnostic4` PDF 1쪽입니다.
이 GT는 질문의 원인 관계에 초점을 맞춘 짧은 합성 기준 답변으로, 실제 RAG 답변의 모든 점검·보정 설명을 포함하지는 않습니다.

### 4. 수치로 평가하면 이렇게 나옵니다

| 지표 | 전체 50문항 평균 | 이 사례의 실제 점수 | 사람이 이해할 수 있는 의미 |
|---|---:|---:|---|
| Faithfulness | 0.9795 | **1.0000** | 평가자는 전체 답변의 주장들이 제공된 생성 문맥으로 뒷받침된다고 판단했습니다. 현장 진단까지 100% 정확하다는 뜻은 아닙니다. |
| Answer Relevancy | 0.5280 | **0.5280** | 질문과 답변의 관련성을 이 정도로 측정했습니다. 원인 관계를 묻는 질문에 점검·조치까지 답한 범위 차이와, 영어 역생성 질문을 사용하는 평가 방식의 영향을 함께 고려해야 합니다. |
| Context Precision | 0.7023 | **0.7750** | 기준 답변에 유용한 근거를 검색했지만 검색 결과의 순서·구성에는 개선 여지가 있다는 결과입니다. 문서의 77.5%가 맞았다는 뜻은 아닙니다. |
| Context Recall | 0.8750 | **1.0000** | 기준 답변의 핵심 사실을 뒷받침할 근거는 검색 문맥에 들어 있었습니다. |
| Factual Correctness F1 | 0.4404 | **0.4800** | 짧은 GT와 전체 답변의 주장 범위가 달라 F1이 낮게 나왔습니다. 답변의 정답률이 48%라는 뜻은 아닙니다. |

특히 **F1 0.48**은 실제 평가자 판단을 풀어 보면 이해하기 쉽습니다.

- 평가자는 전체 RAG 답변을 **19개 주장**으로 나눴습니다.
- 그중 **6개 주장**은 짧은 GT가 뒷받침한다고 판정했습니다. 나머지 13개는 이 GT의 범위 밖으로 판정됐으며, 곧바로 거짓 주장 13개를 뜻하지 않습니다.
- 반대로 GT의 핵심 주장 **2개는 실제 RAG 답변에 모두 포함**됐다고 판정했습니다.
- 이 판정으로 계산한 공식 F1은 `2 × 6 / (2 × 6 + 13 + 0) = 0.48`입니다. 원래 매뉴얼에 대한 충실도와 짧은 GT와의 일치도는 서로 다른 평가입니다.

위 주장 수는 Factual Correctness의 분해 결과입니다. Faithfulness가 분해한 주장 수와 동일하다고 가정하지 않습니다.
판정 원본은 [judge_traces.jsonl](results/judge_traces.jsonl), 계산 근거는 [factual_breakdown.json](results/factual_breakdown.json)에 있습니다.

### 5. 결론적으로 성능을 어느 정도로 받아들이면 되나요?

**이 사례에서는 매뉴얼 근거를 찾아 원인 관계의 핵심을 설명하고, 점검 후보까지 제공하는 정비 안내 보조 기능이 작동했습니다.**
다만 단순한 원인 질문에도 답변 범위가 넓어지는 경향이 있어, 질문에 필요한 내용부터 간결하게 답하도록 개선할 여지가 있습니다.
높은 Faithfulness만으로 모든 답변이 정확하다고 결론 내리거나, 낮은 F1만으로 답변 절반이 틀렸다고 결론 내리면 안 됩니다.

이 예시는 평균 점수에 가까운 **E 코드 질문 한 건**입니다. 일반 질문의 약점까지 모두 대표하지는 않습니다.
전체 결과에서는 일반 질문의 Context Precision **0.4433**, Context Recall **0.7037**로 E 코드 질문보다 낮았으므로,
코드 없는 질문에서 필요한 표·절차·안전 경고를 찾는 검색 품질도 별도로 개선해야 합니다.

GT 역시 사람이 검증한 정답이 아니라 자동 생성한 합성 reference입니다.
따라서 이번 수치는 **현재 시스템의 강점과 개선 대상을 찾는 자동 평가 결과**로 보고, 장비 진단 정확도나 서비스 합격률로 단정하지 않습니다.
