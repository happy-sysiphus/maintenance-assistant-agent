## 1. R2 순서를 바꾼 이유 (요청 11 · 12)

| 요청 | 결과 |
|---|---|
| 11. 이유 보이기 | **반영** — 상황 화면(원인 목록 위) · 점검 화면(원인 1 목록 위) |
| 12. 타입 · 주석 · 안내 | **반영** — `field_order` 타입, 주석 3곳, 안내 문구 |
| 13. 모든 점검 기록해야 다음 | **안 함** — 현장에서 막으면 진행이 어렵다. 지금처럼 한 항목만 기록해도 넘어간다 |

```
현장 기록으로 순서를 바꿨어요
지난 해결 기록에서 '절대 드리프트 감시와 상태 비트 확인'이 이상으로 나온 게 4건(설비 2대)이라
이 점검을 먼저 보여요. 점검 내용은 매뉴얼 그대로예요.
```

- 이전 기록과 같은 모양(회색 바탕, 쪽 칩 없음). 앞당긴 점검 항목 옆에 "현장 기록으로 먼저".
- **카드의 첫 점검이 `field_order.lead`일 때만** 보인다(`fieldLead`, api `first_check`와 같은 기준). 조치 보호로 못 옮긴 카드는 `field_order`가 있어도 안 보인다.
- api 문장(`field_order.note_ko`, `field_memory.note_ko`)은 점검 id(E029-K2)가 들어 있어 쓰지 않고, 카드의 점검 이름으로 다시 쓴다.
- 순서가 고정된 케이스(`field_order` + 판단 · 조치 · 결과)에서 안내 생성이 실패하면 "새로고침하면 다시 만들어요" 대신 "이미 기록한 내용이 있어 이 고장은 이 항목으로 이어서 해요".
- 주석 수정: `parts.tsx`(FieldMemoryNote), `OverviewPage.tsx`, `lib/caseFlow.ts` 맨 위.

**확인 상태**: 코드 · 타입 체크 · 빌드만. 실제 화면은 못 봤다.
- Neo4j Aura(`7a100627`)가 DNS에서 없음(NXDOMAIN). RAG가 실패하면 매핑 대체 카드가 쓰이고, 대체 카드는 조치 보호로 순서를 바꾸지 않는다(근영 테스트 `test_r2_script_mapping_card`와 같음).
- E029 해결 종료 4건(설비 2대, K2 이상)으로 `field_order`가 생기는 것까지는 확인했다. Aura를 켜면 그 케이스에서 바로 볼 수 있다.

## 2. 조기 경보 받기 (api)

| 무엇 | 내용 |
|---|---|
| 등급 | `event_type == "early_warning"`이면 `severity: "warning"`(화면 "주의", 주황). 그 밖은 지금처럼 `critical` |
| 묶기 | 묶음 코드 칸을 `store.group_code()`로: 조기 경보는 `"early_warning"`, 그 밖은 `rule_code`. 같은 설비 조기 경보끼리만 열린 케이스에 반복으로 붙는다. **코드 없는 긴급(모델 단독)과 섞이지 않는다** |
| 흔적 | 조기 경보 반복에 `score` · `threshold` · `summary_ko` · `contributing_features`를 남긴다(1분 원시값 `sensor_features`는 크기 때문에 뺌). 처음 알림은 `event`에 전부 있다 |
| 목록 | `/api/cases` 줄에 `event.event_type`(없으면 `"critical"`), `last_detected_at`(마지막 반복 시각) 추가 |
| 현장 기억 | 집계 키 `alarm_key`: 조기 경보는 `"설비|early_warning"`. 모델 단독 긴급(`"설비|"`)의 이전 기록에 조기 경보 닫힘이 섞이지 않는다 |
| 닫기 | 새 주소 없음. 기존 close에 `outcome: "false_alarm"` + `reason`으로 닫는다 |
| 안내 | 코드가 없어 `guidance`는 `no_evidence`(RAG 호출 없음). 센서 정보로 RAG를 부를지는 ML · RAG 결정 |

- 바꾼 파일: `api/main.py`(ingest · summary), `api/store.py`(`group_code`), `api/field_memory.py`(`alarm_key` 한 곳).
- 테스트: `api/tests/test_early_warning.py` 5개 추가 — 주의 · 반복 쌓기, 긴급과 분리, 닫은 뒤 새 케이스, 현장 기억 키 분리(플래그 켬/끔). 전체 89 통과 · 1 건너뜀.
- 긴급이 오면 조기 경보를 같이 닫는 연결은 **하지 않았다**(11/04 회의: 같은 원인 보장 없음).

## 3. 조기 경보 화면

### 작업함

```
● 긴급  test_5  [모델 신호만]  —                          13:40         새 고장  점검 시작
● 주의  test_5  [조기 경보]    고장 가능성 · 확정 아님 3회  11:00 ~ 13:12  새 고장  확인하기
```

- 정렬은 기존 그대로(긴급 먼저) → 주의는 긴급 아래.
- 고장 코드 칸에 주황 점선 "조기 경보", 현상 칸에 "고장 가능성 · 확정 아님" + 반복 수, 발생 칸에 처음 ~ 마지막 시각.
- 버튼은 "확인하기"(대부분 고장이 아니라서 "점검 시작" 대신).

### 상황 화면 (조기 경보 케이스)

왼쪽(그래프 · 신호)은 그대로, 제목만 "조기 경보 전후". 오른쪽은 원인 카드 대신:

```
[조기 경보 · 확정 아님]
10~60분 안에 고장이 날 수도 있다는 신호예요. 고장 코드가 아직 없어 매뉴얼 안내는 없어요.
영향이 큰 신호   US2 작동 허용 신호 흔들림 · 최근 10분 에러 상태 비율 흔들림 · …
이 설비에서 3회  10/03 13:12  이상 점수 0.98
                 10/03 12:05  이상 점수 0.96
                 10/03 11:00  이상 점수 0.97
(이전 기록 — 같은 설비 조기 경보를 닫은 기록이 있으면)
[확인하고 닫기]
[이상을 찾았어요 · 직접 점검해서 기록]
```

- **확인하고 닫기**: 오알람 팝업과 같은 모양. "확인해 보니 어땠나요?" — 이상 없음 / 설비 정지 · 전원 꺼짐 / 정상 작업 중 변동 / 센서 · 신호 문제 / 기타(`EARLY_CHECK_REASONS`, FE 초안) + 메모. 오알람(`false_alarm`)으로 저장한다.
- **이상을 찾았어요**: 기존 수동 점검(코드 없는 고장과 같은 흐름) → 해결 종료.
- 위쪽 바: 주황 "조기 경보". 고장 정보의 고장 코드: "없음 · 조기 경보". 정비일지 문제 칸: "조기 경보 발생".

### 확인 방법과 상태

- ML 예시 알림(`ml/docs/rag_handoff_early_warning.example.json`)의 시각 · 점수만 바꿔 api 수신 주소(`POST /api/ml/handoffs`)로 보냈다: test_5 조기 경보 3건 → 한 줄 "3회", test_2 1건, test_5 모델 단독 긴급 1건 → 따로 한 줄.
- **실제 ML로는 못 봤다.** 조기 경보 판정이 든 모델 번들(11/01 재학습본)이 git에 없고(`.joblib`), FE PC에는 10/06 번들만 있어 `early_warning.model: false`. 번들을 받으면 ML을 `RSW_EARLY_WARNING_HANDOFFS=1`로 켜고 재생하면 api가 지금 경로(`GET /handoffs`)로 그대로 받는다.
