## 먼저: ML 변경 사항에 대한 결정

RAG는 **E012·E016·E028·E029**만 오류 코드로 사용합니다.
S01~S10, 논문 고장 유형 E01~E04, 매분 센서 문서는 사용하지 않습니다.

코드 없는 모델 알림은 자동으로 특정 오류에 분류하지 않습니다. 챗봇의 일반 질문은 코드 없이 가능합니다.

## 1. E 코드로 부르기 + 원인 후보

**답변: 완료했습니다. A/B안의 S 변환은 사용하지 않습니다.**

```python
from rag import answer_question

result = answer_question(
    "이 오류의 의미와 점검·조치를 알려주세요.",
    error_code="E029",
)
```

질문에 E029를 직접 적어도 인식합니다.
Aura의 Situation은 E 코드 네 개이며, 문서별 오류 정의·원인·점검·조치·근거를 연결했습니다.
새 공식 매뉴얼의 명칭을 기준으로 하고 상세 진단 문서는 출처를 구분해 사용합니다.
구판 Festo의 16·28·29는 신형 E016·E028·E029와 의미가 달라 번호만으로 매핑하지 않았습니다.

**화면 합의:** E 코드당 안내 카드 하나입니다. 카드 안에 causes[]를 표시합니다.
causes[].situation_id가 같은 E 코드여도 서로 다른 카드로 만들지 않습니다.
기존 S05~S09 후보별 맞음/아님 → 다음 후보 전환은 사용하지 않습니다.
API의 candidates[]도 해당 E 코드 후보 하나이며, 점검·판단·조치 기록은 기존 저장 API를 사용합니다.

## 3. 답변·조치·점검 기준 분리

**답변: 요청 JSON 구조로 구현했습니다.** 기존 answer와 근거를 제공하면서 다음 필드를 분리합니다.

| 필드 | 내용 |
|---|---|
| sections.interpretation / summary | 해석 또는 일반 질문 답변 / 요약 |
| causes[].situation_id | E 코드 또는 null |
| causes[].name / why | 확인 후보 이름 / 근거 있는 관련 설명 |
| causes[].checks[] | 고정 id·text·cite·criterion |
| checks[].criterion | text·cite 또는 null |
| causes[].actions[] | when·text·cite. 근거 없으면 [] |
| evidence[] | id·doc·page·quote·text·review_needed |
| review_notes | 적용 범위·시각 정보 확인 안내 |

situation_id는 기존 필드명만 유지하며 S 값은 반환하지 않습니다.
점검 ID는 E012-K1과 같이 새 매핑에 고정했습니다. LLM이 새 ID를 만들면 응답 검증에서 거부합니다.
요청 예시의 cite 구조는 유지하고 doc 식별자를 네 문서로 확장했습니다.
답변은 JSON Schema로 생성합니다. 코드 질문의 점검은 허용 ID만 선택하고 세부 텍스트·인용·기준은 프로그램이 검토 매핑에서 연결합니다.
모든 cite의 문서·쪽수와 점검 ID를 검사합니다. 거부 시 validation_errors에 code·message·path를 제공합니다.
검증 실패는 needs_citation_review이며 검증되지 않은 생성 본문을 표시·캐시하지 않습니다.
이는 형식·인용 위치 검사이며 모든 문장에 대한 별도 독립 LLM 의미 검증은 아닙니다.

정상 기준이 없으면 확인 방법을, 그것도 없으면 null을 줍니다.
오류 감시 임계값을 전체 정상 보장으로 바꾸지 않았으며, 설비 파라미터 값은 현장에서 확인하도록 합니다.
문서에 조치가 없는 E012·E028 예시에는 actions=[]가 있습니다.
E016의 보정과 E029의 재시작 안내는 매뉴얼의 수행 조건을 함께 제공합니다. 오류 발생만으로 필수 조치라고 하지 않습니다.

## 4. AI 챗봇: 질문만 호출 + history

**답변: 둘 다 지원합니다. 질문 형식이나 상황 선택을 강제하지 않습니다.**

```python
general = answer_question("이동 보정에는 어떤 전극 캡을 사용하나요?")
followup = answer_question(
    "그럼 새 캡 조건을 다시 알려주세요.",
    history=[
        {"role": "user", "text": "이동 보정과 전극 캡을 설명해 주세요."},
        {"role": "assistant", "text": "앞서 표시한 답변"},
    ],
)
```

일반 질문과 코드 질문은 같은 JSON입니다.
일반 질문의 error_code·causes[].situation_id는 null일 수 있고 causes=[]도 허용됩니다.
질문 문맥은 벡터·키워드 검색과 LLM 생성에 반영합니다.
history는 최근 8개 메시지, 각 1,500자까지 사용합니다. 대화는 자동 저장하지 않습니다.
이전 답변은 문맥이며 매뉴얼 사실의 근거로 사용하지 않습니다.
사진은 분석하지 않습니다.

API의 POST /api/assistant/ask는 기존 question·photos·history 요청을 받습니다.
기존 blocks·caution·situation_ids와 구조화 결과를 함께 제공합니다.
일반 질문의 situation_ids는 []입니다. S ID로 먼저 분류하는 임시 챗봇은 제거했습니다.
수동 검색도 네 문서의 키워드 검색으로 교체했습니다.

## 6. API에서 RAG 호출 + 팀원 실행 환경

**답변: Aura에 구축하고 API에 연결했습니다. 접속정보·키는 개인적으로 전달합니다.**

- Aura 실제 조회 확인: Situation 네 개, 문서 네 개, 198페이지, 저장 청크 905개(원본 882 + 인용 23), 실제 본문 검색 대상 684개. 이미지 자리표시자는 제외합니다.
- 기존 S 그래프는 rag/var/backups/에 백업 후 교체했습니다.
- 키워드·벡터 인덱스 ONLINE 상태와 네 코드 근거 조회를 확인했습니다.
- api/guidance.py는 E 코드를 실제 RAG 함수에 전달합니다. 새 한국어 안내는 최초 상세 조회에서 생성·저장합니다.
- api/assistant.py는 질문·history를 실제 RAG로 전달합니다.
- 정상 생성 결과는 캐시를 재사용합니다. 문서·매핑·모델·질문·대화 문맥이 바뀌면 캐시 키가 달라집니다.
- 생성 중 입력된 작업자 기록도 보존하며, 기록 저장 요청에는 RAG를 재호출하지 않습니다.

팀원은 OpenAI 키 외에 Aura URI·DB 사용자명·DB 비밀번호·실제 DB 이름도 필요합니다.
Neo4j Desktop 설치나 그래프 재구축은 필요하지 않습니다.

```powershell
# 저장소 루트
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r api/requirements.txt
Copy-Item rag/.env.example rag/.env
# rag/.env에 개인적으로 전달받은 설정 입력
cd api
python -m uvicorn main:app --port 9000
```

키·비밀번호는 서버의 rag/.env에 넣고 Git과 VITE_ 변수에는 넣지 않습니다.
회사/Windows 인증서가 필요한 환경은 RAG_SYSTEM_TRUST=1로 OS 신뢰 저장소를 사용합니다. 인증서 검증은 유지합니다.

팀원 실행 절차는 RAG README 4절을 따릅니다. 공용 Aura에 준비된 그래프·인덱스를 그대로 사용합니다.
필수 그래프는 검토된 매핑으로 구축해 build 자체에는 OpenAI 호출이 없습니다.
build --skip-llm도 같은 필수 연결을 만듭니다. use_llm=False는 답변 생성 없이 근거만 조회하는 별도 옵션입니다.
동일 문서 재구축에서는 기존 임베딩을 재사용합니다.

## 검증 및 UI에 남은 변경

오프라인 회귀 테스트 **22개 통과**: python -B -m unittest discover -s rag/tests -v.
인용 문서 혼동·잘못된 ID·빈 값·history·중복 알림·기록 보존·PDF 경로를 검사합니다.
실제 검증은 네 코드 생성 4건, 일반 질문·이어 묻기 2건, Aura 근거 조회, 캐시와 API 연결입니다.
동일 매핑 재구축 후 인덱스 갱신은 OpenAI 호출 0회였고, 공유 파일의 비밀값 검사와 Git 제외 규칙 10건도 통과했습니다.
이는 대표 사례 검증이며 모든 질문·설비 상태의 품질 보장을 뜻하지 않습니다.

초기 임베딩·대표 생성의 표준 토큰 단가 기준 예상 비용은 **약 0.04달러**였습니다. 아래 오류 수정 재검증을 합쳐도 **약 0.08달러**로, 승인한 2달러 이내입니다.
완료된 생성 6건의 입력 23,334·출력 3,592토큰, 문서 임베딩 79,910토큰을 기준으로 했습니다.
캐시 할인·실패 요청·계정별 추가 요금 등은 실제 청구서와 다를 수 있습니다.

UI 담당자가 반영할 것은 다음 네 가지입니다.

1. S 기반 후보 전환을 E 코드당 안내 하나로 변경.
2. 네 문서의 doc 타입·표시 이름·PDF 링크 반영.
3. guidance.sections·causes의 한국어 설명·조치와 null/빈 배열 표시.
4. 첫 생성의 로딩 표시. API 주소·기존 기록 저장 방식은 유지.

기존 S 기반 저장 케이스는 작업 기록 손실을 막기 위해 자동으로 E 코드로 재해석하지 않습니다.
새로 생성되는 케이스부터 새 계약을 사용합니다.
UI mock·화면 코드는 이번 작업에서 수정하지 않았습니다.

소스·PDF·매핑·예시 네 개·테스트 한 파일만 공유 대상으로 둡니다.
.env·백업·파싱·이미지·임베딩 중간물·캐시·임시 검증 기록은 모두 Git 제외 경로에 있습니다.

## 실제 사용 오류 수정 (2026-10-28, 응답 처리 v2)

- 사용자 질문 “원인 후보와 점검 기준, 조치를 알려주세요.”에서 needs_citation_review를 재현했습니다.
- 원인: 생성 스키마가 점검 ID를 자유 문자열로 허용해 E012-K3이 생성됐지만, 검증기는 고정 ID E012-K1/K2만 허용했습니다.
- 수정: 코드별 생성 스키마를 허용 ID 선택으로 제한하고, 점검의 본문·기준·인용은 서버가 검토된 매핑에서 연결합니다.
- 추가 수정: E 코드 의미를 보충 검색에 반영하고, 이미지 자리표시자·이웃 진단 행을 직접 근거에서 제외합니다. Neo4j의 DEPRECATION 분류 알림만 CLI에서 제외하며 오류·다른 경고는 유지합니다.
- 검증: 같은 사용자 질문을 캐시 없이 2회 실행해 모두 ok, E 코드 예시 4건과 일반 질문 1건도 ok였습니다. 공개 예시 네 개를 갱신했습니다.
- 구버전 캐시와 API 저장 안내는 response_version으로 구분하고 새 처리 경로로 갱신합니다. API 실행 중이면 재시작이 필요합니다.
