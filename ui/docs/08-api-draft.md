**확인 · 부탁**

1. **최신 모델 파일:** 구글 드라이브의 `baseline_ensemble.joblib`은 `created 2026-09-29`입니다. 레포 기록(`models/baseline_ensemble_metrics.json`)은 10-06 재학습본(critical_sustain 10, restart_hold, 코드별 쿨다운)입니다. 10/6 파일을 드라이브에 올려 주실 수 있을까요? (9/29 파일로도 돌아가지만 모델 단독 긴급 알림이 더 많이 나옵니다.)
2. **핸드오프 push 대상:** `sensor_features_for_rag.md`에 "핸드오프는 UI용으로만 ML 안에 남는다"고 되어 있어서, 핸드오프 push(`RSW_RAG_URL`)를 api가 받는 것으로 써도 될지 확인 부탁드립니다. 매분 센서 문서(`RSW_RAG_SENSOR_URL`)는 RAG 쪽 그대로입니다.
3. **알 수 있게만:** test_0에서 E029가 매일 19:35에 반복돼 알림이 여러 건 옵니다. api는 같은 설비 · 같은 코드의 열린 케이스에 "반복"으로 묶습니다.

## RAG 담당에게

**api가 지금 하는 것**
- 고장 코드 → 상황 ID 임시 표(E012→S01 …)로 바꾼 뒤, `rag/data/situation_mapping.json`에서 점검 순서 · 근거 쪽 · Festo 오류 번호를 읽어 화면에 줍니다. `answer_question()`은 아직 부르지 않습니다.
- PDF 두 개(`rag/data/festo_manual.pdf`, `rsw_situations.pdf`)를 api가 화면에 내려줍니다. **RAG가 PDF를 따로 주실 필요는 없습니다.**

**붙일 자리:** `api/guidance.py` 한 파일입니다. 여기서 `answer_question()`을 부르게 바꾸면 화면까지 이어집니다.

**결정 · 부탁 (자세한 것은 [`07-rag-requests-now.md`](07-rag-requests-now.md))**
1. 입력을 무엇으로 받을지 — E 코드? 상황 ID? 원인 후보(S05~S09)는 RAG가 골라 줄 수 있는지. **이게 정해져야 화면의 "원인 후보 → 점검 → 맞나요?" 흐름이 이어집니다.**
2. 답을 칸으로 — 특히 조치(조건 + 할 일 + 근거 쪽). 지금은 원인 후보 문장 안에 섞여 있습니다.
3. 점검 항목별 근거 쪽 — 지금은 상황 단위라 모든 점검 항목의 "이상일 때"가 같은 쪽(예: Festo 오류 12, 90쪽)으로 나옵니다.
4. api에서 부를 때 필요한 것 — Neo4j 접속 정보, OpenAI 키(`.env`로 받겠습니다), 답 하나에 걸리는 시간.

## 통합 · 데모 담당에게

**데모 순서 (10/23 로컬에서 확인)**
1. ML 서버 켜기 (`:8000`, 모델 파일 · test CSV 필요 — `ml/README` 0절 드라이브)
2. api 켜기 (`:9000`) → 화면 켜기 (`:5173`, `VITE_USE_MOCK=false`)
3. `python .py/replay.py test/test_0.csv --chunk-s 600` → 약 2분 뒤 작업함에 E012 · E029 · 모델 신호 케이스가 생김
4. E012 케이스 → 상황(실제 그래프) → 점검(매뉴얼 PDF) → 판단 → 조치 → 결과 → 정비일지 → 이력

**아직 결정이 필요한 것**
- 멘토 요구 "조치 후 재검증": 공개 데이터에 조치 후 구간이 없습니다. 시뮬레이션으로 보여줄지 정해야 합니다.
- 데모를 실시간처럼 보여줄지(`--speed`로 느리게 흘림) 미리 흘려 둔 결과로 보여줄지.
- 그래프는 알림을 바로 받을 때만 채워집니다(ML trace가 최근 6시간만 보관) → 데모 때는 push로 켜는 것을 추천합니다.
