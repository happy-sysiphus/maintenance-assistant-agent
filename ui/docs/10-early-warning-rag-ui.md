# 10. 조기 경보 RAG 화면 개발 안내

2026-11-11 · UI 담당자용

ML의 조기 경보를 연 작업자가 **무엇이 변했는지 보고, 점검할 후보를 고르고, 실제 해결 결과를 남기는 흐름**을 만듭니다. 기존 케이스의 매뉴얼 보기·점검·조치·일지 화면을 재사용할 수 있습니다. 화면을 구분하는 기준은 케이스의 `event_type: "early_warning"`입니다.

이 문서에서 제시하는 필드는 현재 로컬 RAG 응답을 기준으로 합니다. HTTP 주소와 케이스 응답 내 배치 위치는 API 담당자와 정하면 됩니다. RAG 함수와 저장 요청의 상세 형식은 [API·UI 연동 계약](../../rag/docs/early-warning-integration.md#rag-호출-계약)을 참고하세요.

## 1. 첫 화면에 센서 소견 또는 이전 해결 카드 표시

**왜 필요한가요?** 조기 경보는 오류 코드가 뜨기 전에 나타날 수 있습니다. 작업자는 어떤 센서가 어느 방향으로 변했는지와, 같은 상황에서 이미 해결한 기록이 있는지부터 알아야 합니다.

- 화면에 **조기 경보 · 원인 미확정**을 표시합니다. `observations[]`의 센서명, 방향, 관측 범위를 사용합니다. 상태 신호는 전환이 확인된 경우 `transitions[]`의 시점을 함께 표시합니다. `direction: null`이면 방향을 표시할 관측이 부족하거나 뚜렷한 방향이 없는 상태로 표현합니다.
- `automatic_card`가 있으면 **이전 해결 사례**를 바로 표시합니다. 카드에는 사례 제목, 점검·조치, PDF 근거, 해결 건수, 과거에 수행한 조치를 보여줍니다. **맞아요**를 누르면 해당 카드를 선택하고, **아니에요**를 누르면 다른 후보를 요청할 수 있게 합니다.
- `automatic_card`가 비어 있으면 센서 소견, **원인 후보 보기**, **오알람 닫기**를 제공합니다. `history_candidates`가 있으면 **이전 해결 사례**라는 표시와 함께 보여줍니다.
- 상세 조회는 RAG의 `inspect()`에 대응합니다. 이 호출로는 Claude를 부르지 않으므로 케이스를 열 때 새 후보 생성 응답을 기다릴 필요가 없습니다.

| `status` | 화면에서 보여줄 상태 |
|---|---|
| `automatic` | **이전 해결 사례** 카드와 맞아요·아니에요 |
| `candidates` | 이전 해결 후보와 원인 후보 보기 |
| `new_pattern` | 연결된 해결 이력이 없는 경보, 센서 소견과 원인 후보 보기 |
| `insufficient_channels` | 확인 가능한 센서 소견과 원인 후보 보기. 자동 카드는 보류 |
| `pending` | 관련 해결 기록을 반영 중이며 자동 카드는 보류 |
| `conflict`, `counterexample` | 이전 사례 후보를 확인할 수 있고, 자동 카드는 보류 |
| `memory_unavailable` | 이전 이력을 지금 조회할 수 없음을 표시하고 후보 요청이나 수동 검색을 제공 |

## 2. 원인 후보 보기와 정비 카드

**왜 필요한가요?** 작업자가 후보를 요청한 시점에 매뉴얼 검색과 Claude 호출이 진행됩니다. 카드에는 관측, 제안 이유, 매뉴얼 근거가 각각 있으므로 작업자가 후보를 비교할 수 있습니다.

1. 버튼을 누르면 현재 케이스와 `event_id`를 지정해 후보 요청을 보냅니다. 요청 중 상태를 보여주고 연속 클릭으로 같은 요청이 여러 번 나가지 않게 합니다.
2. `history_candidates[]`는 **이전 해결 사례**, `candidates[]`는 **매뉴얼 후보**로 표시합니다. 새 후보의 `reason`은 센서 소견을 바탕으로 이 사례를 검토할 이유입니다. `source`는 PDF 근거로 따로 표시합니다.
3. 사례 선택과 조치 기록에는 `manual_case_id`를 사용합니다. 후보를 다시 불러왔을 때 순서가 바뀔 수 있으므로 화면 순번으로 선택을 연결하면 다른 사례에 기록이 붙을 수 있습니다.
4. `no_evidence`일 때는 검색에 맞는 근거가 부족했음을, `generation_error`일 때는 후보를 가져오지 못했음을 표시합니다. 응답에 남은 이전 해결 사례는 계속 보여주고 **수동 매뉴얼 검색**으로 이동할 수 있게 합니다.

카드에서 사용할 필드는 다음과 같습니다.

| 필드 | 표시 방법 |
|---|---|
| `title`, `reason`, `coverage_note` | 사례 제목, 검토할 이유, 매뉴얼 적용 조건. `reason`은 새 후보에 있을 때 표시 |
| `checks[]`, `actions[]` | 등록된 매뉴얼 점검과 조치. 조치 목록이 비어 있으면 매뉴얼에 적힌 조치 없음으로 표시할 수 있음 |
| `source.doc`, `source.page`, `source.quote` | 기존 PDF 뷰어를 해당 쪽으로 열고 발췌 근거 표시. 페이지는 PDF 파일 기준 1부터 시작 |
| `origin` | `history`는 이전 해결 사례, `generated`는 매뉴얼 후보 |
| `applicable_cases`, `repairs[].actual_action` | 이전 해결 건수와 과거 작업자의 실제 조치. 매뉴얼의 `actions`와 구분해 표시 |

## 3. 수동 매뉴얼 검색에서 적용 근거 선택

**왜 필요한가요?** 작업자가 실제로 확인한 근거를 저장하면 그 해결 기록을 같은 센서 패턴에 연결할 수 있습니다. 자유 메모만 남기면 어느 PDF 항목을 적용했는지 찾기 어렵습니다.

- 기존 매뉴얼 검색 화면에 현재 `event_id`와 질문을 전달합니다. 후속 질문을 지원하는 화면은 대화 이력도 전달할 수 있습니다. 응답의 `hits[]`에서 문서명, PDF 쪽, 발췌문을 표시하고 **이 근거 선택**을 제공합니다.
- 검색 근거의 `source`에는 `evidence_id`, `doc`, `revision`, `sha256`, `page`, `quote`가 있습니다. UI가 고른 `evidence_id`를 API에 보내면 API가 실제 검색 응답의 근거와 연결하도록 협의합니다.
- 이미 등록된 매뉴얼 사례를 적용한 경우에는 `manual_case_id`로 선택을 남깁니다. 목록 밖의 근거를 적용하면 그 근거를 해결 기록에 저장하고, 검토 후 기존 사례에 연결하거나 새 사례로 등록합니다.
- 다른 후보나 검색 결과를 계속 보더라도 선택한 근거를 화면에 유지합니다. 사용자가 근거를 바꾸면 적용 근거 표시와 종료 요청의 선택값을 함께 갱신합니다.

## 4. 해결 종료와 자동 카드 반례

**왜 필요한가요?** 이전 사례는 작업자가 실제로 해결했다고 확인한 경우에만 재사용할 수 있습니다. 화면에서 카드를 고른 시점과 해결한 시점을 분리해야 해결 건수가 정확합니다.

1. **맞아요**는 사례 선택으로 기록합니다. 정비 후 종료할 때는 **실제 수행한 조치**를 입력하고 **해결됐어요**를 확인합니다.
2. 종료 요청에 케이스 ID, 판단에 사용한 `event_id`, `actual_action`, `worker_confirmed: true`를 보냅니다. 선택한 등록 사례의 `manual_case_id` 또는 수동 검색에서 고른 근거를 함께 연결합니다. API가 경보 원본과 종료 시각을 붙입니다.
3. 자동 카드에서 **아니에요**를 선택했으면 해당 카드 ID가 API에 남아야 합니다. 그 후 다른 사례로 실제 해결하면 API는 거절했던 카드 ID를 `rejected_auto_case_id`로 연결합니다. 거절만 눌렀거나 오알람·미해결로 끝난 건은 자동 카드의 확정 반례가 되지 않습니다.
4. 종료 화면은 케이스 종료와 이력 반영 상태를 보여줍니다. API가 재시도 중이면 **해결 기록 반영 중**, 새 수동 근거가 검토를 기다리면 **근거 검토 대기**로 표시합니다. 오알람 종료에는 기존 사유와 메모 흐름을 사용합니다.

### UI에서 쓸 수 있는 응답 예시

아래는 케이스 첫 화면을 만들 때 필요한 **RAG 응답 필드 발췌**입니다. 데이터는 합성 예시입니다.

```json
{
  "event_id": "EW-0042",
  "status": "automatic",
  "observations": [
    { "channel": "c3", "name": "electrode position", "direction": "up" },
    { "channel": "c5", "name": "balance pressure", "direction": "down" },
    { "channel": "c10", "name": "US2 operating enable", "direction": "up" }
  ],
  "automatic_card": {
    "manual_case_id": "manual:E012-C2",
    "origin": "history",
    "title": "MPYD 케이블과 공급 압력 점검 후보 (구판 보충)",
    "applicable_cases": 2,
    "source": { "doc": "festo", "page": 90 }
  }
}
```

첫 화면에서 `status`가 `new_pattern`이고 `automatic_card: null`이면 센서 소견과 원인 후보 보기 버튼을 보여줍니다. 버튼의 응답은 `history_candidates[]`와 `candidates[]`입니다. 해결 종료와 검토 요청 전체 예시는 [해결 종료 입력](../../rag/docs/early-warning-integration.md#해결-종료-입력)에 있습니다.

## API 담당자와 먼저 맞출 내용

| 합의할 내용 | 필요한 이유 |
|---|---|
| 케이스 상세, 후보 요청, 수동 검색, 해결 종료의 주소와 응답 위치 | 상세 조회에서 후보 생성이 함께 실행되지 않도록 호출을 분리 |
| 반복 경보의 `event_id` 선택과 원본 센서 데이터 보존 | 첫 경보가 아닌 반복 경보를 보고 정비했다면 해당 센서 패턴에 기록을 연결 |
| 카드와 수동 검색 결과의 선택값 보존 | 새로고침이나 순서 변경 후에도 적용한 근거와 조치 기록이 연결되도록 함 |
| 저장 완료·반영 중·검토 대기의 상태 계약 | SQLite 케이스 종료 이후 Neo4j에 반영되는 시간을 화면에서 구분 |

## 완료 확인

- 자동 카드가 있는 경보는 상세 화면에서 곧바로 카드와 PDF 근거를 확인할 수 있습니다.
- 새 경보는 센서 소견을 보여주고, 후보 요청 후 로딩·성공·근거 없음·실패에 맞춰 화면이 바뀝니다.
- 수동 검색에서 고른 근거와 수행 조치가 해결 종료까지 같은 `event_id`에 연결됩니다.
- 오알람으로 닫는 흐름, 자동 카드 거절 후 다른 후보로 이어지는 흐름, 반복 경보를 선택하는 흐름을 확인합니다.
- 기존 E 코드의 카드·일지 화면에서도 이전 기록을 그대로 읽을 수 있습니다.
