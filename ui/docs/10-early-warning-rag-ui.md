# 10. WARNING 화면 연동과 UI 검수 안내

2026-11-11 · UI 담당자용 · 로컬 통합 브랜치 `fix/warning-shared-aura` (`c6f0db1` 기준)

**WARNING 화면과 API 연결은 이미 구현돼 있습니다.** UI 작업은 기존 화면을 기반으로 오류 안내와 입력 보존을 보완하고, 팀 환경에서 실제 ML 경보부터 Aura 이력 재사용까지 확인하는 것입니다. 화면은 API를 통해 센서 소견, 매뉴얼 후보와 공용 해결 이력을 받습니다. [WARNING 화면 코드](../src/pages/case/WarningPage.tsx) · [API 구현 명세](../../api/docs/warning-api-20261111.md)

## 1. 현재 화면에서 되는 것

| 화면 단계 | 구현된 동작 |
|---|---|
| **경보 열기** | 케이스의 `event_type`이 `early_warning`이면 WARNING 화면을 엽니다. 센서 이름, 상승·하락·방향 미확정, 관측 초와 상태 전환을 표시합니다. 상세 조회에서는 Claude를 호출하지 않습니다. |
| **경보와 후보 선택** | 대표 경보와 원본이 보존된 반복 경보를 선택할 수 있습니다. 자동 카드가 있으면 즉시 표시합니다. **원인 후보 보기**를 누르면 매뉴얼 후보를 요청합니다. **아니에요**를 누른 자동 카드는 해당 경보의 선택 가능한 목록에서 빠집니다. |
| **직접 매뉴얼 검색** | 현재 질문으로 검색하고 PDF의 해당 쪽을 열거나 **이 근거 선택**을 할 수 있습니다. 질문마다 독립적으로 검색합니다. |
| **점검·조치 기록** | 선택한 근거를 유지하며 점검 결과, 작업자, 실제 조치를 임시 저장할 수 있습니다. 새로고침하면 저장한 입력을 복원합니다. |
| **종료 및 이력 확인** | 실제 해결 확인과 일지 승인이 있어야 해결 종료할 수 있습니다. 종료 뒤 화면은 읽기 전용이며 Aura 반영 중·완료·수동 근거 검토 대기·실패를 표시합니다. 오알람은 기존 종료 흐름을 사용합니다. |

UI 통합 테스트는 합성 경보와 테스트용 검색·이력 응답으로 화면의 주요 조작을 검증했습니다. 별도 API 테스트에서는 실제 공용 Aura에 해결 두 건을 반영하고 다음 경보의 자동 카드 반환을 확인했습니다. 팀 환경에서는 이 두 검증을 실제 브라우저와 ML 경보로 이어서 확인해야 합니다.

## 2. UI 담당자에게 요청할 수정

### 2.1 센서 형식 오류를 연결 실패와 구분

- **현재 상태** · 전용 WARNING 조회가 `422`를 반환하면 화면에서 다른 조회 오류와 똑같이 **경보를 불러오지 못했습니다**와 **다시 시도**를 표시합니다. 구형 경보는 요청을 반복해도 v1.4 원본이 생기지 않습니다.
- **수정할 내용** · 전용 조회의 `422`에는 **이 경보에는 분석할 센서 원본이 없습니다. ML 핸드오프를 확인해 주세요**처럼 입력 문제를 표시합니다. 케이스 기본 정보는 유지하고 분석에 필요한 버튼은 비활성화합니다. 연결 오류나 서버 오류에는 재시도를 제공합니다. 케이스 상세의 `warning_rag.status: "invalid_input"`와 공통 요청 함수의 `ApiError.status`를 참고할 수 있습니다.
- **완료 기준** · 구형 경보에서는 센서 원본 확인 안내가 나오고, 일시적인 API 오류에서는 재시도 후 화면을 복구할 수 있습니다. [조회 처리](../../api/main.py) · [공통 API 요청 함수](../src/lib/api.ts)

### 2.2 근거 선택에 실패해도 입력한 점검 결과를 유지

- **현재 상태** · 카드나 PDF 근거를 선택하는 버튼을 누르는 즉시 기존 점검 결과와 확인 체크가 초기화됩니다. 선택 요청이 실패하면 서버의 적용 근거는 이전 상태인데 화면의 점검 입력만 사라질 수 있습니다.
- **수정할 내용** · 서버가 **다른 근거** 선택을 성공으로 응답한 뒤 점검 결과·해결 확인·일지 승인을 초기화합니다. 요청이 실패하면 기존 근거, 점검 결과, 작업자와 조치 내용을 유지합니다. 배경 조회로 상태를 갱신할 때도 편집 중 입력을 덮어쓰지 않습니다.
- **완료 기준** · 기존 카드에서 점검 결과를 입력한 뒤 다른 근거 선택 요청을 실패시켜도 기존 입력이 남습니다. 다른 근거 선택이 성공하면 새 카드의 점검 항목으로 전환됩니다. [근거 선택 화면 코드](../src/pages/case/WarningPage.tsx)

### 2.3 수동 검색 결과에서 PDF 원문 확인이 필요한 항목 표시

- **현재 상태** · API는 검색 결과의 `hits[].review_needed`를 내려줍니다. 화면에는 현재 PDF 링크와 발췌문만 표시됩니다.
- **수정할 내용** · `review_needed: true`인 검색 결과에 **PDF 원문 확인 필요**를 표시하고 해당 문서·쪽 링크를 함께 둡니다. 이 표시는 문서 근거의 확인 필요 여부입니다. 해결을 저장한 뒤 운영자 검토를 기다리는 **수동 근거 검토 대기**와 문구를 구분합니다.
- **완료 기준** · 같은 검색 결과에 일반 근거와 확인이 필요한 근거가 함께 있어도, 어느 항목의 원문을 확인해야 하는지 화면에서 바로 찾을 수 있습니다. [수동 검색 응답 코드](../../rag/early_warning.py)

## 3. 화면 순서대로 보는 API 계약

### 3.1 첫 화면과 반복 경보 선택

1. `GET /api/cases/{case_id}`로 케이스를 열고 `event.event_type`으로 WARNING 화면을 선택합니다.
2. `GET /api/cases/{case_id}/warning?event_id={event_id}`로 실제로 판단할 경보를 조회합니다. 대표 경보의 ID는 `event.event_id`, 반복 경보의 ID는 원본이 있는 `repeats[].event_id`입니다.
3. `observations[]`의 `name`, `direction`, `observed_seconds`, `transitions[]`를 표시합니다. `direction: null`이면 **방향 미확정**입니다. 상태 전환 시각은 센서 블록 시작 기준입니다.
4. `automatic_card`가 있을 때 **이전 해결 사례**를 바로 표시합니다. 자동 카드 유무는 이 필드를 따릅니다. 센서 변화와 카드가 표시돼도 원인은 미확정 상태로 보여줍니다.

| 조회 상태 `status` | 화면 표시 |
|---|---|
| `automatic` | 자동 카드와 **맞아요 / 아니에요** |
| `candidates` | 이전 해결 후보와 **원인 후보 보기** |
| `new_pattern`, `insufficient_channels` | 센서 소견과 **원인 후보 보기**. 채널 부족은 이유를 표시 |
| `pending`, `conflict`, `counterexample` | 자동 표시 보류 사유와 남아 있는 후보 |
| `memory_unavailable`, `feedback_disabled` | 이력 조회 불가 또는 재사용 꺼짐 안내 |

**같은 `event_id`를 해결 종료까지 유지합니다.** 대표 경보 대신 반복 경보를 보고 정비했다면 후보 요청, 검색, 선택, 임시 저장과 종료에 그 반복 경보의 ID를 보냅니다. 화면의 `case_id`는 API 주소에 사용합니다. 공유 해결 건의 집계는 API와 RAG가 처리합니다.

### 3.2 후보 요청, 수동 검색, 근거 선택

아래 경로는 모두 `/api/cases/{case_id}/warning` 뒤에 붙습니다.

| 작업 | 호출 | 요청 및 표시 |
|---|---|---|
| **원인 후보 보기** | `POST /candidates` | `event_id`. `history_candidates[]`는 **이전 해결 사례**, `candidates[]`는 **매뉴얼 후보**로 표시합니다. `no_evidence`나 `generation_error`는 문구를 구분하고 수동 검색으로 이어갈 수 있게 합니다. |
| **맞아요 / 이 사례 선택** | `POST /select` | `event_id`와 `manual_case_id`. 선택은 실제 해결 확인과 별도입니다. |
| **아니에요** | `POST /reject` | `event_id`. 갱신된 목록에서 거절한 사례를 제거합니다. 다른 후보 요청과 수동 검색을 계속할 수 있습니다. |
| **직접 매뉴얼 검색** | `POST /manual` | `event_id`, 현재 `question`, `explain: true`. `hits[]`의 PDF 근거와 `notes[]`의 설명을 보여줍니다. |
| **이 근거 선택** | `POST /select` | `event_id`와 검색 응답의 `hits[].source.evidence_id`. API가 그 경보에서 실제로 반환한 근거를 찾아 연결합니다. |

카드에는 **검토 이유**(`reason`), **매뉴얼의 점검·조치**(`checks[]`, `actions[]`), **과거에 실제로 수행한 조치**(`repairs[].actual_action`)를 구분해 표시합니다. `source.doc`와 `source.page`로 PDF를 열고 `source.quote`를 근거 발췌문으로 표시합니다. `page`는 PDF 파일 기준 1부터 시작합니다. 카드 선택에는 목록 순번 대신 `manual_case_id`를 사용합니다.

### 3.3 임시 저장, 해결 종료, Aura 반영 상태

- **임시 저장** · `PUT /draft`에 `event_id`, `worker`, `actual_action`, `checks`를 보냅니다.
- **해결 종료** · `POST /resolve`에 아래 값을 보냅니다. 적용 근거는 앞에서 `POST /select`로 선택한 값을 API가 사용합니다. 해결 확인과 일지 승인은 작업자가 각각 체크합니다.
- **오알람** · `POST /api/cases/{case_id}/close`에 기존 오알람 사유와 메모를 보냅니다. 오알람은 RAG 해결 이력에 들어가지 않습니다.

```json
{
  "event_id": "EW-0042",
  "worker": "작업자",
  "actual_action": "공급 압력을 점검하고 정상 복귀를 확인함",
  "worker_confirmed": true,
  "log_approved": true,
  "checks": {}
}
```

`checks`를 채울 때는 선택한 카드의 실제 점검 ID와 `normal`, `abnormal`, `unchecked` 중 하나를 사용합니다.

**케이스 종료와 Aura 반영 완료를 화면에서 구분합니다.** `resolve`가 성공하면 케이스는 닫히고, 공용 이력 반영은 백그라운드에서 이어집니다. 종료 응답의 `warning_resolution_status`와 이후 WARNING 상세 응답의 `recording_status`를 확인합니다.

| `recording_status` | 종료 화면 문구 |
|---|---|
| `pending` | 해결 기록을 공용 이력에 반영 중입니다. |
| `saved` | 공용 해결 이력 반영 완료 |
| `pending_review` | 해결 기록 반영 완료 · 수동 근거 검토 대기 |
| `failed` | 공용 해결 이력을 반영하지 못했습니다. 관리자 확인이 필요합니다. |

API가 전송을 재시도하고 화면은 상세 조회로 상태를 갱신합니다. 다른 API에서 같은 이력을 볼 수 있는 시점은 Aura 반영 이후입니다. 수동 근거를 검토하는 작업은 운영자 API가 담당합니다. [종료·검토 계약](../../api/docs/warning-api-20261111.md#api-계약)

## 4. 팀 환경에서 확인할 시나리오

UI는 테스트 API 주소를 연결해 실제 브라우저에서 확인합니다. 아래는 API가 같은 PC의 9000번 포트에서 실행 중일 때의 `ui/.env.local` 예시입니다.

```dotenv
VITE_USE_MOCK=false
VITE_API_BASE_URL=/api
VITE_API_PROXY_TARGET=http://localhost:9000
```

`ui/`에서 `npm ci` 후 `npm run dev`를 실행합니다. 자동 카드 검수에 사용할 **테스트 Aura 이력 구역, 실제 장비에 맞는 매뉴얼 적용 범위, 예시 경보**는 API·RAG 담당자와 맞춥니다. 자동 카드 검수에는 같은 센서 패턴과 매뉴얼 사례로 해결한 별개 케이스 두 건이 필요합니다. 저장소의 ML 예시는 비교 가능한 물리 채널이 하나여서 **채널 부족 표시**를 검수할 때 사용합니다. [ML 예시 입력](../../ml/docs/rag_handoff_early_warning.example.json) · [API 실행 설정](../../api/docs/warning-api-20261111.md#실행)

| 시나리오 | UI 통과 기준 |
|---|---|
| **새 경보 / 채널 부족** | 상세 진입만으로 후보를 생성하는 요청이 나가지 않습니다. 센서 소견을 확인한 뒤 버튼으로 후보를 요청할 수 있습니다. 빈 후보나 생성 실패에서 수동 검색으로 진행할 수 있습니다. |
| **첫 해결 / 두 번째 해결 / 다음 경보** | 첫 해결은 참고 후보로, 두 번째 해결이 Aura에 반영된 뒤 다음 경보는 자동 카드로 확인합니다. 다른 API에서 해당 자동 카드와 PDF 근거를 열 수 있습니다. |
| **자동 카드 거절** | **아니에요**를 누른 사례가 목록과 선택에서 빠집니다. 다른 후보나 PDF 근거를 선택해 진행할 수 있습니다. |
| **반복 경보 / 새로고침** | 반복 경보를 선택해 점검과 조치를 임시 저장합니다. 새로고침 후 해당 경보를 열면 그 경보의 초안이 복원되고, 종료 요청에도 같은 `event_id`가 전달됩니다. |
| **수동 근거 / Aura 반영 지연** | PDF의 해당 쪽을 열고 근거를 선택한 뒤 해결 종료합니다. 반영 중에는 완료로 표시되지 않고, 반영 뒤에는 완료 또는 수동 근거 검토 대기가 표시됩니다. |
| **오알람 / 기존 CRITICAL** | 오알람이 해결 이력으로 집계되지 않습니다. 기존 E 코드 카드·점검·일지 화면을 계속 사용할 수 있습니다. |

검수 결과에는 케이스 번호와 실제 선택한 `event_id`, 기대한 화면과 실제로 보인 상태를 함께 남겨 주세요. API 응답과 화면이 다른 경우 해당 요청 경로와 HTTP 상태를 적어 주면 원인을 함께 확인할 수 있습니다.
