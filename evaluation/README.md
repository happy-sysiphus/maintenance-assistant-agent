## 1. 감지 성능

**확인한 것.** 운영 모델(IsolationForest + LightGBM 앙상블, 60초 창, 피처 46개, 설비별 기준)이 고장 전 구간과 정상 구간을 얼마나 가려내는지, 그리고 종료 코드 규칙과 조기 경보가 고장 전에 켜지는지를 봤습니다.

**자료.** 공개 데이터의 테스트 8건(60초 창 80,533개)입니다. 검증 14건과 학습 64건의 4-fold 교차검증도 함께 봤습니다.

**방법.**

- AUROC는 고장 전 1시간의 창을 양성, 정상 창을 음성으로 둡니다. 에러 상태인 창은 양쪽 어디에도 넣지 않습니다.
- 종료 코드 규칙은 서빙과 같은 방식(코드 네 개, 에피소드 시작에 한 번, 30분 쿨다운)으로 돌려 고장 전 1시간 안에 켜졌는지 봅니다.
- 조기 경보는 종료 코드 10~60분 전에 켜졌으면 적중입니다. 고장이 없는 날의 같은 시각에 켜진 비율(우연)과 비교합니다.

**지표 읽는 법.** AUROC는 고장 전과 정상을 가려내는 정도입니다. 0.5는 찍는 것과 같고 1은 완벽합니다. "규칙 이전 AUROC"는 종료 코드가 뜨는 마지막 10분을 빼고 그 앞 구간만 양성으로 친 값입니다. 마지막 10분은 규칙이 잡으므로, 모델이 규칙에 더하는 몫이 이 값입니다.

| 항목 | 결과 |
|---|---|
| 종료 코드 규칙 (모델과 무관) | 8/8건 감지, 고장 전 중앙값 9.2분, critical 오트리거 0.18회/건·일 |
| 조기 경보, 테스트 | 4/8건 적중(같은 시각 고장 없는 날 21%), 오경보 8.3회/건·일 |
| 조기 경보, 교차검증 합침 | 적중 49%, 우연 34%, 오경보 16.4회/건·일 |
| AUROC | 테스트 0.713(규칙 이전 0.671), 검증 0.767, 4-fold 0.688 ± 0.057 |
| 클래스별 테스트 AUROC | E01 0.537, E02 0.913, E03 0.860, E04 0.622 |
| 정상 구간 알람률 | 0.5%(건별 0.1~1.4%) |
| 30분 이상 앞서면서 오탐이 하루 1회 이하인 건 | 0/8 |

**읽을 때 주의할 점.**

- 고장 직전의 확인은 종료 코드 규칙이 합니다. 이 데이터에서 종료 코드는 고장 약 10분 전에 시작합니다.
- 수 시간 전 예지는 이 데이터로 할 수 없다고 판정했습니다. 80건이 모두 "고장 직전 7일"이라, 긴 시간에 걸친 변화가 고장 때문인지 시간이 흘러서인지 가를 수 없습니다.
- 테스트는 8건이고 클래스마다 1~3건입니다. 클래스별 수치는 건 하나에 좌우되고, 분할 하나의 AUROC는 ±0.04쯤 흔들립니다.

**다시 실행.** `ml/` 폴더에서 실행합니다. 모델과 데이터 파일은 [ml/README.md](../ml/README.md)의 안내대로 받습니다.

```bash
python .py/train.py --exclude-non-welding --cv 4
python .py/train.py --evaluate
```

## 2. 피처 절제

**확인한 것.** 시각 피처나 에러 코드 피처를 빼면, 또는 LightGBM을 빼면 점수가 어떻게 달라지는지 봤습니다(실험 번호 B-22).

| 구성 | 피처 수 | 테스트 AUROC | 규칙 이전 AUROC |
|---|---:|---:|---:|
| IsolationForest 단독 | 46 | 0.645 | 0.619 |
| IsolationForest, 시각 피처 제외 | 42 | 0.638 | 0.612 |
| IsolationForest, 에러 코드 피처 제외 | 44 | 0.607 | 0.594 |
| IsolationForest, 시각·에러 코드 피처 제외 | 40 | 0.619 | 0.608 |
| **앙상블 (운영 모델)** | 46 | **0.713** | 0.671 |
| 앙상블, 시각·에러 코드 피처 제외 | 40 | 0.582 | 0.570 |

**읽는 법.** LightGBM을 더하면 테스트 AUROC가 0.645에서 0.713으로 오릅니다. 앙상블에서 시각과 에러 코드 피처를 빼면 0.582로 내려가므로, 앙상블의 분리력은 이 피처들에 많이 기대고 있습니다.

## 3. 모델 루프 재생

**확인한 것.** 데이터가 쌓이는 대로 다시 학습하고, 새 모델이 지금 모델보다 나을 때만 바꾸는 루프가 실제 데이터에서 어떻게 판정하는지 봤습니다(D-11).

**자료와 방법.** 학습용 64건을 고장 시각 순서대로 흘려보내며 일주일에 한 번 점검했습니다. 16건이 모이면 첫 모델을 만들고, 새 파일이 5건 쌓일 때마다 다시 학습합니다. 두 모델이 모두 처음 보는 파일 5건 이상으로 비교하며(섀도 비교, 시드 3개), 조건 다섯 가지를 계산해 설정한 조건을 모두 넘으면 교체합니다.

| 재생 | 교체에 쓴 조건 | 판정 세 번 |
|---|---|---|
| [replay-1](ml/D-11-model-loop-replay-1.md) | 다섯 조건 모두. AUROC 차가 시드를 바꿀 때 생기는 폭보다 커야 함 | 유지, 유지, 유지 |
| [replay-2](ml/D-11-model-loop-replay-2.md) | 지금 기본값인 세 조건. AUROC 차가 0보다 크고, 조기 경보 적중이 줄지 않고, 오알람이 하루 24회 이하 | 유지, **교체(v001 → v003)**, 유지 |

replay-2에서 교체할 때의 수치는 섀도 파일 5건에서 AUROC 0.7002 → 0.7219, 조기 경보 적중 0건 → 1건, 오알람 2.83 → 5.37회/건·일이었습니다.

**읽을 때 주의할 점.** 교체 때의 AUROC 차 0.0217은 시드만 바꿔도 생기는 폭(0.10) 안에 있습니다. 두 재생의 차이는 교체 조건을 다섯에서 셋으로 줄인 데서 나왔습니다.

**파일.** 실행 명령과 출력은 `ml/results/D-11/runs/`의 `run.log`에 있습니다.

## 4. 현장 판정 반영

**확인한 것.** 작업자가 닫은 조기 경보의 판정이 api에서 ML의 다음 학습까지 흘러가는지, 그리고 그 판정이 모델을 바꿨다고 말할 수 있는지 봤습니다(D-12).

**방법과 결과.**

- [check-1](ml/D-12-feedback-check-1.md): 데이터 재생으로 낸 조기 경보 1건을 "이상 점검 1건, 해결"로 닫았습니다. `GET /api/ml/feedback`과 `model_loop.py feedback pull`을 거쳐, 다음 학습에서 그 경보 뒤 60개 창(전체의 0.06%)이 정상 학습 데이터에서 빠진 것을 확인했습니다.
- [control-1](ml/D-12-feedback-control-1.md): 경보와 관계없는 한 시간(60개 창)을 뺀 대조 실험을 세 번 했습니다. 조기 경보 임계값은 0.953~0.986, 교차검증 건별 AUROC는 0.792~0.823으로 흩어졌습니다. 판정 1건을 넣었을 때의 값(0.9465, 0.7916)은 이 범위 안이거나 그 끝에 붙어 있었습니다.

**읽는 법.** 판정이 학습까지 가는 길은 확인됐습니다. 판정 1건이 모델을 좋게 했는지 나쁘게 했는지는 말할 수 없습니다. 창 몇십 개만 빠져도 학습 결과가 그만큼 움직이기 때문입니다.

## 5. 근거 검색과 답변

**확인한 것.** 매뉴얼 질문에 필요한 근거를 찾아오는지, 답변이 찾아온 근거에 충실한지 봤습니다.

**자료.** 50문항입니다. E 코드 네 개에 8문항씩 32문항, 코드 없는 일반 매뉴얼 질문 18문항입니다. 질문과 기준 답변은 매뉴얼 PDF 네 종에서 자동으로 만들었고, 인용문이 지정한 쪽에 실제로 있는지 자동 검사했습니다.

**방법.** 서비스가 쓰는 `answer_question()`을 캐시와 대화 이력 없이 실행하고, 공식 `ragas` 0.4.3의 지표로 채점했습니다. 답변은 Claude Sonnet 5.5, 임베딩은 text-embedding-3-small, 평가자는 GPT-4.1-mini입니다.

| 지표 | 뜻 |
|---|---|
| Context Recall | 기준 답변의 사실 가운데 찾아온 근거가 뒷받침하는 비율. 필요한 근거를 얼마나 찾아왔는지 |
| Context Precision | 쓸모 있는 근거가 검색 결과의 앞쪽에 왔는지 |
| Faithfulness | 답변의 주장 가운데 찾아온 근거로 뒷받침되는 비율 |
| Factual Correctness F1 | 답변과 기준 답변의 사실이 서로 얼마나 겹치는지 |
| Answer Relevancy | 답변이 질문과 관련 있는지 |

| 지표 | 10/28 (개선 전) | 11/04 (개선 뒤) | 11/04 E 코드 32문항 | 11/04 일반 18문항 |
|---|---:|---:|---:|---:|
| Context Recall | 0.875 | **0.913** | 0.943 | 0.861 |
| Context Precision | 0.702 | 0.671 | 0.793 | 0.456 |
| Faithfulness | 0.9795 | **0.9794** | 0.996 | 0.950 |
| Factual Correctness F1 | 0.440 | 0.538 | 0.574 | 0.475 |
| Answer Relevancy | 0.528 | 0.534 | 0.545 | 0.513 |
| 평균 응답 시간 | 4.3초 | 10.6초 (p95 14.8초) | | |

11/04에는 PDF 198쪽을 표 경계를 살려 다시 변환했고, 검색 문맥을 넓혔고, 답변 모델을 바꿨습니다. 세 가지를 함께 바꿨으므로 점수 차이를 어느 하나의 효과로 읽지 않습니다.

**함께 한 비교.**

- 청크 크기: 일반 질문 18개를 벡터 검색만으로 비교했습니다. 600자, 900자, 1200자에서 Recall@8이 0.78, 0.83, 0.83이고 MRR@8이 0.514, 0.513, 0.518이어서 1200자를 유지했습니다.
- 정비 이력 반영 사례: E016에 "첫 점검(K1)은 정상이었는데 재발했다"는 합성 기록 2건을 넣자, 같은 점검을 되풀이하지 않고 다음 점검(K2)을 먼저 제안했습니다. 사례 한 건의 비교입니다.

**읽을 때 주의할 점.**

- 기준 답변은 자동으로 만든 합성 답변입니다. 사람이 검증한 정답이 아닙니다.
- Factual Correctness F1 0.538은 정답률 53.8%가 아닙니다. 짧은 기준 답변과 주장이 겹치는 정도라서, 근거가 있는 보충 설명도 점수를 깎습니다.
- 청크 크기를 고르는 데 쓴 일반 질문 18개가 평가 50문항에도 들어 있습니다.

**다시 실행.** 저장소 루트에서 PowerShell로 실행합니다. `rag/.env`의 Neo4j Aura, OpenAI, Anthropic 설정이 필요하고 API 비용이 듭니다(11/04 실행은 약 2.5달러). 자세한 옵션은 [rag/RAGAS/README.md](../rag/RAGAS/README.md)에 있습니다.

## 6. 경고 안내

**확인한 것.** E 코드가 없는 센서 경보에서 점검 근거를 찾는 단계와, 과거 해결 카드를 돌려주는 단계를 따로 봤습니다.

**자료.** 합성 입력 50건입니다.

- 새 경보 25건: 20건에는 압력, 위치, 전극 등의 정답 근거를 미리 지정했고(모두 22개), 5건은 센서 관측만으로 근거를 고르기 어려운 경우로 만들었습니다.
- 재발 경보 25건: 합성 해결 이력 6종을 등록해 두고, 20건은 본 문항, 5건은 카드를 보여 주면 안 되는 대조군으로 만들었습니다.

**방법.** 제품이 돌려준 근거와 카드를 미리 지정한 정답과 직접 비교했습니다. 정밀도는 돌려준 것 가운데 맞은 비율이고, 재현율은 정답 가운데 찾아낸 비율입니다. 재발 경보 쪽은 Claude가 마지막에 고르는 과거 이벤트만 정답으로 고정하고, 그 뒤의 그래프 조회, 응답 검증, 카드 구성을 확인했습니다.

| 단계 | 정밀도 | 재현율 |
|---|---:|---:|
| 키워드 검색 상위 5건 | 2.61% (3/115) | 13.64% (3/22) |
| 키워드 + 벡터 검색 상위 5건 | 3.48% (4/115) | 18.18% (4/22) |
| Claude 자동 후보 | 16.67% (2/12) | 9.09% (2/22) |
| 과거 해결 카드 | 100% (20/20) | 100% (20/20) |
| 카드 필드 | 100% (200/200) | 100% (200/200) |

- 자동 후보는 25건 가운데 12건에서 하나씩 나왔고, 12건은 후보 없음, 1건은 생성 오류였습니다.
- 대조군 5건(모델의 `unseen` 응답, 잘못된 선택 ID, 전체 결측, 미래 이력, 같은 에피소드의 이력)은 모두 카드 표시를 보류했습니다.

**읽을 때 주의할 점.**

- 입력이 합성입니다. 현장 정비 성능을 검증한 것이 아닙니다.
- 채점은 미리 지정한 근거만 정답으로 칩니다. 다른 쓸 만한 매뉴얼 문구를 찾아도 점수를 받지 않습니다.
- 카드 100%는 과거 이벤트 선택을 정답으로 고정했을 때의 값입니다. Claude가 맞는 과거 사례를 고르는 정확도는 이 평가에 들어 있지 않습니다.
- 자동 후보가 낮은 이유로 보고서는 검색어 구성을 짚었습니다. 센서 이름과 변화 상태를 이어 붙인 검색어라서 같은 쪽이 반복해서 상위에 올랐습니다. 그래서 화면에서는 자동 후보가 없을 때 작업자가 직접 매뉴얼을 검색합니다.

**다시 실행.** 저장소 루트에서 실행합니다. 팀 Aura 설정이 필요합니다.

```powershell
python -B -m rag.evaluation.timeseries --env-file rag/.env --hybrid --output rag/var/timeseries-eval/results.json
python -B -m rag.evaluation.timeseries --env-file rag/.env --hybrid --live-candidates --section unseen --output rag/var/timeseries-eval/live-candidates.json
```
